# 審查 prompt 範本

每次派審查都從這份範本開始，把 `<…>` 換成實際內容。跨家族短問答與同家 subagent 共用同一份範本。

## 第一輪（整份審查）

```text
唯讀審查（不改任何檔、不 commit、不跑會產生檔案的 build 或測試、不派 subagent）。

對象：<repo 或 worktree 絕對路徑>，<文件路徑，或 diff 檔路徑（範圍 BASE..HEAD）>。
背景：<一兩句：這是什麼、目前在第幾輪>。
依據：<設計文件、上一輪裁決檔的路徑>。
總原則：<這份工作的判準，例如「fail closed、結果不依開啟順序」>。

重點找：
- <這次最可能出錯的地方，3 到 6 條，寫成具體問題>

輸出（繁中）寫到 <結果檔絕對路徑>，分三節：
1. 落實核對：上一輪的每一項標「已關閉／未關閉＋理由」（第一輪沒有上一輪就省略）。
2. 必修／建議：每項一段，寫問題、具體反例（情境＋段落或檔案:行號）、建議修法。只列真問題，不湊數。
3. 結論：「可合併／不可合併」或「可定稿／不可定稿」，不可以的話寫明卡在哪幾項。
寫完回覆必修數量與結論。
```

## 第三輪以後（定點核對）

到了第三輪，只核對上一輪的必修有沒有修好，不再整份重審。

```text
唯讀定點核對（規則同上）。對象：<路徑>，用 `git diff <上一輪 HEAD> <本輪 HEAD>` 看本輪改動。
上一輪裁決：<路徑>。只做兩件事：
1. 上一輪的 N 項是否確實關閉（逐項：已關閉／未關閉＋理由）。
2. 本輪改動是否**新引入**必修等級的問題（只收必修，不收風格與小建議）。另外檢查修訂者自己補的細節：<列出>。
不要重審其他段落。輸出寫到 <結果檔>，結尾給結論。
```

## 規則

- 審查者一律開新的 context，不能是作者本人，也不能是接續作者的 subagent。
- 修訂者自己補了裁決沒寫的細節時，要列進下一輪 prompt，讓審查者一起看。
- 審查者的結論是給主控的意見，不是裁決；採不採用由主控決定並記錄理由。
