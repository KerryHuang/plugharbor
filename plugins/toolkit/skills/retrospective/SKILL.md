# 流程回顧與 plugin 自我進化

從**實際跑過的工作單位**（一份規格、一張票、一份報告……任何有獨立目錄的產出）提取改進機會，讓 plugin 與流程持續進化。
與 `feedback-review` 並列：它處理使用者糾正佇列，本 skill 處理流程與 plugin 的整體檢討；閉環原則共用，見 `${CLAUDE_PLUGIN_ROOT}/references/improvement-loop.md`。

> **這支 skill 自己最容易犯的三個錯，動手前先讀**：
>
> 1. **只看當前 session**：最有價值的發現常跨 session、跨工作單位。單 session 只看得到一次，會被歸成「偶發」。
> 2. **不回頭驗上一版**：只新增、不驗，就不知道哪些規範沒生效。**Step 0 是第一動作，不可跳過。**
> 3. **按「要改哪個檔」分類**：那是症狀分類，三次返工分屬三個 skill 就變三條獨立改進，看不出同一根因。Step 2 先歸併根因再分類。

## 輸入參數

`$ARGUMENTS` → `[--apply] [skill-name]`

| 參數 | 預設 | 說明 |
|------|------|------|
| （無） | — | 回顧整個 session，產出改進報告 |
| `--apply` | — | 產出報告後，詢問確認並直接修改 plugin 檔案 |
| `{skill-name}` | — | 只回顧特定 skill 的使用體驗（可與 `--apply` 合用） |

## 設定

讀專案的 `.plugharbor/toolkit.yml`：

```yaml
retrospective:
  path: docs/retrospective      # 帳本 metrics.yml 與報告所在的版控目錄
  units_glob: "docs/*/*"        # 選填：工作單位目錄樣式，預設 docs/*/*
```

- `path` 不可指向 `${CLAUDE_PLUGIN_ROOT}`（那是安裝快取，更新時會被蓋掉），要在專案的版控目錄內。
- 檔案或 `retrospective.path` 缺失 → 用一題提問問使用者要放哪（建議 `docs/retrospective`），確認後寫入該檔，不猜路徑。
- 提問工具：Claude Code 用 `AskUserQuestion`、pi 用 `ask_user`，其他環境用純文字一次問一題。

## 執行流程

### 0. 先驗上一版：改動有沒有生效（**第一動作，不可跳過**）

閉環原則見 improvement-loop.md 第 1 節。

1. 讀 `{retrospective.path}/metrics.yml`（格式見 [references/metrics-ledger.md](references/metrics-ledger.md)）所有 `status: open` 的待驗指標。檔案不存在＝首次回顧，直接進 Step 1。
2. 逐條看 `due` 是否到期：`date` 比今天；`new_chains` 用該條 `due` 裡記的 `units_glob`（沒記才用設定值）數 `since` 之後新增的工作單位（以目錄在 git 的首次 commit 日期計）。
   **未到期不判定**，只追加一筆 `verdict: not-due` 並寫目前進度。
3. **到期的逐條判定**：生效／未生效／有副作用，**每條附本次的具體證據**，不寫「應該有效」；
   判定追加到該條 `checks`、改 `status`，舊的 check 不改。

| 判定 | 意義 | 後續動作 |
|------|------|---------|
| ✅ 生效 | 有具體證據顯示問題不再發生 | 記錄，不再重複改 |
| ❌ 未生效 | 問題照樣發生，或換個形式發生 | **本次最高優先**：上次的解法方向錯了 |
| ⚠️ 有副作用 | 問題解了但帶出新問題 | 補防護，不要回退 |

### 1. 收集證據（**不限於當前 session**）

跨工作單位重複才是模式，模式才值得改 plugin。

**A. 當前 session**（一定要看，**不可派 agent**：agent 看不到對話脈絡，派出去只拿到憑空推測）

| 收集項 | 找什麼 |
|--------|--------|
| 調用了哪些 skills、順序 | 使用頻率、銜接是否卡頓 |
| **使用者的修正** | 「不對」「改成」——skill 指引不明確處，訊號最強 |
| 補充說明 | 使用者額外解釋 skill 沒涵蓋的內容 |
| 流程卡點 | 等待、重試、繞路（該流程有摩擦紀錄就以它為準，不靠回想） |
| 手動調整 | 使用者手改 skill 產出 → 範本或格式要改 |
| 好的模式 | 使用者確認「對」「就是這樣」，值得固化 |

**B. 跨 session／跨工作單位**（找重複模式，**不可省**）——素材量大且對歸併根因無用，派 `general-purpose` agent 取結論。
先做完 A，把歸納出的**候選症狀**當成搜尋主題（沒有主題的「找找看」只會回來雜訊）：

```
subagent_type: "general-purpose"
model: sonnet
prompt: |
  蒐集跨工作單位的重複模式證據。**只列證據與出現次數，不做根因判斷。**
  來源：① 專案記憶／決策日誌（同一條教訓記兩次以上＝規範沒攔住）
  ② 近期完成的其他工作單位（同樣的返工是否也發生過）
  ③ 被檢討 plugin 的 CHANGELOG 歷史（「修過又復發」＝當初改錯層級）
  ④ 近期交付物是否重複出現同類缺陷
  ⑤ 各流程的卡點紀錄（執行當下記的，比回想可信）
  本次要找的主題：{A 項歸納出的候選症狀，逐條列}
  回報格式：每條一列——症狀｜出現次數｜各次出處（檔案:行號）｜是否「修過又復發」。
  禁止貼原文段落，只給定位。
```

> 判準：**一次是偶發，兩次是巧合，三次是流程缺陷**。只有第三類值得改 plugin，前兩類改了是過度反應。

**C. 量化成本**（有就取，沒有不要編）

```bash
python3 ${CLAUDE_SKILL_DIR}/scripts/chain_cost.py <單位路徑> [--units-glob '<樣式>'] [--projects-dir <dir>]
```

輸出 markdown 表：session、輪數、token、本單位占比、分攤輪數、分攤 token。
**只支援 Claude Code**，且只讀本機 `~/.claude/projects`（Codex、pi、別台機器量不到）——報告要寫「僅本機 Claude Code」；
多單位 session 只取分攤欄，不可整筆算進單一單位。`--units-glob` 預設 `docs/*/*`，與 `retrospective.units_glob` 一致。
返工次數、交付前驗證抓出的缺失數從 git log 與決策紀錄取。
**沒有實際數據時直說「無量化數據」，不要憑印象給數字。**

### 2. 根因歸併（**分類之前先做**）

把所有證據攤開問：**這幾件事，是不是同一件事？** 看「當時為什麼會做錯」，不是「錯在哪個檔案」。

| 歸併訊號 | 例 |
|---------|---|
| 同一個錯誤動作，發生在不同 skill | 三次都是「照抄既有產出而沒讀範本」 |
| 同一個缺失的檢查點，換形式出現 | 契約不一致、欄位對不上，都是「沒回查上游契約」 |
| 同一個前提被沿用而沒人驗 | 多份文件引用同一個錯誤結論 |

歸併後才分類。三條獨立的 P1 歸併成一條根因後，往往升成 P0，且解法是一條原則而非三個補丁。

### 3. 分類改進點

將**歸併後的根因**分為五類：skill 內容（步驟遺漏、指引模糊、產出格式、判斷邏輯）、範本（章節、欄位、範例）、
reference（知識補充或修正、新增）、流程（銜接斷裂、前置缺失、重複工作、順序不當）、新增需求（新 skill／reference／範本）。

### 4. 評估影響與優先級

| 優先級 | 條件 | 行動 |
|--------|------|------|
| P0 | 影響正確性，**或上一版判定為 ❌ 未生效** | 立即修復 |
| P0 | **固定成本結構問題**：每個工作單位都付、與功能複雜度不成比例 | 立即修復 |
| P1 | 影響效率（流程卡頓、重複工作） | 下次更新修復 |
| P2 | 影響體驗（格式、順序、提示） | 排入待辦 |
| P3 | 新功能建議 | 評估後決定 |

> 「固定成本結構問題」不可降到 P3：它不算錯、只是有點多餘，所以極容易被降級，但每個工作單位都收一次稅。
> 判別問：**這個成本，簡單的工作單位付得起嗎？**

同為 P0 時，上一版未生效的排最前：方向判斷錯過一次，再錯一次的代價是使用者對整套流程失去信任。

### 5. 產出回顧報告並記帳

根因、優先級、版本建議由主 session 判定，報告由主 session 依 [references/report-template.md](references/report-template.md) 寫到
`{retrospective.path}/{YYYYMMDD}-{slug}/report.md`（證據附檔放同目錄）。要求：

- **開頭先一句結論＋三個數字**（例：「上一版兩項未生效；本次 3 個根因、P0 4 項、待驗指標 6 條」）
- 全文 ≤1500 字，證據與量測細節放附檔
- 「本次的待驗指標」必填且判準可觀察
- 無量化數據時直說，不憑印象給數字；不放人名，寫角色

報告寫完，把「本次的待驗指標」逐條**追加**進 `{retrospective.path}/metrics.yml`（格式見 metrics-ledger.md）。
`due` 只能寫 `new_chains` 或 `date`；寫不成這兩種的指標無法自動到期，改寫成可數的判準。

### 6. 執行修改（--apply 模式）

僅在使用者指定 `--apply` 時執行。修改前用提問工具列出即將修改的 P0／P1 項目（P2／P3 只列報告），等待確認。

**改法的優先序：刪 → 改寫既有句 → 新增。** 先問「刪掉哪句能解決」，再問「改哪一句」，兩者都不行才新增，
並在報告寫明為何刪與改都不夠。改完對動到的段落做逐句 no-op 測試：拿掉這句，執行者的行為會變嗎？不會就刪。
回報每個動到的檔案行數前後（例：299 → 281）。

確認後依 [references/apply-changes.md](references/apply-changes.md) 執行。**版號不要自己改**，交 `release-plugin` 類機制統一同步。

## 收尾條件

全部成立才算完成：

1. Step 0 上一版驗證已做
2. 報告已寫入 `{retrospective.path}/{YYYYMMDD}-{slug}/`，正文 ≤1500 字
3. 「本次的待驗指標」已填實、判準可觀察，且已追加進 `metrics.yml`（解析通過）——那是下次 Step 0 的唯一輸入
4. `--apply` 模式：改動已套用並逐項列出改了哪些檔；未套用的說明原因

## 錯誤處理

| 情境 | 處理 |
|------|------|
| 當前 session 無 skill 使用記錄 | **不終止**，改走 Step 1-B 的跨 session 證據。使用者問「檢討流程」時，往往正是在沒跑 skill 的 session 裡問的 |
| 完全無任何證據來源 | 才終止，說明查了哪些來源都是空的 |
| 指定的 `{skill-name}` 不存在 | 列出可用 skill 名稱，終止 |
| `chain_cost.py` 回報沒有 session 動過該單位 | 檢查單位路徑是否符合 `--units-glob`；仍無就記「無量化數據」 |
| 找不到 `release-plugin` 等版號同步機制 | 依該 repo 的 `CLAUDE.md` 手動同步全部位置，並在報告標明改了哪幾處供覆核 |
