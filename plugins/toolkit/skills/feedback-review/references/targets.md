# 改動目標判定細則

## 判準

**換到任何專案都成立嗎？** 成立才放 user 層；只要提到某專案的目錄、流程、業務名詞、
連線、內部工具，就放該專案的 CLAUDE.md 或 `.claude/rules`。拿不準時放專案層——
放錯專案層只影響一個專案，放錯 user 層會污染所有專案。

## 各目標的寫法

- **user 層 rules／CLAUDE.md**：寫行為，不寫事件。「刪檔前先看目標」可以；
  「上週二刪錯了某檔」是 memory。
- **專案層**：先看專案既有的規則分層（常駐 vs 依路徑懶載入 vs 參考文件），新條文放進對應層，
  不要一律塞常駐檔。
- **memory**：一次性事實、踩坑紀錄、還沒確認是通則的觀察。同一類 memory 累積多次被糾正，
  才考慮升級成 rule。
- **plugin skill**：不直接改 plugin 檔。plugin 有 retrospective 類 skill 就把證據清單交給它；
  沒有就在報告列出「建議回報給 plugin 維護者」。

## 邊界案例

| 情境 | 判定 |
|---|---|
| 糾正的是一次性的誤解（agent 讀錯需求） | 雜訊，除非同類誤解重複出現 |
| 糾正的規則其實已經寫在目標檔，只是沒被遵守 | 不加新條；照下節「升級成機制」 |
| 同一群跨 user 層與專案層 | 拆成通用原則（user）＋專案的具體做法（專案），分兩題問 |
| 糾正對象是使用者自己前一句話（「不對，我剛說錯了」） | 雜訊 |

## 升級成機制

文字被跳過時什麼都不會失敗，所以已寫過還再犯的，換更硬的機制。由上往下取第一個做得到的：

1. **guard**：能用 regex 從工具呼叫（Bash 指令、寫入的內容）判斷的 → `~/.claude/guards/`（通用）或
   `<專案>/.claude/guards/`（專案）加一條，`evidence` 寫這群的根因與佇列 id。
2. **腳本**：重複的確定性步驟 → 寫成腳本，規則改成「跑這支」。
3. **測試／validator**：產出可檢查的 → 加測試案例或 validator 規則。
4. **文字**：只能靠判斷的才改寫既有條文（更具體、移到更早載入的位置），或判定被長 context 淹沒而配合減量。

提案要附證明：用這群的原話情境做一個測試案例，展示新機制擋得住。機制上線後，原本的規則文字
改成一行指向它，列進 Task 4 的可刪候選。
