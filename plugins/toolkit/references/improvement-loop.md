# 改進閉環：先驗上一輪、人審、記帳

`feedback-review`（回顧使用者糾正）與 `retrospective`（回顧流程與 plugin）共用這三條。兩者的差別只在證據來源與帳本位置，閉環一致。

## 1. 先驗上一輪（第一動作，不可跳過）

回顧開始先看上一輪改了什麼、有沒有生效，再看新問題。只往上疊規則、不回頭驗，就不知道哪些根本沒生效。

- 每條改動記帳時就寫好**可觀察的驗效訊號**（例：「同類糾正是否再出現」「某階段缺失數是否下降」；「品質變好」不算）。
- 判定三種：生效（有具體證據顯示問題不再發生）、無效（問題照樣發生或換形式發生）、樣本不足（未到期，只記進度，不判定）。
- 判定必須附本輪證據，不寫「應該有效」。舊的驗效紀錄只追加、不改寫。
- 無效的條目**排在本輪最前面**：代表上次的方向錯了。不要再疊一條同類文字，改想更強的機制（hook、guard、腳本）或刪掉。
- 有副作用的：補防護，不要整個回退（回退會把省下的也還回去）。

## 2. 人審

每條改動經使用者核准才套用，不自動改。自動改規則會劣化（理由見 `${CLAUDE_PLUGIN_ROOT}/skills/feedback-review/references/principles.md`）。

- 只做增量 Edit，不整檔重寫。
- 改法優先序：刪 → 改寫既有句 → 新增。新增要說明為何刪與改都不夠；每加一條附一個可刪或可合併的候選。
- SKILL.md 與 rule 本文只寫通則與判準；情境、證據、日期留在報告、帳本或 CHANGELOG。「為什麼」對判斷邊界有用時放 `references/`，並抽掉專案與當次細節。
- 一次問一項，不合併、不先列清單讓使用者挑。

## 3. 記帳

核准並套用後，把改動連同驗效訊號寫進帳本，狀態＝觀察中，供下一輪第 1 步使用。

- 帳本跟著**改動目標**走，不跟著執行位置走。
- 帳本進版控的，內容不放人名（寫角色）。
- 帳本格式：`feedback-review` 見 `${CLAUDE_PLUGIN_ROOT}/skills/feedback-review/references/ledger-format.md`；`retrospective` 見 `${CLAUDE_PLUGIN_ROOT}/skills/retrospective/references/metrics-ledger.md`。
