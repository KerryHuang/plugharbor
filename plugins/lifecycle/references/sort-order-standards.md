# 排序規範（查詢／清單／明細／匯出）

> 通用規範，**不綁特定專案的值**。目的：讓「查詢出來的資料要怎麼排」在分析設計階段就有答案，
> 而不是丟給 Dev 猜——排序猜錯的後果是資料看起來對、順序卻不穩，沒有人會回報。

## 適用範圍

任何**回傳多筆**的畫面區塊或端點：查詢清單、明細子表、下拉選單、匯出檔、列印報表。
單筆 CRUD 不適用。

## 兩階段寫法（沿用 FRD → SAD → BFS／FFS 逐階段具體化的慣例）

| 階段 | 寫什麼 | 例 |
|------|--------|-----|
| FRD | **業務語意**，不寫欄位不寫 SQL | 「最新的訂單優先」「明細依建檔順序」 |
| SAD | **排序策略決策**——由誰排（前端／後端）、使用者可否改、與分頁的關係 | 「後端排序，可由使用者切換，白名單 3 欄」 |
| BFS／FFS | **明確值**——欄位 + 方向 + 下列五要素 | `訂單日期 DESC, 訂單號 DESC` |

PM 在 FRD 階段不該被迫寫 `ORDER BY`；SA 在 BFS／FFS 階段不該還留著「最新在前」這種話。

## 五要素（BFS／FFS 必填，缺一即未就緒）

| # | 要素 | 說明 |
|---|------|------|
| 1 | **排序鍵** | 欄位 + 升冪／降冪 |
| 2 | **決勝欄（tie-breaker）** | 排序鍵在該資料集**非唯一**時必填，見下 |
| 3 | **NULL 位置** | 排序欄可為空時必填，見下 |
| 4 | **序語意** | 字串型編號欄位必須標「字面序」或「數值序（含轉型規則）」，見下 |
| 5 | **使用者可否改** | 可排序欄位白名單；改過之後重新查詢是否回到預設 |

---

## 1. 決勝欄（阻塞級）

**判定基準**：排序鍵的值在這份資料集裡是否**唯一**？不唯一 → 必須在末位追加一個唯一欄（PK 或唯一單號）。

不加的後果不是「順序不好看」，而是**資料庫不保證同值列之間的先後**，且每次查詢可能不同。
一旦接上分頁，第 1 頁與第 2 頁會**重複或漏掉**同一筆資料。

```
❌ 訂單日期 DESC                     ← 同一天多張訂單，順序不定
✅ 訂單日期 DESC, 訂單號 DESC        ← 末位唯一，順序穩定且可重現
```

常見非唯一排序鍵：日期（無時間部分）、客戶、狀態碼、金額、任何用來分組的欄位。

## 2. NULL 位置

不同資料庫的 NULL 預設位置不同（例如 SQL Server 與 PostgreSQL 的預設相反），規格不得依賴預設行為，要明寫期望。

排序欄可為空時（如預定交貨日、完成日），規格必須明寫期望位置。
「空交期的單子浮在第一頁最上面」看起來像 bug，實際上是規格沒定。

規格只寫**期望結果**（「空值排最後」），實作手法由 RD 決定。

## 3. 序語意——字串型編號的字典序陷阱

若專案有 `char`／字串型編號欄位且**未左補零**，字典序 ≠ 數值序：

```
字面序：'1', '10', '2', '9'      ← 「最小編號在上」在這裡直接失效
數值序：'1', '2', '9', '10'
```

另外，資料庫定序（collation）可能不分大小寫，混用不同字串型別時中文與英數的相對順序也可能不同。

規格要求：排序鍵是字串型編號時，必須標明採字面序或數值序；採數值序要寫出轉型規則
（含非數值資料如何處理）。標「數值序」而未定義非數值列的行為＝未就緒。

## 4. 前後端分工（預設立場）

| 情境 | 誰排 |
|------|------|
| **有分頁的清單** | **一律後端全量排序**。點欄位標題＝重打 API 帶排序參數 |
| 無分頁、全量資料已在前端（明細子表、下拉選單） | 可前端排序 |

❌ **禁止**：分頁清單做「當頁排序」。畫面看起來會動，但排的只有當前這頁，
使用者以為看到的是全部資料的最大／最小值——這是靜默失效，不會有人回報。

FFS 只在**偏離**上表時才需說明理由；符合預設立場者不必逐頁重述。
此決策同時決定 API 收不收排序參數，屬 SA 該拍板的契約，不是前端自行決定的互動細節。

## 5. 明細（子表）排序

每個明細區塊都要寫預設排序，且必須指名採哪一種序：

| 語意 | 說明 | 常見誤用 |
|------|------|---------|
| 顯示序號 | 單據上的項次欄 | 與建檔序混為一談 |
| 建檔序 | 建立時間或自增鍵 | 中途插入的列位置會跑掉 |
| 業務鍵 | 商品編號、料號等 | 字串型編號踩第 3 節的坑 |

明細若可**中途插入新列**，還要定義：新列插在哪（末端／游標處）、插入後項次是否重編、
重編是否回寫資料庫。

## 6. 匯出／列印

- **預設與畫面當下的排序一致**；不一致必須明寫並說明理由（例如列印一律固定序以便對帳）。
- **分組報表要兩層**：分組鍵的順序 + 組內的順序。只寫一層等於沒寫。
- 排序規則寫在**輸出內容**層次（欄位、方向、分組），不指定產出管道或範本機制。

## 7. 下拉選單／Light API

選項順序幾乎總是被遺漏，導致每個畫面順序不同。必須定義其一：

- 常用在前（要寫出「常用」的判定來源欄位）
- 代碼序
- 名稱序（中文名稱排序受定序影響，要註明是否可接受）

停用／已刪除項目是否出現、出現時排哪裡，一併定義。

## 8. 效能

排序欄位應有索引支撐。大表對無索引欄位排序會產生排序溢寫，且症狀是「平常還好、資料量長大後突然變慢」。

SAD §6.5 NFR 註記排序欄位的索引狀況；已知大表（預估 10 萬筆以上）而排序欄無索引時，
列入 §6.3 風險。

## 檢查基準（供 dev-readiness／verifying-specs 引用）

逐項用**判定基準**掃，不要逐行點名：

1. 每個多筆區塊（清單、明細、下拉、匯出）都有預設排序？
2. 排序鍵非唯一卻沒有決勝欄？→ 阻塞
3. 排序欄可為空卻沒定 NULL 位置？→ 阻塞
4. 排序鍵是字串型編號卻沒標序語意？→ 阻塞
5. 有分頁的清單標了「前端排序」而無理由？→ 阻塞
6. 匯出／列印排序與畫面不一致而未說明？→ 阻塞
7. 排序欄位在資料庫真的存在、型別支援該語意？→ 需實查
8. 分組報表只寫了一層排序？→ 阻塞
