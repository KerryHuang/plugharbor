# 決策紀錄（`decisions.md`，跨階段交接契約）

> 適用：`requirement`（FRD）、`system-analysis`（SAD）、`specify-backend`（BFS）、
> `specify-frontend`（FFS）、`dev-readiness`／`verifying-specs`／`linear-reply`（回寫）、編排規格鏈的呼叫端（讀取）。
>
> **範圍限定：本版僅涵蓋標準模式。** CR（調整模式）與 `cr-frd`／`cr-bfs`／`cr-ffs` 範本
> **尚未納入**——回票改規格所產生的決策目前不會落檔。CR 的決策形狀與標準模式不同
> （多為「既有規格為何要改」而非「多個方案選一個」），需另行設計，不要把本檔的欄位
> 直接套進 `cr-*` 範本。

## 為什麼需要

規格鏈分段執行後（不同 session、不同天、不同人），**文件是唯一交接面**。
下一棒讀不到上一棒的對話，看不到「B 方案被否決過、原因是 X」，就會重提 B、
或重問使用者已經答過的事。

## 為什麼是一份檔，不是四份文件各一章

若把 `§D` 放在每份文件裡，四份文件的 `§D` 合計會佔掉全鏈相當比例的體積，
且四份各有自己的 `D-01`（語意完全不同），69 處裸引用 `D-14` 第一次讀的人會查錯表。
決策是**全鏈**的產物，不是某一份文件的章節；讀它的人是「想推翻某個決策的人」，不是每個讀者。
所以落點改為功能目錄一份 `decisions.md`，各文件 `§D` 只留本階段的編號與一句結論。

## 落點與格式

**路徑**：`{功能目錄}/decisions.md`（與 FRD／SAD／BFS／FFS 同目錄）。

```markdown
# {功能名稱} 決策紀錄

> 全鏈唯一決策落點，D-001 起連號、只追加不重排。各文件 `§D` 只列本階段編號，完整內容在此。

| # | 決策 | 選定 | 否決的選項與原因 | 依據 | 拍板 | 階段 | 日期 | 狀態 |
|---|------|------|-----------------|------|------|------|------|------|
| D-001 | 庫存盤點差異是否即時扣帳 | 不即時，另開調整單 | 即時扣帳——與舊系統現行行為不一致且無法回溯 | 舊系統分析報告＋抽樣實資料 | PO | SAD | 2026-09-01 | 定案 |
| D-002 | 盤點單可否跨倉 | 不可跨倉（建議） | 可跨倉——調整單要拆倉別；被推翻影響 FRD §3、BFS §6.2 | 舊系統只有單倉輸入 | SA | FRD | 2026-09-01 | 暫定 |
| TD-001 | 排程快照放哪裡、怎麼失效 | **待實作定案** | — | 約束：多實例下一致、失效 ≤5 分鐘｜現況：應用層多處用行程內快取｜陷阱：多實例不共享，沿用會讀到舊快照｜候選（非指定）：分散式快取或暫存表 | Dev | 實作 | 2026-09-01 | — |
```

**各文件 `## D. 決策紀錄`** 只留：

```markdown
## D. 決策紀錄

> 全鏈決策唯一落點是同目錄 `decisions.md`（全鏈連號 D-001 起）。本節只列本階段拍板的編號與一句結論，否決選項／依據／拍板者在 decisions.md。

| # | 決策 | 選定 |
|---|------|------|
| D-004 | 規格鏈分流 | standard |
```

SPEC-INDEX 對應行：`> - §D 決策紀錄 — 本階段 D-004~D-007（完整紀錄見 decisions.md）`。

## 技術決策留置（TD）：規劃階段不定手段，開發階段定案

SA／PO 定「會被外面看見」的事：業務行為、資料語意、API 契約、權限與稽核邊界、schema 約束、
上線風險（Migration 先後、降級或停用）。**手段**——快取、鎖、佇列、儲存位置、併發原語、重試與補償的做法、
索引策略、套件——由 Dev 在開發時決定。規格遇到手段層的問題，**不定案，留置成 TD**：

| 欄位 | TD 的填法 |
|------|-----------|
| `#` | `TD-001` 起獨立連號，與 D- 並列在同一份 `decisions.md` |
| 決策 | 手段層的題目（「快照放哪裡」「衝突用哪種鎖」） |
| 選定 | 一律先填 **待實作定案**；完工回寫時改成實際做法 |
| 否決的選項與原因 | 留置時填 `—`；完工回寫時填 Dev 否決了什麼 |
| 依據 | **三樣必填**：`約束：{必須滿足什麼}｜現況：{codebase 現在怎麼做、幾處}｜陷阱：{沿用會踩什麼}`；可加 `候選（非指定）：…` |
| 拍板 | `Dev` |
| 階段 | 留置時 `實作`；完工回寫後不改 |

常見 TD：Migration 做法（DB 先行或 code 先行由 Dev 提案、PO 拍板上線風險；欄位名與型態**不是** TD，那是 §M.1 契約）、鎖種類、快取、佇列、重試與補償、索引實作。

規格正文的落點只寫提醒段，不寫方案：`> ⚠ TD-001（見 decisions.md）：約束…；現況…；陷阱…`。
Dev 票的「規格明細」列出 TD 編號。**約束、現況、陷阱三樣是 SA 在技術面的責任**——把地雷標出來，不幫人選路；
三樣寫空（「要能撐多實例」）等於沒留置，`dev-readiness` 會退回補三樣，不會退回要選型。

完工回寫（PR 合併後）：每筆 TD 的「選定」改成實際做法、「否決」補 Dev 的取捨、日期更新；`verifying-specs`
在 CHANGELOG 出現「完工回寫」後仍有「待實作定案」→ WARNING。

## 三項設計約束

1. **不新增任何分析步驟。** 只把確認門「已算出、已給使用者看過」的內容落檔。不多問使用者任何問題。
2. **各文件 `§D` 清單必進 SPEC-INDEX。** 下一棒才能不整檔載入就知道這一棒拍了什麼。
3. **`decisions.md` 與 `§D` 都不列入去重閘。** 下游引用上游決策只寫一行 `見 decisions.md D-012`，不重抄。

## 欄位規則

| 欄位 | 規則 |
|------|------|
| `#` | 全鏈 `D-001` 起連號，**只追加不重排**。append 前用定位指令取最大號 |
| 決策 | 一句話的題目，不是結論。「庫存盤點差異是否即時扣帳」對；「不即時扣帳」錯（那是「選定」） |
| 選定 | 拍板的做法 |
| **否決的選項與原因** | **強制欄，不得留空。** 確實沒有其他方案時填「無其他方案」——但先自問一次真的沒有嗎 |
| 依據 | 須可追溯：表名、檔名、票號、domain-advisor 留痕、PO 口頭。**不得只寫「討論後決定」** |
| 拍板 | `PO`／`SA`／`顧問`／`證據`；**TD 一律 `Dev`**。`證據`＝由實查定案（如附測試環境查詢結果），不是人拍板——分開標，接手者看得出哪些是查證、哪些是人決定 |
| 階段 | 該決策**產生**的階段（`FRD`／`SAD`／`BFS`／`FFS`／`dev-readiness`／`verifying-specs`／`linear-reply`）；TD 填 `實作` |
| 日期 | `YYYY-MM-DD` |
| 狀態 | `定案`／`暫定`；TD 填 `—`。規則見下節「暫定決策」 |

## 暫定決策（規格鏈中途裁決）

規格鏈跑到一半遇到要使用者裁決的題目，**不停下來問**：採建議選項當暫定、繼續做，到開票前集中問
（流程見 `${CLAUDE_PLUGIN_ROOT}/references/shared-preludes-details.md`「規格鏈中途裁決」）。落檔方式：

- `decisions.md` 記一列，`狀態` 填 `暫定`；「選定」寫建議選項，「否決的選項與原因」寫其他選項，
  並寫**被推翻時影響哪些文件哪幾章**。
- 規格正文**每一處**引用這個 D，都寫成「（暫定，D-xxx 待確認）」，不寫裸的 `D-xxx`。
- 使用者確認後：`狀態` 改 `定案`（被推翻就改「選定」並回派修文件），正文的暫定標記全部改回一般引用。
- 平台／UI 慣例題（分頁、空值與數字格式、對話框、匯出列印管道、錯誤與空狀態）照 codebase 先例直接定案，**不立 D**；正文規則旁寫一句先例出處即可。被使用者推翻的才記。
- 舊鏈的 `decisions.md` 沒有 `狀態` 欄時，從舊鏈接續就在表頭補 `狀態` 欄，既有列填 `定案`。

`skills/verifying-specs/scripts/check-decision-propagation.py` 的 R5 機械檢查兩件事：暫定 D 在正文有沒有裸引用、定案 D 有沒有殘留暫定標記；沒有 `狀態` 欄的舊鏈 R5 跳過。

## append 協定

```bash
D={功能目錄}/decisions.md
[ -f "$D" ] || 依上方格式建檔（建檔不是缺陷，鏈上第一個拍板者建）
grep -n '^| D-' "$D" | tail -1          # 取最大號，下一列接續
```

- 首個寫入者建檔；後續每棒 **append 到表尾**，不改既有列。
- `dev-readiness`／`verifying-specs`／`linear-reply` 的裁決回寫也 append 到同一檔，`階段` 填自己。
  照建議採納且無實質取捨的項不記，只記「使用者改選過的項」與「有實質取捨的項」。
- 同一次寫檔要同時做兩件事：append `decisions.md`、在本文件 `§D` 列本階段編號與一句結論、更新 SPEC-INDEX 那行。
- 「體積放行」也是決策（見 `spec-dedup-and-budget.md`）：決策＝體積放行、依據＝哪章為何不可拆。
- 本階段確實沒有任何拍板時，`§D` 保留表頭寫一列「無」，`decisions.md` 不動。章節不在，下一棒分不出
  「這次沒決策」與「上一棒漏做了」。

## 讀法（下一棒、規格鏈編排者、verifying-specs）

```bash
grep -n '^| D-' {功能目錄}/decisions.md            # 全鏈已拍板清單
grep -n '^| D-' {功能目錄}/decisions.md | grep '| SAD |'   # 只看某階段
```

- 編排者的派工 prompt 把「決策／選定」兩欄貼進去，標明「已拍板、不要重問」。
- 檔案不存在＝尚未有人拍板，**不是缺陷**；prompt 明寫「本棒若有拍板，依 `decision-record.md` 建檔」。
- `verifying-specs`：各文件 `§D` 列的每個編號都必須在 `decisions.md` 找得到（WARNING）；`§D` 未指向 `decisions.md`（WARNING）。

## 引用他鏈決策

「依據」欄要引另一條規格鏈的 D 編號時，先開那份 `decisions.md` 讀原列，並對程式碼確認它實際寫入的表／欄位。讀不到或對不上就標 `[推論]`，不寫成定案。

> 事故：某次依「另一條鏈的 D 編號規定到站時會寫某欄位」裁定覆寫規則，寫進三份文件；verifying-specs 複驗才發現
> 那條 D 寫的是另一張表的欄位，新系統根本沒有程式寫原欄位，只能撤回改立新 D、四份文件再修一輪。
> 他鏈決策的標題和本鏈欄位語意相近，憑記憶對上就當證據；錯誤會傳到全部下游文件。

## 什麼該記、什麼不該記

| 該記 | 不該記 |
|------|------|
| 確認門呈現過方案比較、使用者選了其中之一 | 沒有分歧的事實陳述（「這張表有 12 個欄位」） |
| 使用者推翻了建議做法 | skill 內部的執行順序選擇 |
| domain-advisor 對 domain 邊界／狀態機歸屬的裁示 | 已經寫在正文規則裡、沒有被否決過的東西 |
| 體積放行、規格鏈分流 | 純格式偏好 |
| `dev-readiness` 阻塞項中有實質取捨的裁決 | 逐條照抄建議的例行項（含審查 agent／verifying-specs／dev-readiness 照建議收的修正，正文寫審查編號即可） |

## Red Flags

- **事後補寫。** 想不起來就代表當下沒有真的裁決過，不要編。
- **只填「選定」不填「否決」。** 那等於沒做——下一棒仍然看不到為什麼不能走 B。
- **把 `decisions.md` 當成待辦清單。** 沒有建議答案的未決事項屬「待澄清事項」章節；這裡只收已拍板，
  或已採建議選項、標 `暫定` 等開票前確認的。
- **在文件 `§D` 寫完整七欄。** 那就是早期版本的形狀，會把體積長回去；`§D` 只留編號與一句結論。
