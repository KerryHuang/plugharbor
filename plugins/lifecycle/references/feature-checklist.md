# 功能清單（feature-checklist.md）

讓使用者一眼看出哪些做完、哪些在做、哪些已規劃、哪些只是構想。每個專案一份，放 repo 的 `docs/feature-checklist.md`（不是規格，不放 `<spec.dir>`）；roadmap 或 README 開頭連到它。`docs/` 是文件站、submodule 或有落檔白名單時，本清單與 `docs/todo.md` 改放 repo 根目錄（`FEATURES.md`、`TODO.md`），腳本帶路徑參數。

## 格式

```markdown
# <專案> 功能清單

總計：完成 91／共 168（另有 19 項決定不做）；進行中 3、已規劃 40、構想 34；待確認 3 項。更新於 2026-11-11。

## <領域或模組>

完成 14／共 15。<可選：驗收文件、範圍說明>

- [x] 新增模組 — 一句話說明，可附驗收或設計文件
- [ ] 🚧 記錄匯入 — 部分完成：已有 CSV 新增，缺更新既有記錄
- [ ] 📋 兩條權限軸 — 設計見 docs/specs/permission-axes.md
- [ ] 💡 行動版 — 討論中提到，還沒設計（待確認）
- [-] 多租戶 — 不做：<理由>
```

| 標記 | 狀態 | 判準 |
|---|---|---|
| `[x]` | 已完成 | 已合併到主線且驗收過，或已上線 |
| `[ ] 🚧` | 進行中 | 有分支、PR 或 worker 在做；部分完成也算 |
| `[ ] 📋` | 已規劃 | 有設計文件、規格，或排進 roadmap／票 |
| `[ ] 💡` | 構想 | 只在討論出現，還沒設計 |
| `[-]` | 決定不做 | 使用者裁決或設計寫明不做；行尾附理由 |

- 每項一行：`- [狀態] <功能名> — <說明>`。票號、設計文件路徑寫進說明，不另設欄位。
- `[ ]` 一定要帶 🚧／📋／💡 其中一個；腳本把沒帶的列為「未分類」。
- 判斷不了的項目在行尾標「（待確認）」，不猜；回報時列給使用者裁決。
- 「決定不做」可留在原領域節，也可集中成一節；集中時那一節不寫小計。
- 「總計：」行與各節「完成 X／共 Y。」由腳本產生，不手算（「共」不含決定不做）。

## 與 todo 的分界

判準：做完後產品多一項使用者看得到的能力，就進本清單（做完留紀錄、不做也記理由）；其餘動作進 todo（含 bug、重構、調查、雜事），做完就丟。

| todo 的壽命 | 放哪 |
|---|---|
| 單一 session 的步驟 | CLI 內建的待辦工具 |
| 一個功能的實作步驟 | 實作計畫檔 |
| 跨 session、不屬於任何功能 | `docs/todo.md` |

- bug 進 todo；修完會多一項能力的（其實是缺功能）才進本清單。排進某版範圍的 bug，冒號後註明版本（如「（v0.3.0）」）。
- 重構、技術債進 todo；為了解鎖某功能時註明是哪一項。
- 屬於某份交付物（分析、規格、票）的待辦留在那份文件裡，`docs/todo.md` 只收不屬於任何東西的雜事。
- 調查的結論冒出新功能，才進本清單標 💡 或 📋。
- 🚧 項目拆出的步驟放 todo，本清單只記狀態與缺什麼。

`docs/todo.md` 一行一項、動詞開頭，冒號後寫脈絡，可附日期：

```markdown
# 待辦

- 清已合併的 branch：worktree 殘留 3 個（2026-11-11）
```

做完就刪（紀錄留在 git 歷史），不打勾留著；查下去發現是功能就移到本清單。不設統計腳本。

## 更新時機

| 時機 | 動作 |
|---|---|
| 設計或規格定案（brainstorming、`lifecycle:spec`） | 設計列的功能逐項加入，標 📋 |
| 討論冒出新點子、使用者沒說不做 | 加入，標 💡 |
| 開分支或派 worker 開工 | 改 🚧 |
| 合併且驗收過（`lifecycle:implement` 後段） | 與合併內容同一個 commit 打勾 |
| 使用者裁決不做 | 改 `[-]`，附理由 |
| 回報規劃結果、使用者問進度 | 附清單路徑與腳本印出的各狀態數量 |

每次改完跑 `--write` 更新數字；清單跟程式碼同一個 commit 進 git。

## 腳本

```bash
python3 ${CLAUDE_PLUGIN_ROOT}/scripts/feature_checklist.py [路徑]           # 報表：各節／總計、待確認、未分類
python3 ${CLAUDE_PLUGIN_ROOT}/scripts/feature_checklist.py [路徑] --write   # 改寫總計行與各節小計
python3 ${CLAUDE_PLUGIN_ROOT}/scripts/feature_checklist.py [路徑] --check   # 數字過期 exit 1，可放 pre-commit
python3 ${CLAUDE_PLUGIN_ROOT}/scripts/feature_checklist.py [路徑] --open    # 只列未完成項目（依節），排線用
```

路徑預設 `docs/feature-checklist.md`。總計行可以有前綴（如「依據 <commit>。」），腳本只改寫「總計：」之後。

## 排線：找出能並行的，能做的先做

規劃下一段、或使用者問「哪些可以分開做」時，以 `--open` 列出的未完成項目為輸入：

1. **分四類**，每項附一句理由（依賴什麼、會跟誰衝突）：

   | 類別 | 判準 |
   |---|---|
   | 主線 | 線內有先後依賴，前一段的產出是下一段的輸入 |
   | 獨立線 | 不依賴主線產出，也不改主線的檔案 |
   | 小件 | 半天內做完、不碰主線檔案 |
   | 先拍板 | 缺使用者裁決或設計，現在動手是猜 |

2. **列共用資源**：同一批檔案、單一序列的版本號或 migration、gate／CI 排隊、部署、瀏覽器或測試環境。共用同一資源的兩條線不同時進那個資源，要錯開或輪流合併。
3. **並行數看瓶頸，不看能拆幾條**：先找出唯一不能並行的環節（通常是 gate、CI 或部署），開的線數以不在那裡長時間排隊為準；小件塞進等 gate 的空檔。
4. **能做的先做**：一段只有一小部分被卡住，就把那部分拆成獨立項目，其餘先開工；計畫裡的步驟已被別段完成就沿用、不重做，並在計畫記一筆。
5. **先拍板類**照提問規則一題一題問，不擋其他線。
6. **回報**一張表：每條線做什麼、狀態、卡在什麼；派工方式照 user 層派工判準（subagent 或 worker）。

## 首次採用

新專案：初始化時建空清單（只有標題與總計行）。既有專案：派 subagent 從設計文件、roadmap、手冊、驗收文件彙整成初稿，主控逐節查證後再跑 `--write`；查不到依據的標「（待確認）」。
