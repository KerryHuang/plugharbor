# 交棒協定（條件式自動接棒）

> 唯一定義處。各 skill 的「下一步」段落引用本檔，不各自定義接棒條件。

## 為什麼有這份協定

一條規格鏈有 6~7 個交棒點，每個都要人打一次指令、等一次啟動。
其中**只有少數幾棒真的需要人做決策**，其餘純粹是接力動作——
把純接力的往返消掉，保留真決策的往返，是本協定的全部目的。

**不是全自動。** 全自動會讓上游的錯誤累積到鏈末才爆，回頭修的成本高於當初停下來問。

## 兩類交棒點

### A. 硬性停點（**永不自動**，必須人確認後才續行）

| 交棒點 | 為什麼不能自動 |
|--------|--------------|
| `system-analysis` → `specify-backend` | SAD Step 8.5 是技術方案拍板點，方案選錯後面全白做 |
| `verifying-specs` → `linear-create` | 開票是**對外動作**（指派他人、產生 SLA），一律先確認 |
| `requirement` 的**分流判定**（Step 9.8） | 選 lite 就不寫 SAD，判錯要回頭補；讓人看過五條判準再走 |
| 任何 skill 出現「方案分歧」「體積超標放行」「PO 裁決」 | 這些本來就是問句，沒有預設答案 |

### B. 可自動接棒（滿足**全部**續行條件時直接續跑）

| 交棒點 | 說明 |
|--------|------|
| `requirement` → 下一棒 | 下一棒**依分流結果**：`chain_profile=standard` → `system-analysis`（SAD 中途的 8.5 確認門仍會停下）；`chain_profile=lite` → **直接 `specify-backend`**。⚠ 分流本身是 Step 9.8 的 `AskUserQuestion`，屬硬性停點，先確認再接棒 |
| `specify-backend` → `specify-frontend` | 後端契約定了，前端規格是承接，無新決策 |
| `specify-frontend` → `dev-readiness` | 檢核是驗證動作，不是決策 |
| `dev-readiness`（結論 ✅）→ `verifying-specs` | 兩者都是驗證，且 dev-readiness 已明訂 ✅ 即交棒 |

## 續行條件（**全部**滿足才自動接棒）

1. **零阻塞**：本棒無 ❌ / CRITICAL / BLOCKER 項。
2. **零待確認**：無 `TBD`、`[待確認]`、`[需釐清]`、未回答的開放議題（OI）殘留。
3. **零分歧**：無「兩個方案都可以，請選一個」性質的未決點。
4. **零放行請求**：無體積超標、無規範豁免需要使用者拍板。
5. **本棒產出已落檔**：文件已寫入磁碟，`analysis/` 共享產物已更新。

任一條不滿足 → **停下來，把不滿足的那一條說清楚**，依
`${CLAUDE_PLUGIN_ROOT}/references/shared-preludes.md`「互動詢問規範」逐題問完後再判斷一次。

## 自動接棒的執行方式

滿足條件時，**不要問「要不要繼續」**（那就是本協定要消掉的往返），改為：

1. 以一行明確宣告續行：
   > ✅ {本棒} 完成，零阻塞。**自動續跑 `{下一棒}`**（隨時可中斷；不想自動接棒請說一聲）。
2. 直接執行下一棒。
3. 續跑的棒**同樣適用本協定**——它跑完也照樣判斷，可以連續自動接棒到遇上硬性停點為止。

典型的一段連跑：`specify-backend` → `specify-frontend` → `dev-readiness` → `verifying-specs`，
中間三個往返全部消掉；到 `verifying-specs` 完成後停下，等人決定開票。

## 接棒在哪個 session 跑

同一個 session 連跑，context 會一路累積，每一輪都要重讀，長鏈的 token 用量會很可觀。

- 照本檔在同一個 session 自動接棒。建議在 user settings 設 `autoCompactWindow`
  （例如 `/autocompact 400k`），讓 context 到 400k 就自動壓縮，不要等到模型預設的上限。
  plugin 沒辦法替使用者設定這一項。
- 若使用者另有多 session／worker 編排工具，可每棒開新 session 跑；本檔的續行條件照樣適用，判定的人換成協調者。

## 使用者控制

- 使用者說「不要自動接棒」「一棒一棒來」→ 本 session 全程停用自動接棒，每棒結束都停。
- 使用者說「一路跑到底」→ 硬性停點**仍然停**（那是安全邊界，不因指示而放寬），
  待決事項在停點處接連逐題問完，不必每題各停一次。
- 中斷後重新叫任一 skill，協定照常適用。

## 落檔

自動接棒時，在 `analysis/_context.yml` 記一行 `handoff_log`（時間、從哪棒到哪棒、當時的判定結果），
讓事後可追「這條鏈哪幾棒是自動跑的、當時憑什麼判定零阻塞」。
