# 表單欄位版面判準

推導表單類畫面（新增／編輯／篩選）時，照一、二、三節對照；產出後用第七節清單自查。
每條都標外部出處，見文末〈外部出處〉。這些是通則，不是你這個專案的裁決：與專案既有慣例衝突時，在該條就地寫明取捨，不要靜默選邊。

## 零、順序：先認必填，再談排版

「必要欄位放前面」看似排版問題，前置作業其實是重新認定哪些欄位真的必填。先做第一節的檢查，再動版面，否則排版要重做。

## 一、必填

### 1a. 標「少數的那一邊」

必填與選填一定要有一邊被明確標記，不能只靠表頭那句「未標示者為必填」。NN/g 的結論是使用者不讀那句話，讀了也會忘。WCAG 3.3.2（Level A）把「必填欄位有清楚標示」列為硬性要求。

| 情形 | 做法 | 出處 |
|---|---|---|
| 必填是少數 | 標必填（星號放標籤前面，便於掃視） | NN/g |
| 選填是少數 | 標選填（標籤後綴「（選填）」） | GOV.UK Design System |

- 不可只靠顏色傳達必填（WCAG 3.3.2、1.4.1）。
- 格式限制（日期格式、長度上限）屬於「指示」，直接寫出來，不要讓使用者靠報錯才知道。

### 1b. 有預設值的欄位標必填，等於沒標

必填檢查通常是「非空」。預設值若是 `0`、`false` 或任何非空值，這條規則恆定通過，從未擋下任何一次送出，只會讓使用者以為自己填過。

逐欄問「這欄空著時會發生什麼」：

| 答案 | 結論 |
|---|---|
| 不會空，它有預設值 | 假必填，拿掉 |
| 由其他欄位計算帶入 | 衍生值，不列必填 |
| 真的會空，然後送不出 | 真必填 |

降為選填的連帶責任：使用者從此能清空該欄。下游若仍要求非空，必須在送出前補上預設值。放寬驗證與補正規化是同一批工作。

### 1c. 整批驗證的必填，會擋死使用者沒碰過的既有列

明細表的驗證多半對整個陣列跑。新增一條必填，等於「只要有一筆舊資料違規，整張表單就送不出，且錯誤指向使用者沒動過的那一列」。

做法：加必填前先確認既有資料有多少筆會違規。原型階段列進待確認清單：「新增這條必填，既有資料有空值怎麼辦？」替代做法是送出前補預設值，既有列照樣存得起來。

## 二、排列

### 2a. 依填寫的決策順序分區，不依資料表欄位家族

照資料表分類切的區塊，會讓使用者在區塊間來回跳。判準是「填到這一欄時，上一個決定是什麼」，不是「這欄在資料庫屬於哪一類」。區塊名稱要一眼看懂，避免「基本資訊」「其他設定」這種讀不出內容的抽象名詞。

### 2b. 連動欄位必須同框

只要 A 改變會自動改 B，A 與 B 就必須同時可見。跨捲軸的連動，從使用者角度就是資料被偷偷動過。

### 2c. 欄位親緣勝過區塊語意

一欄的值幾乎總是從另一欄推導或對照而來，兩者相鄰的收益大於歸類正確的收益。

### 2d. 同性質量值相鄰

數量、單價、金額這類同性質的量值，使用者會一起讀、一起改，連續排列。並排時標籤去掉重複的量詞。

### 2e. 一列多欄只留給概念相關的欄位

Baymard 的結帳流程測試結論：多欄版面更難填、更易錯，視線被往多個方向拉扯，使用者會漏填必填欄。唯一例外是概念相關的欄位並排（姓／名、郵遞區號／城市）。

內部作業系統是第二個例外：GOV.UK 預設一頁一題，但明文指出替需要快速反覆切換任務的內部人員設計時，相關問題群組在同一頁是合理的。因此規則不是「不准多欄」：

- 同一列的欄位必須概念相關，不為省高度把不相干的欄位塞一起。
- 一列塞幾個，看語意距離，不看畫面寬度還剩多少。
- 相關的欄位不要被換行拆開。

### 2f. 視覺分區不等於程式分區

區塊標題只是看起來有分組。螢幕閱讀器要靠 `fieldset` + `legend`（或等效 ARIA）才讀得出「這幾個欄位屬於同一組」（WCAG 1.3.1）。檢查法：把 CSS 關掉，欄位的從屬關係還看得出來嗎？原型用 `neutral-style.css` 的 `fieldset`／`legend` 即可。

### 2g. 分欄的斷點判準一致

區塊寬度若會被視窗以外的東西影響（側邊面板、抽屜），用容器查詢（`@container`），不要和視窗斷點（`@media`）混用，否則側邊面板展開時欄位縮了、分欄卻不縮。

## 三、預設值

### 3a. 什麼該預帶

| 條件 | 預帶？ |
|---|---|
| 系統已知答案（登入者、今天日期、來源單據） | 預帶 |
| 答案幾乎總是同一個，且各使用者群一致 | 預帶 |
| 使用者群之間分歧 | 不要硬給 |
| 下游已在補同一個值 | 不要再補一次 |

### 3b. 加預設值之前，先查誰已經在補

前端補、後端也補，結果不是補兩次，而是前端的補值會覆蓋使用者的明確操作（例如使用者刻意清空，被改寫回預設值）。往下追到值最後被寫入的那一行，看沿途有幾個人動過它。

### 3c. 使用者會照單全收預設值，即使它是錯的

使用者傾向不動已經有值的欄位（Zuko）。預設值填錯的成本，遠高於「使用者多按一次」。

| 情形 | 可否預設 |
|---|---|
| 有強證據該值對這個使用者是對的，且改起來明顯、低成本 | 可以 |
| 只是「大多數情況如此」，但改錯的後果是髒資料 | 先量分布再決定 |
| 同意條款、法律聲明、任何改變使用者聲明意圖的欄位 | 絕不預設 |

### 3d. 看不見的補值比預設值更危險

送出前才補的值，使用者從頭到尾沒看過，繞開了預設值唯一的安全網：使用者至少有機會看到並改掉它。能在畫面上預帶就預帶；送出前補值只留給使用者無從得知的系統值（流水號、建立時間戳）。

## 四、命名

- 布林欄不冠「是否」：開關控制項已表達型別。
- 量值欄不綴「數量」：兩欄並排時會擠掉欄寬。
- 與領域用語不符就改成領域用語；與既有系統語意不符，回查實際語意再定名。
- 空白欄名是缺陷：欄位設定選單裡出現沒有名字的欄（多半是純 icon 的操作欄），使用者無從得知那是什麼。
- 改名要全部語系同步，不能只改一種。

## 五、可見性與存廢

- 建檔欄位與執行結果欄位分開：問「這個值是誰寫進去的」。不是這張畫面寫的，新增時隱藏、編輯時唯讀。
- 待淘汰的欄位往後放，不直接砍。
- 只對特定情境有意義的欄位用條件顯示，不要對用不到的使用者露出永遠填不了的欄。

## 六、連動強度

- 自動帶值只在使用者沒動過該欄時套用；無條件連動會覆寫使用者剛親手改的值。
- 逐欄記錄「是否被使用者改過」；系統自己的寫入不記為「動過」，否則連動會被自己關掉；資料重載時整份清空。
- 連動強度變更是行為變更，不是重構：會翻掉既有測試的預期，要讓原作者知道，不要靜默合併。

## 七、自查清單

1. 先認必填，再談排版，逐欄問「空著會怎樣」。
2. 整批驗證的畫面，新增必填前先想既有資料違規怎麼辦。
3. 凡 A 改變會自動改 B，A 與 B 同區可見。
4. 非建檔欄位：新增隱藏、編輯唯讀。
5. 依決策順序分區，不照資料表欄位家族。
6. 下游已補預設值就不要在前端再補。
7. 必填／選填標了少數的那一邊，且不只靠顏色。
8. 同一列的欄位彼此概念相關。
9. 分區有 `fieldset`／`legend`，不只是視覺標題。
10. 預設值在畫面上看得見，不用送出前補值取代。
11. 版面草案與全欄位清單做差集，確認沒漏欄。
12. 需求文件沒寫的規則一律列進待確認，不自行發明。
