# 仿真資料

原型是拿給人確認「這樣對不對」的。資料太整齊，確認的人看不出版面撐不撐得住；資料像真的，又會把真實資訊帶進公開文件。兩者的解法：組合要寫實，識別值一律假。

## 一、使用者給了樣本，就用樣本

使用者貼的資料、截圖、現有畫面的範例列，優先於本檔的任何建議：

- 照樣本的欄位集、數量級、金額範圍、日期跨度、狀態分布組出資料。
- 樣本裡的真實識別值（人名、公司、單號、電話、email）換成假值，組合（誰多誰少、哪幾列有狀態）保留。
- 樣本與需求描述衝突時，不自己挑，列進待確認。

## 二、沒有樣本，組合要寫實

四個維度各自要有「不整齊」的部分：

| 維度 | 做法 | 避免 |
|---|---|---|
| 數量 | 混合 1、2、12、150 這類不同量級；偶有大單 | 全部都是 10、100 |
| 金額 | 幣別與小數位一致；有小額、中額、一兩筆離群大額；總計要能由明細加總出來 | 全是整千；明細加起來對不上總計 |
| 日期 | 跨數週到數月；有今天、昨天、上週；逾期的排在其中；同一張單的日期先後合理（下單日 ≤ 出貨日） | 全部同一天；未來日期出現在「已完成」 |
| 狀態 | 依真實分布：多數是常態、少數卡關。每個狀態至少出現一次，空狀態另設畫面 | 每種狀態平均各一列；全部「已完成」 |

筆數：列表 8～15 列夠看版面；要展示分頁才做 25 列以上並標明「示意」。單據明細 3～6 行。

長度也要不整齊：偶爾放一個很長的名稱、一欄空值、一個超過欄寬的數字，確認版面不會破。

## 三、識別值一律假

| 類型 | 規則 | 範例 |
|---|---|---|
| email | 網域只用 `example.test`（或 `example.com`） | `amy.lin@example.test` |
| 電話 | 明顯假的區段 | `0900-000-123`、`(02) 5550-0147` |
| 身分證／統編／稅號 | 明顯假的樣式，不可通過真實校驗碼 | `A000000000`、`00000000` |
| 人名／公司 | 通用假名，避開知名人物與真實公司 | `王小明`、`範例商行` |
| 單號 | 帶明顯測試前綴，序號不連號 | `ORD-TEST-0412`、`ORD-TEST-0419` |
| 地址 | 街名用「範例路」「測試街」 | `範例路 100 號` |
| 銀行帳號、信用卡 | 全 0 或 `4111` 類公開測試號，且遮罩 | `**** 0000` |

不要用真實專案的客戶名、料號、單號，即使「只是參考」也不行。

## 四、自查

- 有沒有任何一筆資料能被當成真實個資或真實客戶？
- 金額小計、總計加得起來嗎？
- 日期先後說得通嗎？
- 狀態分布看起來像真實營運，還是平均發牌？
- 最長、最短、空值各出現過一次嗎？
