# 精簡規格範本（`scale: lean`）

一份檔寫完需求、設計、驗收與決策，落 `<spec.dir>/<feature>.md`。章節不適用就寫「不適用」加一句理由，不刪章。
層名、整合面向依專案實際架構寫，不預設技術。

```markdown
# {功能名稱}

| 項目 | 內容 |
|------|------|
| 狀態 | 草稿／審查中／已批准／已實作／已部署 |
| 版本 | 1.0.0 |
| 票號 | {票號或「無」} |
| 最後更新 | {YYYY-MM-DD} |

## 1. 概述
- **背景**：{業務背景與動機}
- **目標**：{要達成的結果}
- **範圍**：包含 {…}；不包含 {…}

## 2. 需求
### 2.1 使用者故事
| # | 角色 | 想做什麼 | 為什麼 |
|---|------|---------|-------|
| US-01 | {角色} | {操作} | {價值} |

### 2.2 業務規則
- BR-01：{規則}（依據：{來源}）
- BR-02：{推導出的規則} `[推論]`（依據：{推導理由}）

### 2.3 驗收標準
每條關鍵規則至少一個正例與一個反例，直接代入數字。
- [ ] AC-01（US-01／BR-01）：給定 {情境}，當 {動作}，則 {結果}
- [ ] AC-02（反例）：給定 {情境}，當 {動作}，則 {拒絕或錯誤訊息}

### 2.4 非功能約束
{效能、資料量、權限、稽核等約束與目標值；不寫實作手段}

## 3. 設計
### 3.1 影響範圍
{受影響的模組、畫面、端點、資料表；既有可重用的元件（附路徑）}
### 3.2 資料
{新增或變更的資料結構、遷移需求}
### 3.3 介面
{API／畫面／事件的輸入輸出與錯誤情境}
### 3.4 邊界與例外
{空值、極值、狀態轉換、並發、權限不足時的系統行為}

## 4. 實作與測試計畫
- 檔案清單：{預計新增／修改的檔}
- 測試：{單元／整合／端到端各驗什麼，對到哪幾條 AC}

## 5. 決策
| # | 決策 | 選定 | 否決的選項與原因 | 拍板 |
|---|------|------|----------------|------|
| D-01 | {題目} | {做法} | {不得留空} | PO／SA／證據 |

## 6. 風險與待澄清
- 風險：{描述、影響、緩解}
- 待澄清：正文中所有 `[NEEDS CLARIFICATION: …]` 在此列一行，清零前規格不得標「已批准」

## 7. 變更歷史
| 版本 | 日期 | 變更內容 |
|------|------|---------|
| 1.0.0 | {日期} | 初始版本 |
```

## 品質檢查（寫完自查）

- [ ] 範圍有寫「不包含」
- [ ] §3.4 涵蓋空值、極值、狀態、並發、權限五個面向（不適用要寫理由）
- [ ] 每條 US 都有對應 AC，關鍵 BR 有正例與反例
- [ ] 推導出的規則標了 `[推論]` 與依據
- [ ] 決策表「否決的選項與原因」沒有空格
- [ ] `[NEEDS CLARIFICATION` 已清零，或狀態維持草稿並在 §6 列出
- [ ] 沒有寫死框架、快取、鎖等手段（屬實作決定）
