# 規劃指引（給規劃 subagent）

產 `tasks.md` 時照本檔。層名與順序依專案實際架構調整；專案沒有分層就照它既有的模組切法。**照既有慣例寫，不單方面引入新風格**（有裝 workspace 可參考 `workspace:convention-first`，可選；沒裝就先 grep 既有同類實作當樣板）。

## 規劃前要做的分析

1. 找受影響的層級或模組。常見分層（以分層架構為例）：

   | 層 | 內容 |
   |---|---|
   | 核心／領域 | 實體、值物件、領域服務介面、存取介面 |
   | 應用 | 用例（命令／查詢）、DTO、映射、驗證 |
   | 基礎設施 | 存取實作、schema／migration、外部整合、背景排程 |
   | 對外介面 | route handler／controller、畫面、背景工作入口 |

2. 搜既有程式找類似實作與可重用元件，task 的「讀」欄列出當樣板的檔。
3. 標出整合點、風險與邊緣案例（null、邊界值、狀態轉換、錯誤處理、權限）。
4. 只挑本功能真正涉及的整合面向：外部 API（認證、重試、逾時、回應驗證）、背景排程（取消、重試、日誌）、資料存取（索引、避免 N+1）。

## task 順序

| 模式 | 順序 |
|---|---|
| 標準 | 核心 → 資料存取 → 應用 → 對外介面 → 測試補強 |
| TDD | 核心 → 資料存取 → 測試（Red）→ 應用（Green）→ 重構 → 對外介面 |

每層的注意事項：

- **核心**：避免貧血模型；依業務概念命名，不用底層資料表或欄位代碼命名。
- **資料存取**：schema 變更同步對應的 schema 來源（migration 與手寫 SQL／view 不能各說各話）。
- **應用**：按使用者故事順序實作命令與查詢，含輸入驗證與映射。
- **對外介面**：輸入模型的必填、長度、格式限制要跟資料層組態與驗證器一致，讓 API schema 直接反映限制。
- **測試**：單元測試必寫；涉及資料存取組態、原生 SQL、特殊型別或定序、軟刪除、分頁、查詢轉譯時，整合測試也必跑。整合測試因環境不可用可標 skip 並註明，邏輯錯一定要修。

## 品質檢查項（放進最後一個 task 或步驟 8）

| 檢查 | 判定 |
|---|---|
| 分層違規（上層直接引用下層實作） | 阻止 |
| 字串串接 SQL／命令（注入風險） | 阻止 |
| 阻塞式 async 呼叫 | 警告，列入審查 |
| 端點缺授權標記 | 警告，列入審查 |
| 對外介面缺型別／schema 標記 | 警告，列入審查 |

## 拆 task 的判準

- 每個 task 要能在一個 subagent context 內做完（見 dispatch.md「context 預算」）。
- 每個 task 有可執行的驗收指令；寫不出驗收指令表示 task 切得太虛。
- 影響同一檔的 task 不標 `[P]`。
- 讀 ledger「已定決策與注意」（含 LEARNINGS 抄來的條目），避開上次踩過的坑。
