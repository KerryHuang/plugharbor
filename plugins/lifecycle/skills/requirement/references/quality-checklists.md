# 需求文件品質檢查清單

## 標準模式

- [ ] 業務背景清楚說明「為什麼」需要這個功能
- [ ] 使用者故事涵蓋所有主要角色，§2.1 每條 US 都填了角色欄
- [ ] 驗收條件使用 Given-When-Then 格式
- [ ] 欄位規格包含資料型態和長度
- [ ] 業務規則無遺漏且可測試
- [ ] 測試案例涵蓋正常和例外情境
- [ ] 無任何未解決的疑問（已全部在寫前釐清）
- [ ] 不包含實作細節（不指定程式語言、框架、API 路徑）
- [ ] §2.2 只展開 Must；Should／Could 停在 §2.1 清單
- [ ] §4 每個畫面都有區塊清單與 footer（版面由前端決定那句）
- [ ] §4 **未**列完整四類欄位群（完整欄位表的 owner 是 FFS §2；在 FRD 重寫一次屬重抄）
- [ ] §4 業務層欄位表只列「業務上需要交代」者（必填有理由／有算法／有權限差異／有非顯然預設值）
- [ ] §4 每個畫面都有操作表（操作／觸發條件／執行後行為／權限）與預設排序（業務語意）
- [ ] §4 無省略號（「等」「欄位1、欄位2…」「依實際需要增減」）
- [ ] §4 有列出的欄位都有**業務層**來源（`手動輸入`／`固定清單：{值列舉}`／`參照{主檔}`／`{本單據自身欄位}`／`系統計算：{公式}`）
- [ ] §4 來源欄**未**出現 API 路徑或 Response 欄位名——那是 FFS §2 的前端契約層才填的（見 `references/screen-spec-format.md` §來源欄的兩階段寫法）
- [ ] §3 業務流程有 Mermaid flowchart（涉及多步驟流程或狀態變化時必填）

## 調整模式

- [ ] 參照文件路徑正確且可找到
- [ ] 變更原因清楚說明「為什麼調整」
- [ ] 變更範圍的影響矩陣涵蓋所有原始功能項目
- [ ] 每個 CUS-XX 故事都標記類型（新增/修改/停用）
- [ ] 修改的故事有對應原始 US-XX 編號
- [ ] 驗收標準包含「向後相容性」測試案例
- [ ] 風險評估包含 Breaking Change 識別
- [ ] 無任何未解決的疑問（已全部在寫前釐清）
