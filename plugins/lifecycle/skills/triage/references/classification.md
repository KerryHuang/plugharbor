# 有效性與分類準則

## 1. 有效性結論（先判，再分型）

| 類別 | 判準 | 必附證據 |
|------|------|---------|
| 有效 | 描述的行為或需求成立，且不屬下列任一類 | 勘察結果 |
| 已實作 | 勘察顯示現況已有此能力；常因版本差異、功能開關未開、入口沒找到而被說「缺少」 | 實作位置（`檔案:行號`）、開關或版本條件 |
| 重複 | 已有票或規格涵蓋同一主題 | 票號、規格路徑 |
| 非需求 | 只在說明行為或定義，沒有要改變什麼 | 原文引述 |
| 資訊不足 | 缺重現步驟、環境或前提，無法判斷 | 缺的項目清單 |

「已實作」與「重複」都不歸 Feature：標「先實機確認、勿逕自開發」，或以變更需求併入既有票。

## 2. 分型（僅對「有效」）

| 型 | 定義 | 判準 |
|----|------|------|
| **Bug** | 既有功能跑出錯誤結果 | 本該動卻不動；勘察為已實作但壞掉 |
| **CR／Enhancement** | 調整或擴充既有功能 | 想要不同行為而非錯誤結果：改欄位、預設值、版面、查詢條件、既有行為 |
| **Feature** | 全新能力 | 勘察為未實作，且無既有規格 |

CR 與 Bug 易混：用 Bug 格式（重現步驟、預期、實際）書寫不代表是 Bug。本質是「想要不同行為」就是 CR。勘察中發現證據與初判矛盾（如「Bug」實為設計如此），隨時改判，以證據為準。

單票模式的判型訊號（衝突時以描述語意為準）：

| 訊號 | 偏向 Feature／CR | 偏向 Bug |
|------|-----------------|---------|
| 標題關鍵字 | 新增、需求、希望、調整為、支援 | 錯誤、無法、壞了、異常、重複、漏、不一致、報錯 |
| 描述結構 | 使用者故事、目標、範圍 | 重現步驟、預期對實際 |
| 既有 label | 需求、規格類 | 測試、Bug 類 |

票掛在父票下且描述是測試情境清單，通常是測試子票而非 Bug 根票，不由本 skill 分流，建議改用 `lifecycle:ticket-reply`。

## 3. 防呆（開票前必過）

1. **「客戶說缺少」不等於真的沒有**：勘察顯示已實作就不歸 Feature，放進「已實作防呆」區。
2. **既有票與規格對照**：標「需新建」前查規格目錄與票務系統（`lifecycle:ticket-ops` 的 `query`），多數主題已有票或文件。
3. **變體與術語先確認**：客戶或場域變體、版本命名對照先定，分類才不會建立在錯前提上。
4. **純現況描述非需求**：標註即可，不當需求開票。
5. **證據與信心度**：每項附勘察證據與信心度（Confirmed／Likely／待實機）。
6. **同症狀合併**：多處同症狀（如多個畫面都看不到圖片）疑同一根因，標「合併調查」。
