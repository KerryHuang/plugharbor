# 獵邊界分組派工樣板

`dev-readiness` Task 2~4 的派工。**一組操作一個 agent**，用 `general-purpose`。

> 為什麼不新建專用 agent：獵邊界的差異全在「哪些操作、哪些維度」，行為完全相同
> （讀規格 → 對每個操作套維度生問題 → 查 DB 接地 → 回頭查規格是否已答）。
> **差異是輸入不是行為**。

## 分組（**現場分析，不要照抄**）

<law>
**分組方式必須依本次操作清單的實際性質決定**，不得套用固定分組表。
</law>

分析步驟：

1. 列出每個操作的**前置條件**：涉及哪些資料表、要讀 BFS/FFS 的哪幾章
2. **前置相同者歸一組**——同組共用同一批規格章節與 DB 表，agent 只需載入一次
3. **B13 單獨一組**：它不逐操作問，而是**對全部規格文件掃一次「值」**，性質與其他維度不同

**組太細會變慢**：每組固定成本是「定向讀規格章節 ＋ 查該組涉及的表」。
3~6 個操作是常見的合理區間；操作數 ≤4 時不必分組，一個 agent 跑完即可。

> 僅供理解判準，**不要照抄**：某次把「主檔 CRUD 4 個操作」歸一組（共用 BFS §6.1~6.4、
> 同一張主表）、「明細連動 3 個操作」歸另一組（共用 §6.5 與主從兩張表），
> 因為兩組要讀的章節與表完全不重疊。換一份規格這個分法就不成立。

## 派工 prompt

```
subagent_type: "general-purpose"
model: sonnet
prompt: |
  你是開發就緒度的邊界獵手。目標是**逼出規格沒寫的隱含決策**，不是複述已寫的內容。

  功能目錄：{絕對路徑}
  本組操作：{操作清單，每項含操作名、涉及資料表、對應 API 端點、對應畫面}
  適用維度：{本組要套的維度編號，見下}

  <步驟>
  1. 對每個操作 × 每個適用維度，生成「開發者一定會問」的問題
  2. DB 接地：先讀 {功能目錄}/analysis/db-analysis.yml（命中即用，**不重查**）；
     該檔沒有的表／欄位才用唯讀 DB 查詢工具補查（如專案有提供；無則標「待實查」），
     並把結果**寫回同一份 yml**。
     據此**剔除不成立的假問題**、**補上 DB 揭露的真邊界**（如某 FK 實際可為 NULL → 必問空值處理）
  3. 覆蓋判定：每條問題去 BFS §7（VR/BR）、FFS §4（欄位驗證）、SAD §6.6（邊界清單）查是否已答
  4. {parity 鏈才帶這步，chain_origin: foxpro}：未答的問題先查 FoxPro 分析報告 {報告路徑}——
     FoxPro 有此行為 → 回報「對齊 FX-xx」並附 FoxPro 行為當建議答案；FoxPro 是 bug → 標 P-FIX；
     FoxPro 沒有、也非平台必要 → 標「不處理(parity)」，不算阻塞、不提新規則
  </步驟>

  <分桶——判定前必做>
  **業務／契約桶**（行為、回應碼與訊息、擋下或降級、資料語意、
    資料模型契約：表／欄位名／型態／長度／可空／回填）→ 未答即阻塞
  **技術手段桶**（鎖種類、快取、佇列、儲存位置、重試與補償做法、索引、
    Migration 做法）→ **不問手段、不逼選型**。只查 decisions.md 是否有對應 TD
    且「約束／現況／陷阱」三樣齊備：齊備＝✅ 不阻塞；缺任一＝❌，**補的是三樣不是選型**
  </分桶>

  <讀取紀律>
  規格一律定向讀取（grep -n 'SPEC-INDEX v1' → grep -n "^## " → Read 帶 offset/limit）。
  只讀本組操作相關的章節。
  </讀取紀律>

  <回報格式>
  只回三樣：
  1. 覆蓋矩陣（操作 × 維度 → ✅已答／⚠️模糊／❌未答）
  2. 阻塞項清單，每條：問題、開發者會卡在哪、**建議答案（必附）**、應回寫的文件＋章節
  3. 本組補查並寫回 db-analysis.yml 的表／欄位（若有）

  **禁止**貼規格原文、DB 查詢完整結果進回報。
  **禁止**生成無關痛癢的假問題稀釋阻塞訊號——每條問題必須有 DB 或業務領域的接地。
  </回報格式>
```

## 維度分派

維度定義見 `${CLAUDE_PLUGIN_ROOT}/references/boundary-dimensions.md`（與 SA 盤點共用同一組編號）。

| 鏈 | 逐操作套用 | 全文掃一次 | 標不適用 |
|---|---|---|---|
| **standard** | B1~B12＋M1~M4 | **B13** | — |
| **lite** | B1／B2／B3／B9／B11 | **B13** | M1~M4 |

<law>
**lite 鏈仍要看 B4／B5／B6／B10 一眼**——lite 的前提就是這四項沒有內容。
**一旦抓到實質內容，代表分流判定錯了**：停下告知使用者，補做 `system-analysis` 後回 standard
（見 `${CLAUDE_PLUGIN_ROOT}/references/chain-profile.md`「中途升級」）。
這一條寫進派工 prompt，讓 agent 也知道要回報。
</law>

## 匯流

各組回報齊了才進 Task 5。主 session 要做的：

1. **合併覆蓋矩陣**，確認沒有操作落在任何一組之外
2. **複核量化斷言**——阻塞項筆數、覆蓋率抽驗（見 `${CLAUDE_PLUGIN_ROOT}/references/dispatch-conventions.md` §四）
3. **判斷阻塞項是否真的阻塞**——agent 可能把技術手段誤判成業務契約
4. 若某組一次獵出**大量**未落實項 → 那是 BFS/FFS 撰寫時 ② 沒做，**在報告中明說**，
   讓下次的撰寫階段補上對照，而不是默默當成本階段的功勞
