# 指標定義與禁用指標

## 清單即真相

每個統計數字都必須是某張清單的 `len()`。建 drill dataset 時同時記下 key，
組報表時**用 `len(items)` 插值，不要另外算一次**。

發布前用 `scripts/verify_counts.py` 強制檢查，非零 exit code 即不得發布。

## 必備清單

| key | 定義 | 陷阱 |
|-----|------|------|
| `delivered` | 完成時間落在上週窗內，**扣除批次結案** | 這才是產能；`query` 沒回 `completedAt` 就標「未提供」，不用 `updatedAt` 近似 |
| `cleanup` | 上週窗內的批次結案（見下） | 與產能分開，不然虛胖；缺完成時間則標「未偵測」 |
| `created` | 建立時間落在上週窗內 | 分頁要拉完；缺 `createdAt` 標「未提供」 |
| `review` / `progress` | 該階段全量計數（非窗內） | 存量與流量不同口徑，要標明 |
| `blocked` | 帶 `blocked` label 的未完成票 | 停滯天數是重點，不是張數；沒有此 label 約定標「未提供」 |
| `req` | `backlog` 與 `todo` | 含大量陳年掛單，要講明 |
| `overdue` / `dueweek` | 有期限、**且未完成** | 含已完成會虛報；缺 `dueDate` 整組標「未提供」 |
| `lead_*` | 流動時間分桶，**只算 `delivered`** | 含 cleanup 會製造假長尾；需要建立與完成時間 |
| `wip_*` / `del_*` | 依歸戶 label 的在手／交付 | 同一刻度畫圖才誠實 |
| `case_*` | 各案子的所有在跑工作 | 案子用 label 或功能碼比對 |

## 批次結案的偵測

判準與閾值寫在 SKILL.md「共同規則」。兩個容易踩的坑：

> **間隔不能用 1 分鐘**——一次清理常橫跨數分鐘，60 秒會把它切成兩段，其中一段不足 5 張而漏判，
> 陳年票因此被算成當週產能。放寬到 180 秒解決。
>
> **不能只用「lead time > 30 天」**——會漏掉簇內剛開的票（開了十天、隨簇結案，但它確實是清理）。
> 所以用**簇的票齡中位數**而非逐票判定。

## 衍生指標

| 指標 | 算法 | 呈現 |
|------|------|------|
| 淨變化 | `len(created) − len(delivered) − len(cleanup)` | 正值＝積壓惡化 |
| 產能 vs 需求 | 依歸戶 label 分群，交付 vs 在手 | **左右同一刻度**，比值愈大愈危險 |
| 開發段耗時 | `完成時間 − 建立時間`，只算 `delivered` | 中位數＋分桶 |
| 驗收段停滯 | `now − updatedAt`，算 `review` | 中位數＋「停超過兩個月」張數 |

開發段與驗收段**要放在一起對照**——這對照本身就是結論（常見型態：交付中位數幾天，驗收段停滯中位數幾十天）。

## 禁用指標

| 指標 | 為什麼不用 |
|------|-----------|
| **Cycle／Sprint 完成率** | Cycle 常被當成全票容器而非承諾，完成率長期個位數百分比，無資訊量 |
| **工時／故事點** | `estimate` 不在 ticket-ops 契約內，覆蓋率也通常偏低且格式不一致。畫出來很專業但數字是編的，被追問一句就垮 |
| **人員票數排名** | 票數 ≠ 工作量，且會議上點名會變成防禦性辯論、吃掉決策時間。改報「哪一棒缺人」 |

工時覆蓋率低這件事**本身**要進「臨時動議」——是待決事項，不是可跳過的缺陷。
