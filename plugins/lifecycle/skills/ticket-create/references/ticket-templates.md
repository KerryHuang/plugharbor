# 票描述範本與通則

票是給人翻的，不是讀的。所有範本由 `lifecycle:ticket-create` 取用；標題、描述一律技術中立，只描述行為與契約。

## 通則

1. 描述第一個標題用 `##`，不重複標題。
2. 只放票生命週期內穩定的內容：交付範圍、對齊的需求編號、驗收條件。既有檔案路徑、套件選型、實作做法不進票（開票到開工常隔一至兩週，過期內容是辨識成本）。
3. 規格明細不抄進票，用「檔案路徑 §章節」指路，粒度到子節。
4. 驗收條件（AC）至多 5 條，每條是可觀察的結果，對齊需求編號（若規格有）。機械性項目（逐欄驗證、CRUD 基本操作）由規格保證，不展開成 AC。
5. QA 票只寫 E2E 情境，不寫單元測試維度。
6. Bug 票必填「根因分析／程式碼問題定位／修改細節」；根因未知時寫「最可能位置＋排查方向」，不杜撰行號或機制。
7. 有規格檔就附「參考文件」表；沒有就整段省略。
8. 最後一行放票源 flag（見 `create-dispatch.md`）。

## 標題格式

`lean` 單票與 `full` 父票：`{標題}`（Bug 加前綴 `【Bug】`）。`full` 子票：`【需求】`、`【規格】`、`【測試】`、`【實作】`＋同一標題。專案已有標題慣例（盤點時看同主題既有票）以慣例為準。

## lean 單票：Feature

```markdown
## 參考文件

| 文件 | 路徑 |
|------|------|
| 規格 | `{規格路徑}` |

## 目標

{為什麼要做、不做的影響——至多 3 句}

**包含**：{範圍}
**不包含**：{排除項目}

## 規格指路

{行為與契約的明細在：`{規格路徑} §章節`}

## 驗收條件（≤5）

- [ ] {可觀察結果}
```

## lean 單票：Bug

```markdown
## 問題描述

{一句話現象}

## 重現步驟

1. {步驟}

## 預期行為／實際行為

- 預期：{…}
- 實際：{…}

## 根因分析

{機制，不是現象複述}

## 程式碼問題定位

`{檔案相對路徑}:{行號}`，{函式或方法}：{此處為何造成問題}

## 修改細節

{建議方向，僅建議}

## 影響範圍

{受影響的功能、資料、使用者}

## 驗收條件

- [ ] {修好後可觀察的結果}
- [ ] {既有相鄰行為不變}
```

## full：父票

父票只做總覽與 rollup，不放實作內容。

```markdown
## 目標

{同 lean Feature 的目標，至多 3 句}

## 子票

- PM：需求　SA：規格　QA：測試　Dev：實作
（建立後由建票回報補上票號）

## 驗收條件（≤5）

- [ ] {整體可觀察結果}
```

## full：子票

沿用 lean 的段落，依角色只留該角色的部分。

| 子票 | 描述要點 |
|------|---------|
| PM（需求） | 目標、包含／不包含、使用者故事（至多 5 條）、驗收條件。涉及新畫面時附原型連結（若專案有）。 |
| SA（規格） | 規格制定範圍（工作流、資訊流、資料流各一句重點）、產出物（規格檔路徑與完成勾選）、Done 條件（規格通過 `lifecycle:spec-check`）。 |
| QA（測試） | 測試範圍＋**一張 E2E 情境表**：每列從使用者操作走到結果，預期結果欄一併寫資料落地與回歸點；5 到 8 列為度；測試後 □ 改 ☑（通過）或 ☒（未通過）。 |
| Dev（實作） | 功能目的、對接介面（端點或契約總覽）、涉及資料、「規格明細」指路節、驗收條件（至多 5 條）。Dev 範圍大時可拆多張 Dev 票（例如前後端），後者以 `blocked_by` 掛前者。 |

Bug 的 `full`：父票用 Bug 範本的「問題描述／預期／實際／影響範圍」；QA 子票寫重現步驟與驗收（驗收人為開票人）；Dev 子票寫根因、定位、修改細節與驗收條件。

## 估點、期限、優先級、指派

`ticket-ops` 契約不含這些欄位。使用者要求時，優先級與期限寫在描述最上方一行文字，指派與估點列入回報的「需手動設定」清單，不自行猜工具欄位。
