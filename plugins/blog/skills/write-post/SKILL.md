# 寫文章

站台名稱、文章目錄、frontmatter 欄位、分類、作者標示、紅線（隱私、數字出處等）都**屬於各專案**：
先讀專案的 `.claude/rules/posts.md`（或 `AGENTS.md`）；兩者都沒有就問使用者，不套用別的站台的規則。

## 1. 定題

和使用者確認三件事，**一次問一題**：題目、分類、誰寫初稿。
素材優先順序：使用者在對話裡說的話 → Google Drive `blog-inbox/` 的素材包（其他 session 用 `blog-capture` 收的）→ 使用者的 session 紀錄與 repo → 官方資料。

## 2. 蒐集素材

- **技術／專案文：** 有素材包就先讀（`blog-inbox/<日期>-<slug>.md`），再從 repo 的 commit 紀錄、設計文件、使用者的 session 原話補細節。素材包標了「已去識別化」的，寫稿時不得把拿掉的資訊加回來。
- **研究／數據文：** 抓官方原始資料存進專案規定的資料目錄，用程式計算，再回官網抽查前幾筆。對不上的數字不用。

## 3. 寫白話初稿

照專案規則在文章目錄新增檔案，frontmatter 先標草稿（欄位與寫法依專案規則）。
結構預設：真實場景開場 → 第二段內講出結論 → 分段展開（每段一個重點）→ 收穫 → 名詞解釋；專案規則有規定就以它為準。
寫完自己掃一遍：

- 每個專有名詞都有白話解釋
- 沒有無出處的數字或說法
- 沒有個資、內部資訊
- 使用者的經歷、想法、引言只能來自使用者本人說過的話，缺了就留 `<!-- 待使用者補：... -->` 並回報，不替使用者編

## 4. 檢查

- 跑專案規則指定的型別檢查與 build；沒指定就看 `package.json` 或 README 的建置指令，仍不確定就問。
- **沒脈絡的讀者驗稿：** 開一個全新的 subagent（不帶任何對話脈絡），只給它草稿全文，請它回答三題：這篇在講什麼、讀者讀完能做什麼、哪幾句看不懂或像是缺了前提。看不懂的地方改掉再交稿。
- 開 dev server 看文章頁，表格和連結都要正常。

## 5. 交稿與發布

- 給使用者草稿網址和三五行重點，問「直接發布」還是「再改」。
- 草稿階段的 commit 訊息格式依專案慣例。
- 使用者明說發布才把草稿標記拿掉；發布前交給 `publish-check` 做上線前檢查，push 與部署方式依專案規則。
- 上線後，素材包搬到 `blog-inbox/done/`；文章介紹的是某個 repo 時，提議在該 repo 的 README 加連回文章的一行（有其他 session 正在改該 repo 就請那個 session 加）。
