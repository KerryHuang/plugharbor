# 操作手冊撰寫規範

> 由 `operation-manual` 與 `manual-writer`、`manual-reviewer` 引用。專案有自己的撰寫範本（慣例放 `{docs-root}/操作手冊/_範本/`）時以專案為準；沒有就用本檔。
> 本檔的例子用虛構產品「Greenleaf 訂貨管家」的「採購單作業」，只示範寫法。

## 這份手冊要做出什麼

**讀者是完全沒碰過這個系統的新人。** 從頭讀一遍就能開始操作，不需要旁邊有人教。

| 原則 | 意思 |
|------|------|
| 白話 | 不預設讀者懂任何術語。看不懂的字，等於這頁沒寫 |
| 不跳步 | 每一步都寫，包括「按下去之後會看到什麼」。老手覺得理所當然的，正是新人卡住的地方 |
| 圖文並行 | 每個操作配一張圖。文字講「做什麼」，圖講「在哪裡」 |
| 只寫他看得到的 | 客戶只會用到一種模式，手冊不比較版本（見下節） |

這是教學手冊，不是查閱手冊：查閱手冊可以只列欄位表，教學手冊必須完整走一遍流程。

## 模式純度：一種模式一本

同一支功能有多種模式時（例如採購單分標準版、簡易版），客戶只會看到其中一種：

| 不要 | 要 |
|------|----|
| 一本手冊寫兩種模式，用「標準版看這段、簡易版看那段」分流 | 一種模式一本，只寫這個客戶用得到的 |
| 開頭放模式比較表，要讀者自己判斷是哪一版 | 手冊裡完全不出現另一種模式 |
| 寫「標準版沒有簽核（簡易版才有）」 | 寫「採購單不需要簽核」 |

模式的區分是內部的事，用檔名與目錄（`採購單作業-標準版/`）區分；文件標題與內文只寫功能名稱。
`manual-reviewer` 第 6 項會 grep 模式名稱：出現在封面或標題可以，出現在內文比較句不行。

## 白話怎麼寫

**不用系統內部的詞。** 新人只看得到畫面上的字：

```
不好：沒有 amount_visible 權限時金額欄會被遮罩
好　：帳號沒有開放看金額時，畫面上所有金額欄都顯示「—」
      （不是 0，是一條橫線，代表「不給你看」，不代表這張單沒有金額）
```

**用具體動作，不用抽象名詞。**

```
不好：完成表頭維護後始得進行明細編輯
好　：先把上半部的供應商、日期填好，按［送出新增］。存檔後畫面中間才會出現「明細項目」，這時才能填品項
```

**術語第一次出現就解釋。** 躲不掉的詞（表頭、明細、簽核），第一次用括號講白，之後才直接用。

**每個關鍵動作都寫結果。**

```
不好：按［送出新增］
好　：按［送出新增］。畫面跳回清單，你剛建的採購單出現在最上面，並且這時才有單號（例如 PO260001）。
      按之前單號欄是空的，這是正常的
```

**先講為什麼，再講怎麼做。** 一句話講一件事；中文一句超過三十字就考慮斷開。

## 不跳步

寫的時候把自己當成第一次坐在電腦前的人，每個操作回答三個問題：

1. 我現在在哪？（畫面是什麼、從哪進來的）
2. 我要點哪裡？（按鈕在畫面哪個位置，配圖）
3. 點完之後呢？（畫面怎麼變、怎麼確認成功）

最容易漏的是第三點。

## 圖文怎麼配

文字講「做什麼」，圖講「在哪裡」，兩者不重複。圖不能取代文字：畫面改版後圖會過期，文字還在，也只有文字能被搜尋與比對。

### 圖文比有標準

**目標 200～400 字／圖，400～600 提醒，超過 600 不過**（參考標竿約 170 字／圖）。超標就是文字太多：補圖或砍字。

**算法固定，一律跑腳本，不要自己數：**

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/text-image-ratio.py" <手冊.md>
```

分子是正文字數（剝掉圖片語法、程式碼區塊、HTML 註解，計 CJK 與英數字元，不計標點與空白），分母是行首 `![` 的次數。
不要用「整份檔案長度 ÷ 圖數」：分子含圖片語法本身，每補一張圖分子就變大，指標反而在懲罰補圖。

### 一個操作一張圖

不要一張圖配五個步驟。節奏大約是每頁 60～300 字配 1～4 張圖。

### 圖要標註

| | 用途 |
|---|---|
| clean（原始截圖） | 探索留存的素材，不放進手冊 |
| annotated（標註過） | 紅框框出該步驟講的位置，紅底白字標籤寫重點 |

手冊開頭放一句導讀告訴讀者怎麼看圖。一張圖最多三個框；標籤是重點提醒，不是欄位名（寫「公司別自動帶入」，不寫「公司別」）。手冊圖不用 legend（圖例帶會把圖加高，整批尺寸不一）。

### 圖說與 caption 對帳

圖說格式：`![aNN 圖說](images/aNN-英文語意名.png)`，寫「這張圖要看什麼」，不複述標題。圖說裡的方括號一律用全形［］，半形 `[` `]` 會讓 markdown 圖片語法提早結束；檔名只用英文語意名，不含方括號。

**caption 是在標註動手之前寫的**，句型多半是「紅框處為 X、Y、Z」。標註時常有正當理由少框一個（元素當下是 disabled、與遮罩相交），而 caption 不會自己跟著改。所以：

- 圖放進手冊前，**開圖看紅框裡實際是什麼**，再回頭對 caption；對不上就改 caption 或補框。
- 不要拿 caption 去比對「標註清單」：兩份都是文字，雙方同時說錯會互相印證成一致。清單只用來定位該看哪幾張。
- caption 寫得越精確，與實際標註耦合越緊，越需要這一步。

## 用語與標記

| 對象 | 寫法 | 範例 |
|------|------|------|
| 畫面上的 UI 元素 | 全形方括號 | 點［新增］、填［供應商］、切到［採購單檢視］ |
| 步驟標題 | `### 步驟N. 動作名稱` | `### 步驟3. 確認自動帶入的欄位` |
| 系統顯示的值 | 全形引號 | 狀態會變成「已送簽」 |
| 要小心的地方 | 整句粗體 | **選完檔案還沒完成，要按送出才算數** |
| 嚴重誤解 | ⚠ 開頭的引言區塊 | `> **⚠ 品項檢視的一列是「一筆明細」，不是「一張採購單」。**` |

## 補充說明寫在哪

同一條規則有兩個落點，兩邊都要有，寫法不同：

| 位置 | 形式 | 寫什麼 |
|------|------|--------|
| 步驟正下方 | `> **說明：** ...` | 一句白話，這一步的補充或例外 |
| 附錄 B「為什麼會這樣」 | 表格，一列一個現象 | 使用者會覺得奇怪的現象與原因 |

新人卡住時不會翻附錄，所以就地要有；教育訓練與客服要整表講，所以附錄也要有。

## 共用內容只寫一次

查詢列、分頁、排序、匯出、附件上傳這類每支功能都長一樣的東西，抽到共用手冊寫一次，各功能手冊用交叉引用指過去。第三支功能開始才會痛，但架構要在第一支就定。

## 不放內部資訊

手冊是交給客戶的東西，靠「交付前記得移除」不可靠，一開始就不要放。

| 不放 | 可以放 |
|---|---|
| 規格文件路徑與檔名 | 程式代碼（如 `ORD100`）：客戶報修時報這組號碼最快 |
| 票號 | 畫面上看得到的欄位名稱 |
| 資料表與欄位代碼 | 系統顯示的訊息原文 |
| 內部流程編號、盤點編號 | |
| 「待補」「尚未實測」這類文件進度 | |

待補事項不寫進手冊，手冊以當前版本為準。真正的內部待辦要開票，留在文件裡會過期。

## 截圖不得含客戶資料與個資

沒有例外。手冊走功能軸不是客戶軸，同一本會給所有客戶看，截圖上留著 A 客戶的名單，等於交到別家手上。

用位置檢查，不要用資料類型檢查：想著「遮個資」只會遮人名，逐個位置掃才不會漏。

| 位置 | 會洩漏什麼 |
|---|---|
| 登入的公司（租戶） | 客戶身分 |
| 左右側清單欄 | 整欄人名，常在每張圖都出現 |
| 卡片或列的 header | 操作人員姓名 |
| 表單欄位 | 姓名、電話、住址、Email、身分證號、緊急聯絡人 |
| 對話框內表格 | 整份名單，可能上百筆 |
| 列印／PDF 預覽 | 報表內容本身就是資料 |
| 下拉選項 | 客戶名、廠商名、部門名 |
| 成功／錯誤提示卡 | 常帶剛操作那筆的姓名 |
| 瀏覽器分頁標題、網址列 | 客戶代號、租戶 slug |

### 做法：截圖前換成假資料，不要事後遮罩

遮罩是事後在 PNG 上塗色塊，代價全落在讀者身上：整欄變色塊、清單只剩圓圈、遮罩色與底色對不上、與紅框相交、整批標準不一致。現行做法是截圖前用腳本把 DOM 裡的值換成假資料，截出來就是正常畫面。流程與工具見 `browser-docs:annotate-screenshot` 的「前置：個資」。

- 只換三類：姓名、客戶或租戶名稱、金額。設備名稱、單據編號、品項、流程說明、功能代碼是業務內容，換掉手冊就失真。
- 登入的公司固定換成「示範公司」，不從假名池抽：跨功能、跨批次每份手冊都一樣。它不是客戶：同一張圖常兩者並存，客戶名走假名池，租戶名固定示範公司。判準是「它代表登入的那家公司嗎」，不是「它長在哪個位置」。
- 假名跨圖一致（同一個人每張圖都叫同一個名字），看起來像真的（不用 `XXX`、`測試1`）。
- 遮罩只留作備案，用在腳本改不到的地方：canvas／SVG 文字、圖片型內容、瀏覽器邊框。

示範資料也要像樣：用 `TEST-0001` 這類測試客戶示範「資料沒建完整會怎樣」，畫面是對的，但看起來不專業。

## 章節標記與排序

每章前後加 HTML 註解，標記章節 id 與對應的畫面路由（PDF 看不到，但它是「章節 ↔ 畫面」唯一的機器可讀對應，局部更新靠它定位；id 用 kebab-case）：

```
<!-- section: create-po route:/purchase/orders/new -->
# 第四章　新增採購單
...
<!-- /section: create-po -->
```

章節跟著使用者的作業順序，不跟系統選單：

| 章 | 內容 | 必要性 |
|---|---|---|
| 第一章 開始之前 | 前置主檔、自動帶入規則、權限 | 有前置依賴時必要 |
| 第二章 進入功能 | 從主控台進入、認識主畫面 | 必要 |
| 第三章起 | 依作業順序：查詢、新增、修改、週邊操作、列印／匯出 | 必要 |
| 倒數第二章 | 常見錯誤訊息 | 有驗證訊息時必要 |
| 附錄 A | 名詞對照 | 必要 |
| 附錄 B | 為什麼會這樣 | 必要 |

每章最小單位是「步驟N. 動作名稱」，一步一張圖，必要時下方加 `> **說明：**`；一節結束用 **檢查結果** 告訴讀者怎麼確認做對了。

## 檔案與存放

| 項目 | 規則 |
|------|------|
| 手冊 | `{docs-root}/操作手冊/{模組}/{功能}/{功能名稱}_操作手冊.md` |
| 簡報 | 同目錄 `{功能名稱}_操作手冊簡報.md`（Marp） |
| 截圖 | 同目錄 `images/aNN-英文語意名.png` |
| 檔名語言 | 圖檔一律英文，中文檔名在部分平台與工具會出錯 |
| 圖片歸屬 | 每份手冊自備，不跨目錄引用共用圖（手冊要能整包交付） |

## 產出交付檔

指令與格式限制見 [build-deliverables.md](build-deliverables.md)。封面資訊取自手冊開頭的第一個表格；封面的品牌文字由設定 `manual-brand` 或 `--brand` 決定，都沒有就不印。
目錄由 H1／H2 自動產生，PDF 的目錄可點擊但沒有頁碼。簡報不要用 raw HTML 做色塊（Marp 預設不允許，標籤會原樣印出來），要色塊用 blockquote。
