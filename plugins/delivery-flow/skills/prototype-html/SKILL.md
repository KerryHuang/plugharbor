# prototype-html — 需求描述 → 單檔 HTML 原型

> 非 Claude Code（如 Pi）執行時，先讀 `${CLAUDE_PLUGIN_ROOT}/references/harness-terms.md`（Claude Code 照字面執行可略過），把 Claude 專屬工具與路徑換成對應項。提問照該檔對照：Claude Code 用 `AskUserQuestion`，pi 用 `ask_user`，其他純文字一次一題。

把一個功能的畫面做成單一、self-contained、可點切換的 HTML 原型，讓 PO 或客戶在需求階段確認「畫面長這樣對不對」。原型不是正式前端：不寫框架程式、不串真實 API、不當開發版面依據。

參考檔都在 `${CLAUDE_SKILL_DIR}/references/`：

| 檔案 | 何時讀 |
|---|---|
| `assembly-guide.md` | 組裝前必讀：檔案形態、版型、狀態、說明面板、驗證 |
| `neutral-style.css` | 沒有設計系統時，用 `cat` 進輸出檔的 `<style>`，不要 Read 進 context |
| `field-layout-criteria.md` | 畫面含表單（新增、編輯、篩選）時推導欄位用 |
| `mock-data.md` | 填資料前必讀 |

## 輸入

| 參數 | 必填 | 說明 |
|---|---|---|
| 功能名 | 是 | 命名輸出檔與標題，kebab-case 佳 |
| `--from <路徑>` | 否 | 需求文件、探索摘要或規格作為畫面來源 |
| `--design-system <URL 或路徑>` | 否 | 使用者的設計系統；沒給就用 `neutral-style.css` |
| 補述 | 否 | 沒有文件時，用口述描述要畫的畫面與欄位 |

來源優先序：`--from` 文件 → 使用者口述 → 使用者貼的樣本資料或截圖。

## 流程

### 1. 解析需求，不確定就停下來問

整理出畫面清單，以及每個畫面的欄位、狀態、主要操作。

**需求本身有歧義時，停下來問，不先畫再說。** 歧義的徵兆：做什麼、為誰、範圍到哪、兩個說法是不是同一件事、資料量級（影響要不要分頁、要不要搜尋）、有哪些角色看得到哪些欄位。

問法：用具體例子，不問抽象選擇。提問工具照 `${CLAUDE_PLUGIN_ROOT}/references/harness-terms.md`，一次一題，建議選項放第一個並標（推薦）。

| 不要這樣問 | 這樣問 |
|---|---|
| 「列表要分頁嗎？」 | 「訂單列表大概有多少筆？例如每天 20 筆，一頁看得完就不需要分頁；每天 500 筆，就要分頁加搜尋。你們比較接近哪一種？」 |
| 「要哪些欄位？」 | 「客服要在列表上直接判斷這張單能不能出貨，我會放『單號、客戶、金額、狀態、下單日』。需要加『付款方式』嗎？」 |

只問會改變畫面結構的事。不改版面的細節（文案、欄位順序微調）不問，直接做並寫進說明面板的「待確認」。使用者說「你決定」，就選推薦項並記在「已定案」。

### 2. 開工前先看有沒有既有原型

```bash
find . -name '*_prototype.html' -not -path './node_modules/*'
```

同功能已有原型就改原檔：不新建、不改檔名、不另存新版，用 Edit 逐處改。細節見 `assembly-guide.md` 第六節。

### 3. 決定風格來源

- 使用者給了設計系統（URL 或檔案）：讀它的 token 與元件，照它做。讀不到就請使用者給檔案，不自己猜一組「類似的」。
- 沒給：用 `neutral-style.css`。不要自創公司色票、不模仿特定品牌。

### 4. 推導畫面

不是把欄位排出來就好。先想：誰在用、查詢條件要哪些、列表欄位怎麼顯示、操作動線（快速進編輯、批次操作）、規則邊界（空值、上限、權限）。

表單類畫面照 `field-layout-criteria.md` 的零到三節推導（必填真假、分區、連動欄位同框、預設值）。

推導不出來的、需求沒寫的規則，不自行發明，列進「待確認」。

### 5. 準備資料

照 `mock-data.md`：

- 使用者提供了樣本，就用樣本的組合（量級、金額範圍、日期跨度、狀態分布），識別值換成假的。
- 沒樣本，數量、金額、日期、狀態的組合要寫實、不整齊。
- 識別值一律假：email 用 `example.test`，電話與證號用明顯假樣式。

### 6. 組裝

照 `assembly-guide.md`：單一檔、CSS inline、側欄切換多畫面、必含設計說明面板、呈現正常／空狀態／錯誤／關鍵 chip。

輸出路徑：專案有慣例（例如與需求文件同目錄）就照做，沒有就問使用者要放哪；問不到就放目前目錄下的 `<功能名>_prototype.html`。

### 7. 自我驗證

照 `assembly-guide.md` 第七節跑 grep。有瀏覽器工具就自己開檔截圖看版面；沒有就在回報註明「視覺未驗證」。

### 8. 待確認逐題問

說明面板的「待確認」清單有項目時，不要留在面板就收工。只問第 1 步定義的「會改變畫面結構」的項目，逐題問使用者，一次一題，附推導依據與建議選項；不改版面的細節（文案、欄位順序微調）維持在「待確認」不問：

- 當下定案：用 Edit 改原型對應處，把該項從「待確認」移到「已定案」並附一句結論。
- 使用者說要 PO 本人拍板：保留在「待確認」。

## 收尾條件

全部成立才算完成：

1. 原型檔存在，路徑已回報（改既有原型時路徑不變）。
2. `src="http` 與 `href="http` 的 grep 都為 0。
3. 設計說明面板存在，含推導與「待確認」。
4. 第 8 步已執行；回報「已定案 N 項、留待 PO M 項」，M 項逐項列出。
5. 資料沒有任何真實個資或真實客戶資訊。

## 非目標

- 不寫 Vue、React 等正式前端，不串真實 API，不做真實驗證或分頁運算。
- 不取代畫面規格文件：原型負責「長相與動線」，規格負責「欄位與規則」。
- 不綁任何資料庫工具或 DB agent：資料來源只有使用者提供的樣本與 `mock-data.md`。
- 不自動附到票務工具；要附由使用者決定。
