# Shared Preludes — 常駐卡

> 各 skill 開工前先載入的共通原則。只留要點，skill 專屬細節放各自的 `references/`。

## 核心原則：問題漏斗——實證 → 使用者
每個要決定的問題依序過兩層，前一層解得掉就不往下送：
1. **實證**：先用一手證據驗證**問題本身**。先查現行方案（①同類既有產出 ②專案慣例 ③上游文件 ④現行 codebase），涉及資料語意或行為的，要拿實機畫面、實際輸出、唯讀查詢結果或原始碼（附行號）。證據推翻問題前提 → 撤題；證據直接給出答案 → 採用並標依據。
2. **使用者**：只剩實證解不了的——業務／商業取捨、不可逆、證據不足。題目附「實證查到什麼」。

**平台／UI 慣例以現行 codebase 為準**（分頁與每頁筆數、空值與數字格式、對話框開法、匯出與列印管道等）：照既有先例直接採用並標檔案路徑，不提問；無先例或先例互相衝突才問。

## 互動詢問規範
用 `AskUserQuestion`（其他 harness 的對照見 `harness-terms.md`）；推薦項置首標「（推薦）」；**一律一次一題**（每個裁決一次，不列清單讓人批次勾選，回報結尾的提問也一樣）；長內容先以文字收尾一回合再問。

**題目要讓沒跟上前文的人一看就懂：**
- **白話先行、代碼放括號**：表名、欄位、狀態碼、內部編號不單獨出現，先寫意思，例如「出貨單狀態（`ship_status`）」。
- **選項寫後果**：label 說選什麼，description 說選了之後會發生什麼、影響哪些人或資料、有什麼代價；不要只重述 label。
- **一題一件事**：問句要能直接回答，不把兩個決定塞進同一題。
- 對照：✗「`ship_status=B` 要對齊 D-2 嗎？」→ ✓「簡易版出貨清單比完整版少了『退回量』欄。新版要沿用簡易版的精簡欄位，還是統一用完整版？」

**需求題用具體例子問**：一句話帶過的需求題，使用者常答「都可以」或答錯，因為看不到後果。
1. **例子來源**（優先序）：測試環境的真實單據 → 現行系統的實際輸出 → 標明「假設情境」的自造例。落檔時人名改角色。
2. **題型**：情境（誰、何時、數字）→ 問畫面該顯示什麼 → 選項寫結果與代價。例（虛構）：「小林訂了 500 個、已出 300、退回 20，清單的『未出量』要顯示 220 還是 200？」選項：「220：退回視同沒出，業務會再排出貨」「200：退回另走退貨單，未出量不動」。
3. **順序**：先問正常情況，真的會分岔才追邊界，不一次丟所有極端值。
4. **落檔**：確認過的例子直接寫成驗收條件的正反例，後續 QA 沿用同一筆。

## 核心原則：不猜測
先找答案 → 找不到才問（附建議）→ 確認後才寫 → 寫前總清查。不留 `[需要澄清]` 這類佔位。

## 核心原則：分析嚴謹度
下結論（需新建／沒有／根因是 X）前逐項確認：來源查齊、深度到源頭、與現況對齊、維度齊全、證據優先。結論標 Confirmed／Likely／Unknown；否定結論註明查過哪些地方。

## 核心原則：權威來源優先序
①範本與一手證據定格式與結論 ②既有同類產出只給在地化參數 ③他人的結論只是線索。動手前問：我照的是範本，還是某人上次的產出？

## 核心原則：決策回寫的掃描義務
回寫前列全部落點（相關文件、索引、CHANGELOG、上游既定敘述）。**取代不追加**：舊敘述必刪，不留矛盾的兩份說法。

## Step 0.3: Plugin 版本對版
鏈起頭與每個硬性停點，比對已載入的 plugin 版本與 marketplace（`plugharbor`）最新版本。跨 patch 一行告知；跨 minor 以上停下建議 `/reload-plugins`。查不到 marketplace 資訊則略過。

## Step 0.5: 落檔位置
產出放專案既有的目錄慣例；會議記錄的位置看 `publish-target`（見 `config.md`）。**不自建第一階目錄**，都不適用就問使用者。

## 引用方式（在 SKILL.md 中）
`> 核心原則 / 前置步驟：依 ${CLAUDE_PLUGIN_ROOT}/references/shared-preludes.md。`
