# 審查要證據

審查的結論要能被別人重驗：每一句「沒問題」「查無」都附上怎麼查的。下列規則同時適用主 session 與審查 subagent，派工時把本檔路徑寫進 prompt。

## 1. 預設只報告

review 的產出是報告，不改檔、不 commit、不留言、不 merge。使用者明確要求「順便修」「直接留言」「審完 merge」才做那一步（遠端留言與 merge 見 `review-remote.md`）。

## 2. 變更檔歸屬表

列出 diff 的每一個變更檔（`git diff --name-only <base>...HEAD`），每檔歸到至少一個檢查項，或寫明排除理由；不能有檔案沒人看過。

```markdown
| 變更檔 | 歸到的檢查項 | 結論 |
|---|---|---|
| src/order/service.ts | 資料存取、測試 | 1 個 ⚠️（見 #3） |
| package-lock.json | 排除：相依鎖檔，套件本身在「新套件」項查 | — |
| docs/api.md | 排除：純文件，不影響行為 | — |
```

檢查清單的每一項也要有結論（通過／有發現／不適用＋一句理由），不留空白。

## 3. 「查無」前先證明查得到

宣稱「沒有 X」之前，先證明那個查法抓得到已知的 X：

- 用 grep／搜尋時，先對一個已知命中（既有程式裡確定有的例子，或臨時樣本）跑同一條指令，看到命中再對變更範圍跑。
- 跑測試或 linter 判「沒有失敗」時，確認它真的有跑到變更檔（看收集到的檔數或測試數，不是 0）。
- 報告寫成「查無 X（指令：`…`；已對 `<已知命中>` 驗證抓得到）」。做不到驗證就寫「未驗證」，不寫「查無」。

## 4. 標出被削弱的保護

以下變更即使「測試全綠」也要逐條列為發現（至少 ⚠️），並寫出改前改後：

- **被削弱的測試**：刪測試、加 skip／only／xfail、放寬斷言（精確值改成「不為空」、刪 assert）、改預期值去配合新輸出、mock 掉原本真實跑的路徑。
- **拉長的 timeout／重試**：測試或程式的逾時、重試次數、sleep 被調大。
- **新增的 suppression**：lint／型別／analyzer 的 ignore、disable、`@ts-ignore`、`# noqa`、`#pragma warning disable`、`eslint-disable`、`nolint`，以及新加進忽略清單的路徑。

每條要回答：為什麼需要、有沒有不削弱的替代做法。理由不成立就列為要修。

## 5. 新套件查 registry

diff 新增相依（套件清單或鎖檔有新名稱）時，逐一到對應 registry 查證真的存在，且名稱拼字正確（防 AI 幻想出的套件名與仿冒套件）：

```bash
npm view <name> name version            # npm
pip index versions <name>               # PyPI（或 curl https://pypi.org/pypi/<name>/json）
dotnet package search <name> --exact-match   # NuGet
go list -m <module>@latest              # Go
cargo search <name> --limit 1           # crates.io
```

查不到、下載量極低、建立時間很新、名稱跟知名套件只差一兩個字 → 列為 🚫，請作者確認來源。查詢結果（版本、存在與否）寫進報告。

## 6. 報告要附的證據段

報告最後加一段「證據」：

- 變更檔歸屬表（第 2 節）
- 每個「查無」的指令與驗證（第 3 節）
- 被削弱的保護清單，沒有就寫「無（查法：…）」（第 4 節）
- 新套件查證結果，沒有新套件就寫「無新增相依」（第 5 節）
- 比對過的規範檔清單，沒有就寫「無適用規範檔」（第 7 節）

## 7. 專案規範合規

- 蒐集：每個變更檔從自身目錄往上到 repo 根，路徑上的 `CLAUDE.md`、`AGENTS.md`。
- 比對：只拿路徑涵蓋該檔的規範，別的目錄的規範不套用。
- 列為發現時，引用規則原文與規範檔路徑；引用不出來就不算發現。
- 驗證時，除了發現與 `file:line`，也把規則原文與規範檔路徑交給驗證 subagent，要它確認規則涵蓋該檔且確實違反。
