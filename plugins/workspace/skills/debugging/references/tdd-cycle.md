# TDD 循環：Red-Green-Refactor

適用：任務標記 `[TDD]`、使用 `--tdd` 參數、實作複雜業務邏輯需測試先行。與技術棧無關；指令用專案自帶的測試指令，迭代期只跑本測試類別／檔案（篩選條件）。

```
Red (寫失敗測試) → Green (最小實作) → Refactor (重構) → 重複
```

## Phase 1：Red — 寫失敗測試

1. **分析需求**：從規格書（若有）提取測試案例
   - 逐條對應業務規則：業務邏輯 → 分支／計算／狀態流轉測試；驗證規則 → 驗證器測試；Guard／前置條件 → guard clause 測試
   - 依測試價值判斷優先級，**高價值先行**（業務分支、Guard、計算、狀態流轉、驗證）
   - 每條規則至少 1 個測試，顯示名稱標註規則來源
2. **建立測試類別**（放在專案測試目錄的對應位置，跟隨既有結構）
3. **生成測試骨架**：有裝 `backend` 用 `backend:unit-testing`（可選）；沒裝就照專案既有測試當樣板
4. **執行驗證**（只跑本測試類別）
5. **確認失敗**：測試必須失敗（紅燈）——編譯失敗也算預期紅燈

輸出：

```
[RED] 測試 {TestName} 已建立
[RED] 執行結果：失敗 ✓（預期行為）
[RED] 失敗原因：{原因}
→ 進入 Green Phase
```

## Phase 2：Green — 最小實作

原則：**只寫通過測試的最小程式碼**，不追求完美、不過度設計，允許暫時的「醜」程式碼。

1. 建立實作檔案（若不存在）
2. 寫最小程式碼通過測試
3. 執行驗證，確認通過（綠燈）

```
[GREEN] 實作 {ClassName} 已建立
[GREEN] 執行結果：通過 ✓
→ 進入 Refactor Phase
```

## Phase 3：Refactor — 重構

原則：**不改變外部行為**，改善可讀性、移除重複、提取方法。

1. 識別重構機會：重複程式碼、過長方法、命名不清
2. 執行重構
3. 執行驗證，確認仍通過（綠燈）

```
[REFACTOR] 重構完成：{重構描述}
[REFACTOR] 執行結果：通過 ✓
→ 循環完成，可進入下一個測試案例
```

## 循環完成報告

```markdown
## TDD 循環報告

| 階段 | 狀態 | 說明 |
|------|------|------|
| Red | ✅ | 測試 {TestName} 建立並失敗 |
| Green | ✅ | 實作 {ClassName} 通過測試 |
| Refactor | ✅ | {重構描述} |

### 建立的檔案
- 測試：`{TestFilePath}`
- 實作：`{ImplFilePath}`

### 下一步
- [ ] 繼續下一個測試案例
- [ ] 最終回歸：跑全 suite（commit 前跑一次）
```

## 整合

- **測試命名**：方法名 `Method_Scenario_ExpectedResult`（英文）；顯示名稱是否用繁中跟隨團隊慣例
- **收尾**：完成所有循環後，走 `backend:unit-testing` 的 Step 5 測試價值複審剪枝（可選；沒裝就自行檢查有無「測框架本身」的低價值案例，刪除前徵詢使用者），再 commit
- **角色分工（有裝 lifecycle 時，可選）**：`lifecycle:tester` 負責 Red，`lifecycle:developer` 負責 Green 與 Refactor（沒裝 lifecycle 就用 general-purpose agent 分別帶「測試工程師」「實作者」角色說明；職責 plugin 載入了附錄時，把附錄絕對路徑寫進派工 prompt）
