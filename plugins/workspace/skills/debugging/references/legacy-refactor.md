# 重構沒有測試的舊程式碼

要重構、但動到的範圍沒有測試覆蓋時照這份做；已有測試就直接走 [tdd-cycle.md](tdd-cycle.md) 的 Refactor 階段。

**重構不改行為；行為變更（含修 bug）另開 commit。沒有鎖住行為的測試就不動手重構。**

## 1. 先鎖住現有行為

- **特徵測試**：用實際輸入呼叫要動的範圍，把「目前的輸出」原樣寫成斷言。看起來像 bug 也照錄，標註「疑似 bug」另案處理，不在重構中順手修。第一次執行必須綠燈；紅燈代表沒抓到現況，改測試不改程式。
- **黃金樣本**：輸出大或難逐欄斷言（報表、產檔、整段 HTML／JSON）時，存一份基準輸出，重構後整份比對。先把時間戳、亂數、不定排序等不穩定欄位固定或排除。
- **驗證測試真的會抓**：故意改壞受測程式一處，確認測試轉紅，再還原。
- **難以測試**（外部 IO、UI、靜態相依）：先做最小的 seam 改動（把相依改成參數或介面注入），這一步用 IDE／語言工具的自動重構，不手改邏輯。

## 2. 大型改動先排順序（Mikado）

- 直接試做目標改動；編譯或測試一壞，記下缺的前置條件，`git restore` 回綠燈，先做最底層的前置，逐層往上。
- 依賴圖記在計畫檔或 `.tmp/`；不在紅燈上疊改動。
- 整個模組要換掉時，新舊並存、逐條呼叫路徑切到新實作，切完才刪舊的（絞殺榕）。

## 3. 小步執行

- 一步一個手法（抽取函式、改名、移動、引入參數物件…），跑篩選測試，綠燈才走下一步；每個綠燈都是可 commit 的點。
- 改名、移動、抽取優先用 IDE／LSP 的自動重構。只能文字取代時，grep 全專案，含字串、反射、設定檔、DI 註冊、序列化欄位。
- 刪「沒有呼叫端」的程式碼前，同樣查反射、DI、序列化、公開 API、設定檔的引用。
- 指標（複雜度、覆蓋率、linter 警告數）只拿來找下手處，不當目標；不一次清掉全部警告。

## 4. 收尾

- 全 suite 與黃金樣本比對都通過。
- 特徵測試留下當回歸測試，名稱改成說明行為的名字；只為重構而存的黃金樣本，問使用者要不要保留。
- 回報列出：鎖住了哪些行為、照錄而未修的疑似 bug、哪些步驟靠文字取代而非自動重構。
