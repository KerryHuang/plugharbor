# 系統性除錯

採 TDD 方式系統性除錯：先用測試重現問題，再改碼，最後用同一測試驗證修復。**沒有可重現的失敗測試就不動手改碼。**

測試先行開發（新功能、複雜業務邏輯、任務標 `[TDD]`）走同一條紅燈→綠燈→重構循環，做法見 [references/tdd-cycle.md](references/tdd-cycle.md)。

測試與建置指令一律用**專案自帶**的（README、CI、`package.json`、`Makefile` 找得到的那支）；迭代期帶篩選條件只跑相關測試，全 suite 留到最後回歸。有裝 `backend` 且是 .NET 專案時，指令與範本見其 `unit-testing` 的 .NET 附錄（可選）。

## 除錯流程

### 1. 問題定義

收集資訊：錯誤訊息或非預期行為、重現步驟、預期行為 vs 實際行為。

### 2. 重現問題

建立**失敗測試**把 bug 條件固定下來（用專案現有的測試框架）：

```text
test "方法_bug 條件_預期行為":
    Arrange - 重現 bug 的條件（建立被測物件、mock 依賴）
    Act     - 呼叫有問題的方法
    Assert  - 預期的正確行為
```

執行並確認它**失敗**（先看到紅燈才有意義）。若測試一開始就綠，代表沒重現到 bug，回頭調整條件。

### 3. 根因分析

追蹤程式碼路徑：

1. 從失敗點向上追呼叫堆疊。
2. 檢查相關的服務／資料存取實作。
3. 驗證資料查詢邏輯（如適用）。
4. 檢查依賴注入（或相依設定）是否正確。

常見根因對照：

| 症狀 | 可能原因 |
|------|---------|
| Null 參考例外 | 依賴未註冊、設定值／連線字串為空 |
| 資料不正確 | 查詢或轉換邏輯錯誤 |
| 輸出未更新 | 狀態變更未觸發、快取未失效 |
| 操作無回應 | 前置條件判斷回傳 false、事件未綁定 |

> 追「為何」到源頭，別在下游改讀另一處資料把症狀遮掉。

### 4. 修復問題

對症下藥，改在正確的層：

- 領域邏輯問題 → 修改實體／領域規則
- 應用流程問題 → 修改應用服務
- 資料存取問題 → 修改 Repository／查詢
- 呈現層問題 → 修改 Controller／視圖模型

### 5. 驗證修復

先跑先前的失敗測試轉綠，再跑全部測試確認**無回歸**，最後跑專案的建置確認成功。

### 6. 除錯工具

- 詳細測試輸出（測試指令的 verbose 選項）。
- 只跑特定測試專案或檔案，縮小範圍。
- Mock 呼叫驗證：確認方法被呼叫／未被呼叫（語法依採用的 mocking 框架）。
- 必要時加策略性日誌，找到根因後移除。

## 檢查清單

- [ ] 建立失敗測試重現問題
- [ ] 識別根因（追到源頭，非表象）
- [ ] 修復程式碼（改在正確的層）
- [ ] 目標測試通過
- [ ] 全體測試無回歸
- [ ] 建置成功
