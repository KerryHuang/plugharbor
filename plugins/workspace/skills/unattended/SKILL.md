# 無人值守模式

使用者叫用後，主控照路線一個工作單元接一個往下做，**直到使用者回來（送出新訊息）為止**，不限晚上。可逆的決定自己拍板並記帳，只有「停下條件」才停。使用者回來時交一份能直接照著驗的回來報告。

流程裡寫「（專案）」的步驟，照專案根的 `.plugharbor/unattended.md` 做（格式見 `references/project-config.md`）。

## 自動駕駛模式

使用者說「自動駕駛」「照 roadmap 跑」時，先讀 `references/autopilot.md`：路線改從專案的 `docs/roadmap.md` 一段接一段取，只有使用者說「暫停」「停止自動駕駛」才停，一般訊息處理完就繼續。開場檢查、插手與接回、佔位段、段收尾都照該檔，其餘照本檔。

## 0. 開場：先讀專案設定

- 讀 `.plugharbor/unattended.md`。沒有這份檔，**趁使用者還在**一次一題問，先問閘門與合併（必要），再問部署與實機驗證，照範本寫出來再開始。問不到（人已經走了）就不合併、不部署：每個單元做到審查完，留在自己的分支上，寫進報告。
- 把授權範圍寫進帳本開頭，派出去的每個 worker／subagent prompt 也照抄：
  - 可改：本 repo 的哪些 worktree／分支；可不可以合併、push（專案）。
  - **其他 repo 一律不動**：看到別的 repo 該修，只寫進回來報告的「刻意沒做」，不 commit、不 push、不發版。
  - 範圍：路線上的哪幾個工作單元、做到哪算哪。
  - 電源（專案）：使用者離開前確認接電源、別蓋螢幕；人已經走了就記進報告，並預期長測試可能因睡眠逾時。

## 1. 裁決帳本

帳本放 repo 外的 `.tmp/<YYYYMMDD>-<slug>/plan.md`（位置規則見 `tmp-scratch`），每件事一行，附時間：

- `使用者裁決：…`（原話或明確選項）和 `主控裁決（待使用者確認）：… — 理由 — 選錯的代價` 分開寫，絕不把自己的決定寫成使用者說的。
- 審查結果、閘門數字、commit 範圍、部署結果都記進來。context 被壓縮後以帳本與 `git log` 為準。

## 2. 一個工作單元的流程

0. **設計單元：先分類、再送審。** 初稿裡「代為決定的事」分兩類：
   - **使用者行為類**：答案反過來，使用者的操作步驟、畫面、誰能做什麼會變（上下限、權限、狀態推進、刪除與取消規則、訊息揭露）。
   - **技術類**：只有程式內部不同（存哪、格式、命名、檢查放哪一步），主控裁決記帳，不問。

   行為類照推薦做、記成主控裁決待確認、列進回來報告的「待決」；題目帶具體例子，讓人不看設計也能答。推翻的先改設計再續審。理由：方向翻盤要整段重審。
1. 派實作（subagent 或 pane worker），prompt 自足並含第 0 節的授權範圍。實作與修正時只跑相關的測試類別或檔案，加上 typecheck、build；完整套件只在第 4 步閘門跑一次（本機或 CI 照專案設定）。
2. 審查：有 `toolkit:agent-dispatch` 就先試跨家族；沒裝或湊不到別家，就同家、用新 context 審，回報寫「退回同家審查」。派工腳本報錯而退回同家的是**工具故障**：照常往下做，但在回來報告最前面標 🔴、附錯誤訊息，有推播工具就推播；不能寫成湊不到別家。
3. 依審查修正。會改變使用者看得到的行為的建議，採用也可以，但記成主控裁決待確認。
4. 閘門（專案）：背景跑，等通知。全部通過才往下。
5. 外洩掃描（專案，沒設定就略過）：只看筆數，必須全部是 0。
6. 合併（專案）：設定檔在、但沒寫合併方式就用 fast-forward 推預設分支；落後就先 rebase 再重跑閘門。不用 merge commit、不 force push。
7. 部署（專案）：背景等通知；這次的變更不會觸發部署就不等。
8. 實機驗證（專案）：照專案寫的方式驗這次動到的地方。
9. 更新帳本與回來報告，照 `worktree` 的移除流程清掉這個單元的 worktree（沒做完、或有未 commit／未 push 的內容就保留 worktree 與分支，寫進報告），**接著做下一個工作單元**。做完一個就停是錯的：授權是一路推到使用者回來。

長工作（閘門、部署、審查、worker）丟背景時，先挑空檔工作，沒有才等，不輪詢。每次在帳本記一行 `空檔：等 <工作>（<資源>）→ 做 <工作>`，或 `空檔：無 — <理由>`。依序挑：

| 候選 | 條件 |
|---|---|
| 後續單元或段的計畫、設計、文件，更新回來報告 | 永遠可做：不吃 CPU、不改程式碼 |
| 另一個 worktree 實作別的單元 | 和進行中的單元沒有共用檔（專案設定的共用檔清單），且兩條線的重測試錯開 |
| 改到同一批檔案的單元 | 不做，照順序 |

## 3. 資源規則

- 同一個 worktree 裡有人在改檔時不跑閘門；要並行就讓另一方用另一個 worktree。
- 兩件工作共用同一批檔案、schema 遷移、build 產物或瀏覽器就不並行：前一件合併後，下一件才開始實作。只共用 CPU 的可以並行實作，但重測試不同時跑。專案的具體清單寫在專案設定。
- worker 交回、讀完結果檔就關它的 pane，不留著待命。
- 開 herdr pane worker 時帶 `--env AGENT_DISPATCH_UNATTENDED=1`（有裝 toolkit 時，worker 的提問會被擋下、改照推薦做）；worker 代做的決定收進回來報告的「主控裁決待確認」。不寫自動回答提問的程式；仍卡住就記進報告。

## 4. 停下條件（只有這些）

- 不可逆或破壞性操作：force push、刪分支／資料、`reset --hard`。
- 要動授權範圍外的東西：其他 repo、使用者層設定、帳號、付費服務。
- 閘門或部署失敗，查不出原因，或修了兩次還是失敗。
- 設計沒涵蓋、而且會改格式或使用者行為的分岔；兩邊都可逆的話，照建議做並記帳，不停。

停下時把現況、證據、建議寫進回來報告的「待決」，然後去做路線上不依賴它的下一件事；沒有可做的才結束。

## 5. 異常判讀

- 測試大量逾時、執行時間是平常的好幾倍：先查電腦是不是睡了（macOS：`pmset -g log | grep -E "Entering Sleep|DarkWake to FullWake"`）。是睡眠就照原樣重跑，不改測試。`caffeinate` 擋不住蓋螢幕。
- 部署失敗：看託管平台 log；是這次合併造成的就 `git revert` 該 commit 並 push，不 reset。

## 6. 回來報告

寫在帳本同一個資料夾的 `return-report.md`。使用者回來時先交報告（路徑加一句話結論），再從第 6 項開始一次一題問。報告依序：

1. 一句話結論：哪些可以驗、哪些還不行。
2. 可驗項目：每項附路徑、帳號或資料、具體操作步驟與預期結果。
3. 驗證結果分開宣稱：閘門數字、外洩掃描、push 的 commit 範圍、部署、實機；沒跑到的標「未驗證」。工具故障造成的降級標 🔴 列在最前面。
4. 主控裁決待確認：每條附理由與選錯代價。
5. 刻意沒做的事（含其他 repo 的發現）與已知問題。
6. 待決：用 AskUserQuestion 一次一題問。
