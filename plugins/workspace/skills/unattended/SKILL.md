# 無人值守模式

使用者叫用後，主控照路線一個工作單元接一個往下做，**直到使用者回來（送出新訊息）為止**，不限晚上。可逆的決定自己拍板並記帳，只有「停下條件」才停。使用者回來時交一份能直接照著驗的回來報告。

流程裡寫「（專案）」的步驟，照專案根的 `.plugharbor/unattended.md` 做（格式見 `references/project-config.md`）。

## 自動駕駛模式

使用者說「自動駕駛」「照 roadmap 跑」時，先讀 `references/autopilot.md`：路線改從專案的 `docs/roadmap.md` 一段接一段取，只有使用者說「暫停」「停止自動駕駛」才停，一般訊息處理完就繼續。開場檢查、插手與接回、佔位段、段收尾都照該檔，其餘照本檔。

## 0. 開場：先讀專案設定

- 讀 `.plugharbor/unattended.md`。沒有這份檔，**趁使用者還在**一次一題問，先問閘門與合併（必要），再問部署與實機驗證，照範本寫出來再開始。問不到（人已經走了）就不合併、不部署：每個單元做到審查完，留在自己的分支上，寫進報告。
- 把授權範圍寫進帳本開頭，派出去的每個 worker／subagent prompt 也照抄：
  - 可改：本 repo 的哪些 worktree／分支；可不可以合併、push（專案）。
  - **授權 repo 清單**：只能動專案設定「授權 repo」明列的 repo 與操作（改、push、發版）；沒列的一律不動：看到該修，只寫進回來報告的「處置結果」，不 commit、不 push、不發版。細則見 `references/speed-rules.md` 的「工具 repo」。
  - 範圍：路線上的哪幾個工作單元、做到哪算哪。
  - 電源（專案）：使用者離開前確認接電源、別蓋螢幕；人已經走了就記進報告，並預期長測試可能因睡眠逾時。

## 1. 裁決帳本

帳本放 repo 外的 `.tmp/<YYYYMMDD>-<slug>/plan.md`（位置規則見 `tmp-scratch`），每件事一行，附時間：

- `使用者裁決：…`（原話或明確選項）和 `主控裁決（待使用者確認）：… — 理由 — 選錯的代價` 分開寫，絕不把自己的決定寫成使用者說的。
- 審查結果、閘門數字、commit 範圍、部署結果都記進來。context 被壓縮後以帳本與 `git log` 為準。

## 2. 一個工作單元的流程

審查、閘門、合併以「一次交付」（整段，或使用者指定的單元）為單位；一次交付裡的子單元只是實作者內部各自 commit 的切分，不各走一套計畫、審查、CI。專案設定的「單元流程」可覆寫本節的預設。速度規則（計畫、審查、測試、修正、插單、CI 證據、量測）見 `references/speed-rules.md`。

0. **設計單元：先分類、再送審。** 初稿裡「代為決定的事」分兩類：
   - **使用者行為類**：答案反過來，使用者的操作步驟、畫面、誰能做什麼會變（上下限、權限、狀態推進、刪除與取消規則、訊息揭露）。
   - **技術類**：只有程式內部不同（存哪、格式、命名、檢查放哪一步），主控裁決記帳，不問。

   行為類照推薦做、記成主控裁決待確認、列進回來報告的「待決」；題目帶具體例子，讓人不看設計也能答。推翻的先改設計再續審。理由：方向翻盤要整段重審。
1. 開工登記：有裝 `toolkit:tower` 就在單元 worktree（沒有先開）裡跑 `tower.py takeoff --mode unattended --goal "<單元目標>" --segment <段號>`（帶預計 `--paths`），航班 ID 記帳本；起飛回 `kind: work` 重疊就跳過此段，`kind: path` 當共用檔照順序；沒裝照舊。
2. 派實作（subagent 或 pane worker），prompt 自足並含第 0 節的授權範圍。**設計夠細（介面、權限、錯誤行為、驗收案例都有）就不另寫實作計畫、不審計畫**，整段交一個實作者做到底；缺哪項先補哪項。本機只跑新增或修改的測試類別、直接受影響的既有類別，加前端 typecheck／build；安全網與完整套件交閘門（第 5 步）。
3. 審查：整段完成後**讀整份 diff 審一次**，新 context；有 `toolkit:agent-dispatch` 就先試跨家族，沒裝或湊不到別家，就同家、新 context 審，回報寫「退回同家審查」。審查者從 diff 出發，可讀必要上下文（呼叫端、權限守衛、既有測試），**不跑測試**。派工腳本報錯而退回同家的是**工具故障**：照常往下做，但在回來報告最前面標 🔴、附錯誤訊息，有推播工具就推播；不能寫成湊不到別家。
4. 修正：交回**原實作者**（續派沿用 context，附錯誤情境、通過條件、目前 SHA），修一輪；同一問題反覆誤解就換人診斷。一次審查加一輪修正是正常路徑的目標，不是上限：安全、權限、資料錯誤、公開契約的問題必修，修完逐項核對原發現；審出 🔴 的安全類修完再審一次。會改變使用者看得到的行為的建議，採用也可以，但記成主控裁決待確認。
5. 閘門（專案）：背景跑，等通知，一次交付一次 CI。所有必要 job 通過才往下；首個失敗就通知診斷，不等全跑完。最終版與已驗證版的測試／建置輸入相同（只差文件）可沿用結果，細則見 `references/speed-rules.md`。
6. 外洩掃描（專案，沒設定就略過）：只看筆數，必須全部是 0。
7. 合併（專案）：設定檔在、但沒寫合併方式就用 fast-forward 推預設分支；落後就先在本地 rebase 再重跑閘門（重跑與否見 `references/speed-rules.md`「CI 證據」），只 fast-forward 推預設分支；rebase 過的功能分支不推回同名遠端分支（已推過的只能 force push）。不用 merge commit、不 force push。有裝 `toolkit:tower` 先 `land-check`：10 → `override --kind scope --reason "<理由>"`；11 → 帳本記 `空檔：等航班 <id> 落地` 並做別的；12 → rebase、重跑閘門後重試；沒裝照舊。
8. 部署（專案）：背景等通知；這次的變更不會觸發部署就不等。
9. 實機驗證（專案）：照專案寫的方式驗這次動到的地方。
10. 更新帳本與回來報告，有裝 `toolkit:tower`，確定單元已完成、要清 worktree 時才 `tower.py release`，再照 `worktree` 的移除流程清掉本地 worktree 與分支；遠端分支照專案設定「合併」寫的處理，沒寫就保留並列進報告，不自行 `push --delete`（沒做完、或有未 commit／未 push 的內容就保留 worktree 與分支且不 release，寫進報告），**接著做下一個工作單元**。做完一個就停是錯的：授權是一路推到使用者回來。

長工作（閘門、部署、審查、worker）丟背景時，先挑空檔工作，沒有才等，不輪詢。每次在帳本記一行 `等待工作／SHA｜選定任務｜資源｜產出或暫停點`；選不到就寫具體阻塞（缺哪個前置、哪個衝突），不反覆抄「下一段相依」。依序挑：

| 候選 | 條件 |
|---|---|
| 空檔來源的項目（開 worktree 動手前也照第 1 步 takeoff；沒登記，land-check 只回「沒有航班」等於沒檢查）（待辦檔「近期可開工」、roadmap 近期段的前置、審查與報告留下的缺陷、flaky／CI 紀錄、文件落差；來源與欄位見 `references/speed-rules.md`） | 依賴已滿足；唯讀或文件類不吃 CPU、不改程式碼，永遠可做 |
| 另一個 worktree 實作別的單元 | 和進行中的單元沒有共用檔（專案設定的共用檔清單；同檔不同段落也算共用），重測試經 `scripts/test-lock.sh` 排隊 |
| 改到同一批檔案的單元 | 不做，照順序 |

下一段的實作依賴這段，不代表它的決策題、驗收案例、file map 不能先做。小型唯讀整理主控自己做，不另派 agent。

## 3. 資源規則

- 同一個 worktree 裡有人在改檔時不跑閘門；要並行就讓另一方用另一個 worktree。
- 兩件工作共用同一批檔案、schema 遷移、build 產物或瀏覽器就不並行：前一件合併後，下一件才開始實作。只共用 CPU 的可以並行實作，但重測試不同時跑：一律用 `sh <本 skill 的 Base directory>/scripts/test-lock.sh <測試指令>` 包起來，派出去的 prompt 也照抄。專案的具體清單寫在專案設定。
- 實作者交回後不立刻丟掉：Agent subagent 記下 agent id，修正用 SendMessage 續派；pane worker 保留到該段審查與修正完成才關，帳本記 worker id／session，中斷後可恢復。審查者一律新 context，交回就關。
- 用 `toolkit:agent-dispatch` 的 `mux.py spawn` 開 worker 時帶 `--env AGENT_DISPATCH_UNATTENDED=1`（有裝 toolkit 時，worker 的提問會被擋下、改照推薦做）；worker 代做的決定收進回來報告的「主控裁決待確認」。不寫自動回答提問的程式；仍卡住就記進報告。

## 4. 停下條件（只有這些）

- 不可逆或破壞性操作：force push、刪分支／資料、`reset --hard`。
- 要動授權範圍外的東西：授權清單沒列的 repo 或操作、使用者層設定、帳號、付費服務。
- 閘門或部署失敗，查不出原因，或修了兩次還是失敗。
- 設計沒涵蓋、而且會改格式或使用者行為的分岔；兩邊都可逆的話，照建議做並記帳，不停。

停下時把現況、證據、建議寫進回來報告的「待決」，然後去做路線上不依賴它的下一件事；沒有可做的才結束。

## 5. 異常判讀

- 測試大量逾時、執行時間是平常的好幾倍：先查電腦是不是睡了（macOS：`pmset -g log | grep -E "Entering Sleep|DarkWake to FullWake"`）。是睡眠就照原樣重跑，不改測試。`caffeinate` 擋不住蓋螢幕。
- 部署失敗：看託管平台 log；是這次合併造成的就 `git revert` 該 commit 並 push，不 reset。

## 6. 回來報告

寫在帳本同一個資料夾的 `return-report.md`。使用者回來時先交報告（路徑加一句話結論），再從待決開始一次一題問。報告依序：

1. 一句話結論：哪些可以驗、哪些還不行。
2. 可驗項目：每項附路徑、帳號或資料、具體操作步驟與預期結果。
3. 驗證結果分開宣稱：閘門數字、外洩掃描、push 的 commit 範圍、部署、實機；沒跑到的標「未驗證」。工具故障造成的降級標 🔴 列在最前面。
4. 主控裁決待確認：每條附理由與選錯代價。
5. 處置結果：工作中發現的問題各自怎麼處理（已修、已排隊並有 owner 與啟動條件、待使用者決定、未授權不動，含授權範圍外 repo 的發現）與已知問題。
6. 塔台紀錄（有裝 `toolkit:tower` 才寫；沒裝略過）：`<git-common-dir>/tower/log.jsonl` 在帳本期間的事件（撞檔、override、等航班）。
7. 待決：用 AskUserQuestion 一次一題問。使用者答的時候明說以後都這樣（不只這次）的，在專案 `AGENTS.md` 的相關段落寫一行，附日期；之後他改口，就改原來那條，不另加相反的一條。只對這次有效的答案只記帳本。
