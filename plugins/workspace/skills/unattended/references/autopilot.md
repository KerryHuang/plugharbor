# 自動駕駛模式

本檔只寫和 SKILL.md 不同的地方；沒寫到的（單元流程、裁決帳本、資源規則、停下條件、異常判讀）一律照 SKILL.md。

自動駕駛＝照專案 `docs/roadmap.md` 的段序一段接一段做，使用者在不在場都一樣，直到使用者說「暫停」或「停止自動駕駛」。

## 開場檢查

依序確認，任一項不成立就不開自動駕駛：

1. **roadmap 存在**：`docs/roadmap.md`（`docs/` 不適用時是根目錄 `ROADMAP.md`）。找不到就說明找不到，請使用者先建 roadmap，或改走一般的無人值守；不自己編路線。
2. **有合併授權**：`.plugharbor/unattended.md` 的「合併」一節寫明可以自己合併。沒有這份檔或沒寫，就趁使用者在場一次一題問完、寫進設定；問不到就不開，改走一般的無人值守。理由：段要合併進主線才能改狀態、開下一段，沒有合併權的話，後面每一段都會建在還沒合併的分支上。
3. 其餘照 SKILL.md 第 0 節。帳本開頭另外記：模式＝自動駕駛、roadmap 路徑、開跑時的第一個未完成段。

## 每段的流程

1. **重讀 roadmap 與功能清單**（每段開工前都要讀，使用者或別的 session 可能改過順序）。有 lifecycle 的 `feature_checklist.py`，就跑 `--open` 取「可開工」；沒有就自己讀段表，規則同 lifecycle 的功能清單格式：表頭含「工作段」「狀態」的表格，列序就是順序；狀態以「已上線／已完成／完成」開頭的算做完；取第一個還沒做完的列。
2. **判斷這段能不能做**：
   - 有設計 spec，或段表內容足以拆成工作單元：拆成工作單元，逐個照 SKILL.md 第 2 節做到合併、部署、驗證。
   - 只有佔位，或被 ⛔ 擋住：照「佔位段與被擋的段」處理。
3. **段做完的收尾**（見下節），寫完累積報告，回到步驟 1。

要使用者拍板的行為類決定，照 SKILL.md 的做法：照推薦做、照常合併、記成主控裁決待確認。不同的是**動手前先推播**這個問題，使用者在場就能早點答，翻盤時要重做的範圍比較小。有 PushNotification 之類的推播工具就用；沒有的話，只寫進累積報告。

## 插手、暫停與接回

- **一般訊息就是插手**：把它當插入的事項，處理完回到 roadmap 繼續，不結束模式。「先停一下這個做法」這類話也算一般插手。
- **改方向**（例：「先做 O2」）：把新順序寫回 roadmap 的列序，照專案的合併方式 commit 進主線，再照新順序繼續。只記在帳本不夠，跨天或 context 壓縮後重讀 roadmap，就會回到舊順序。自己發現順序該調整時不改 roadmap，只寫進報告。
- **暫停**：只認「暫停」「停止自動駕駛」。收到後不再開新的工作單元；手上這個做到合併，或做到分支乾淨的狀態（已 commit、worktree 沒有未提交內容）就停，交累積報告。帳本保留。
- **接回**：使用者說「繼續自動駕駛」，或在額度用盡、session 中斷之後這樣說，就讀同一份帳本，以帳本、roadmap、`git log` 為準接續；已合併的段不重做。帳本路徑寫在累積報告開頭。

## 佔位段與被擋的段

- **佔位段**：沒有設計 spec，內容寫「開工前再切段」之類。不自己設計，也不自己切子段，因為那等於替使用者決定一整塊產品的樣子。在報告「待決」寫「<段> 需要設計」，附設計要問的問題草稿，並推播。
- **被擋的段**：⛔ 等的目標還沒完成。在報告記一筆，說明在等什麼。
- 碰到上面兩種，往後找下一段來做，條件是：沒有 ⛔ 指向擋住的段，它的 spec 也沒寫要用到擋住的段的產出。判斷不了就不跳，寧可提早停，也不要做錯段。找不到可以做的段就結束模式，交累積報告。

## 段做完的收尾

段內所有工作單元都合併後，用一個 commit 同時做兩件事：把 roadmap 該段的狀態改成完成，並在功能清單把該段的項目打勾。有 lifecycle 腳本就跑 `--check`，必須通過。這個 commit 照專案設定的合併方式進主線，專案規定走 PR 的就也開 PR。

## 累積報告

格式照 SKILL.md 第 6 節，差別有三點：

- **每段做完就更新**同一份 `return-report.md`，不等使用者回來才寫。
- **開頭多兩行**：帳本路徑，以及目前進度（第幾段做完、下一段是哪段、停在哪裡）。
- **交出時機**：使用者說暫停、模式結束，或使用者問進度時。
