# 自動駕駛模式

本檔只寫和 SKILL.md 不同的地方；沒寫到的（單元流程、裁決帳本、資源規則、停下條件、異常判讀）一律照 SKILL.md。

自動駕駛＝照專案 `docs/roadmap.md` 的段序一段接一段做，使用者在不在場都一樣，直到使用者說「暫停」或「停止自動駕駛」。

## 開場檢查

依序確認，任一項不成立就不開自動駕駛：

1. **roadmap 存在**：`docs/roadmap.md`（`docs/` 不適用時是根目錄 `ROADMAP.md`）。找不到就說明找不到，請使用者先建 roadmap，不自己編路線。
2. **有合併授權**：`.plugharbor/unattended.md` 的「合併」一節寫明可以**不經人核准**自己合併：fast-forward 推預設分支，或開 PR 後自己 merge。PR 要等人核准的不算。沒有這份檔或沒寫，就趁使用者在場一次一題問完、寫進設定。理由：段要合併進主線才能改狀態、開下一段，沒有合併權的話，後面每一段都會建在還沒合併的分支上。
3. **不成立時**：不開自動駕駛，也不拿 roadmap 當一般無人值守的路線。使用者在場，就說明原因，並問要補設定，還是改由使用者講定工作單元、走一般的無人值守；使用者不在，什麼都不開，只留一份說明原因的報告。
4. 其餘照 SKILL.md 第 0 節。帳本開頭第一行固定寫 `模式＝自動駕駛`，接著記 roadmap 路徑、開跑時的第一個未完成段。接回時靠這一行找帳本。

## 每段的流程

1. **重讀 roadmap 與功能清單**（每段開工前都要讀，使用者或別的 session 可能改過順序）。有 lifecycle 的 `feature_checklist.py`，就跑 `--open` 取「可開工」當主線、「可平行」當平行線候選；沒有就自己讀段表，規則同 lifecycle 的功能清單格式：表頭含「工作段」「狀態」的表格，列序就是順序；狀態以「已上線／已完成／完成」開頭的算做完；取第一個還沒做完、帳本也沒記成「略過」的列。帳本已記為佔位、被擋、停下而略過的段直接跳過，不重寫待決、不重新推播；使用者答了那段的待決或改了 roadmap，才拿掉「略過」。
2. **判斷這段能不能做**：段表那一列連到一份存在的 spec，而且 spec 除了標題還有內容，才算有設計，拆成工作單元，逐個照 SKILL.md 第 2 節做到合併、部署、驗證。其餘一律算佔位，照「佔位段與被擋的段」處理；被 ⛔ 擋住的也一樣。不靠段表那一格的文字自己拆單元。
3. **段做完的收尾**（見下節），寫完累積報告，回到步驟 1。

要使用者拍板的行為類決定，照 SKILL.md 的做法：照推薦做、照常合併、記成主控裁決待確認。不同的是**動手前先推播**這個問題，使用者在場就能早點答，翻盤時要重做的範圍比較小。有 PushNotification 之類的推播工具就用；沒有的話，只寫進累積報告。

## 排線：主線＋最多 1 條平行線

每段收尾、以及丟長工作到背景時，重排一次，不等使用者問「還有什麼可以先做」：

- 主線＝步驟 1 取到的段。平行線從「可平行」（沒有 lifecycle 就自己看主線之後 3 個未完成段裡有設計、沒被 ⛔ 擋的段）依序挑第一個符合的段：有設計、它的計畫列出的共用檔和主線沒有交集（判準見 SKILL.md 第 2 節的空檔表），開在另一個 worktree。挑不到就不開，記理由。
- 同時最多兩條線；兩條線的重測試錯開。平行線做完照常合併，下一次排線時主線若已前進，平行線改成新的主線之後的段。
- `--open` 列出「列序矛盾」時不開平行線去繞過它，寫進報告「待決」並推播。
- 排完把「下一步排線」寫進累積報告並推播，不等回覆就開工：主線是哪段、平行線是哪段與理由（或為什麼沒開）、其餘在等什麼。使用者回訊息改排線，就當插手處理。

## 合批：一條線一次做幾段

相鄰、連到同一份設計、會改同一批檔案的段合成一批，閘門、審查、合併只走一次。

- 候選：roadmap 同一列寫多個段號的（使用者指定一起做），以及 `--open` 的「可合批」（沒有 lifecycle 就自己看緊接主線、連到同一份設計的段）。平行線也照同樣條件，和可平行清單裡相鄰的段合批。寫計畫時確認改同一批檔案才合。
- 上限：含第一段最多 3 段，或預估 diff 約 800 行，先到先停；超過就先合併前面的，剩下的下一批。
- 做法：一個 worktree、一條分支，**每段各自 commit**；審查按段列結果，roadmap 狀態與功能清單照段更新。
- 一段卡住（閘門或審查修兩次還過不了）：在分支上 revert 那段的 commit，其餘重跑閘門後合併；卡住的段放回排程、寫進報告「待決」並推播。
- 排線表寫明每條線這批含哪幾段、為什麼合。

## 插手、暫停與接回

- **一般訊息就是插手**：把它當插入的事項，處理完回到 roadmap 繼續，不結束模式。「先停一下這個做法」這類話也算一般插手。
- **改方向**（例：「先做 O2」）：把新順序寫回 roadmap 的列序，照專案的合併方式 commit 進主線，再照新順序繼續。只記在帳本不夠，跨天或 context 壓縮後重讀 roadmap，就會回到舊順序。自己發現順序該調整時不改 roadmap，只寫進報告。
- **暫停**：只認「暫停」「停止自動駕駛」。收到後不再開新的工作單元；手上這個做到合併，或做到分支乾淨的狀態（已 commit、worktree 沒有未提交內容）就停，交累積報告。如果手上這個是該段最後一個單元，而且已經合併，就把「段做完的收尾」也做完再停，避免 roadmap 和清單不同步。帳本保留。
- **問進度**：交出累積報告就好，不從待決開始逐題問（SKILL.md 第 6 節的逐題問只在暫停或模式結束時做），交完繼續往下跑。
- **接回**：使用者說「繼續自動駕駛」時（含額度用盡、session 中斷之後），在 `.tmp/*/plan.md` 中找第一行是 `模式＝自動駕駛` 的帳本，取最新的一份；有多份或判斷不了，就列出來問使用者。以帳本、roadmap、`git log` 為準接續，已合併的段不重做。某段的單元全部合併了、卻還沒收尾，就先補收尾。

## 佔位段與被擋的段

- **佔位段**：沒有設計 spec，內容寫「開工前再切段」之類。不自己設計，也不自己切子段，因為那等於替使用者決定一整塊產品的樣子。在報告「待決」寫「<段> 需要設計」，附設計要問的問題草稿，並推播。
- **被擋的段**：⛔ 等的目標還沒完成。在報告記一筆，說明在等什麼。
- 兩種都在帳本把該段記成「略過」，附原因。
- 碰到上面兩種，往後找下一段來做，條件是：該段在功能清單的項目沒有 `⛔ 等：<擋住的段號>`，它的 spec 也沒寫要用到擋住的段的產出。判斷不了就不跳，寧可提早停，也不要做錯段。找不到可以做的段就結束模式，交累積報告。

## 段做完的收尾

段內所有工作單元都合併後，用一個 commit 同時做兩件事：把 roadmap 該段的狀態改成完成，並在功能清單把該段的項目打勾。有 lifecycle 腳本就跑 `--check`，必須通過。這個 commit 照專案設定的合併方式進主線，專案規定走 PR 的就也開 PR。

## 換新 session

收尾 commit 進了主線、累積報告與下一步排線寫好後，在 herdr 內（`HERDR_ENV=1`）就換新 session 再開下一段：下一段拿到乾淨的 context 與已安裝的最新版 plugin。不在 herdr 內就不換，直接接下一段。

- **前提**：沒有還在跑的 subagent、背景工作或 pane worker；`/clear` 會讓它們變成孤兒。平行線還在做就這次不換，帳本記 `換新：略過 — <理由>`，下一段收尾再試。
- **先記帳**：帳本寫 `換新：<段> 收尾後`；接回只靠帳本、roadmap、`git log`，沒寫進去的都會丟。
- **啟動**：執行 `nohup sh <本 skill 的 Base directory>/scripts/self-rotate.sh 繼續自動駕駛 <帳本資料夾>/rotate.log >/dev/null 2>&1 &`，然後直接結束這一回合，不再呼叫工具。腳本等這個 pane 閒置後送 `/clear`、`/reload-plugins`、「繼續自動駕駛」，新 context 照「接回」接著做。
- **失敗時**：`rotate.log` 最後一行不是「完成」，session 會停在原地；使用者送「繼續自動駕駛」照常接回。

## 累積報告

格式照 SKILL.md 第 6 節，差別有三點：

- **每段做完就更新**同一份 `return-report.md`，不等使用者回來才寫。
- **開頭多兩行**：帳本路徑，以及目前進度（第幾段做完、主線與平行線各在哪段、停在哪裡）。
- **交出時機**：使用者說暫停、模式結束，或使用者問進度時。
