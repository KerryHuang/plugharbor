# S4 標註：分組、派工與對帳

> 由 `operation-manual` SKILL.md 的 S4 節指向。SKILL.md 保留規則與判準，
> 本檔放推導細節、逐條出處與範例。

## 分組怎麼推導出來

**不要用一個 agent 序列跑完全部截圖**，也**不要照抄固定的分組表**。
每支功能的畫面結構差很多——看板類沒有新增刪除、報表類只有查詢與匯出、
流程類有簽核狀態機——分組必須從**這一支功能的實際截圖需求**推導。

1. **逐張列出前置條件**：拍這張圖之前，畫面要先做什麼？
   （導航到哪個路由、點開哪個對話框、資料要先處於什麼狀態）
2. **把前置路徑相同或相近的歸一組**——同組的圖從同一個畫面狀態出發，
   只需小幅操作就能各自到位
3. **需要寫資料的單獨成組**（新增、刪除、送簽這類會改變資料的）
4. 一組一個 agent，**各自 `new_page` 開自己的分頁**

**判準是「起始狀態」**：跨組要重新導航、或要改變資料才能到位，那就該切開；
同一個狀態下連續拍幾張，那就是同一組。

組數看功能複雜度——簡單的報表可能只有兩組，有完整 CRUD 的主檔可能五、六組。
**組太細會讓每個 agent 都要重新導航登入，反而更慢**，一組少於兩張圖通常不值得切。

> 範例（某主檔功能，**僅供參考不要照抄**）：清單頁一組（主畫面／篩選／
> 欄位設定）、明細與編輯一組、新增流程一組、刪除一組（寫資料，單獨跑）、
> 列印對話框一組。

## 可平行的理由

- 瀏覽器工具都吃 `pageId`／`tabId`，各 agent 開自己的分頁互不干擾
- 共用同一個瀏覽器 profile ⇒ **登入 session 共用，不必重複登入**
- 各組輸出檔名不重疊（`annotation_requests` 已指定產出檔名）

⚠ **會寫資料的組不要跟其他組同時動**——它會改變清單筆數，
其他組可能拍到中間狀態。

## 派工七件事的逐條出處

SKILL.md 有表格；這裡是每一條為什麼在表上。

**第 4 條「各組專用工作目錄」**：三組輸出檔名分得零重疊
（a01–a09／a10–a18／a19–a26），**但三組都在共用 scratchpad 各自建 `gen.py`，
第 1 組靜默覆寫了第 3 組**。分開輸出是直覺會做的事，也正因為做了會產生
「已經處理過撞檔」的錯覺；**中間工作檔會撞，是因為它們不在派工訊息裡，
沒人想到要分**。改分 `g1/`／`g2/`／`g3/` 後，三支同名腳本共存，零復發。

**第 5 條「開場自報工具」**：agent 定義是 session 快照，
寫到一半才發現沒有 `Write`，整棒重派。

**第 6 條「收尾只關自己的分頁」**：
「session 結束時它會自己走」不是收尾方案。曾有 S2a 派工被別的 session
留下的 profile lock 擋掉而重派；`--isolated` 下 Chrome 隨 session 消失，不必再協調 lock。

**第 7 條「帶上上游的環境前提」**：S2a 派工明寫「代碼只能建一次」——
因為建了刪不掉，軟刪會留列。這句沒進 S4 派工，另一組又建了一次，
測試環境因此多留了數筆軟刪列。
**約束寫在上一棒的派工訊息裡，它不會自己走到下一棒。**

## 座標：為什麼這一棒不做量測

三組平行跑出 25／21／17 分，看似分組生效了（先前單一 agent 37 分），
**但三組都在做同一件本來不必做的事**——目測座標 → 疊圖 → 截圖 → 發現框歪 → 重來，
累計 63 分鐘，之後還追加補圖 17 分。

實證：目測提示在 y 838–882、實測 862–912；另一組用等距推算選單列高，
第 4 到第 5 列實際多 1px，第 5 筆露出 1px 字頂。

> **在替一個流程加第三層補救之前，先問這個問題本來需不需要存在。**
> 這裡的答案是不需要——探索時順手記一行矩形，整輪量測就消失了。

## 為什麼改成在 PNG 上疊，而不是回 live 重拍

agent 定義原本寫「回到 live 畫面重做，不要在 PNG 上疊圖」。
後來**三組全部靜默繞過**，各自建了 9 個 HTML 疊圖檔。

繞過是對的——rect 既已前置採集進 inventory，回 live 重現狀態
只剩成本沒有收益。**但因為沒人承認這條路，也就沒人替它配工具**，
於是撞上色彩管理位移：CSS 指定 `#3467A9`、截圖出來是 `(65,102,164)`，
遮罩跟底色差一截，重做約 20 分鐘。而同一個 plugin 裡 `linear-illustrate`
早有參數化的 PIL 標註器——**它重新發明了它**。

> **規範跟實務背離時，先問為什麼被繞過，不要加強制。**

## 遮罩與紅框相交（僅在走備案遮罩時）

> **預設不遮罩**——敏感值在 S2a 截圖前就換成假資料了（見
> [anonymize-before-capture.md](../../../references/anonymize-before-capture.md)）。
> 遮罩只用於 JS 改不到的 canvas／SVG 文字與圖片型內容。本節講的是那些情況。

同一張圖既要遮罩又要標註時，**先算兩組矩形有沒有相交**，再動手。
相交就三選一：把遮罩拆成數塊繞開主角、該欄改填假資料、
或拿掉這個紅框改用文字敘述。

> 案例：三個標註 agent **各撞一次同一個形狀**——
> `render failed` 提示正好落在品名欄上，整片品名遮罩把提示蓋掉；
> 另一張的紅框套在［單價（原幣）］整欄、標籤寫「畫面金額不會跟著變」，
> 而那一欄五格全是灰塊，讀者無從驗證。**紅框指著自己的遮罩。**

同一批圖的遮罩標準要一致——一張遮了單價、另一張明碼，審查會判定標準不一。

> 再一次示範這類傷害：群組名稱遮完，清單只剩一排選項圓圈；
> 卡片中段整片塗白，連欄位標題都沒了。**這就是改用假資料的原因。**
**要遮就整批遮，要露就整批露。**

## caption 對帳：這個缺口是改動自己製造的

caption 是 S3 在標註動手**之前**寫的，句型多半是「紅框處為 X、Y、Z」；
標註棒常有正當理由少框一個（元素當下 disabled、rect 拿不到、與遮罩相交），
**而那句話不會自己跟著改**。

> 案例：7 張 caption 與實際紅框對不上。`manual-reviewer` 第 4 項
> 抓到了，但抓到就是退回——重拍加重審 33 分鐘。
>
> 值得注意的是它的來源：為了解決「框內全是灰塊、讀者無從驗證」，
> 要求 caption 把框的內容寫精確。**caption 寫得越精確，與實際標註的耦合就越緊**，
> 而兩邊之間沒有對帳的人。**補救措施自己會長出新的失效模式。**

## 標籤位置：擁擠的畫面由呼叫端指定

標註棒自選標籤位置時，自檢只會做到「標籤不壓紅框」，**不會問標籤底下原本是什麼**。
框少、四周空曠的圖沒差；一張圖兩個框以上、框彼此相鄰、或框貼近左側清單／工具列時，
標籤幾乎一定蓋到畫面內容。

> 案例：兩組標註棒自選位置——一張的標籤蓋掉左側清單項目、
> 一張整條壓在欄位上、一張蓋住每頁筆數選單。改用 `badge`＋`legend` 又撞上兩件事：
> `annotate.py` 的 legend 行高與圓點不隨字級縮放（已修），以及 **legend 會把圖加高**，
> S6 以整批尺寸不一退件。來回四輪，最後由呼叫端開圖找好空白處、給每個標籤座標，一輪到位。

**做法**：呼叫端收件前（或派工時）先開 clean 截圖，對擁擠的圖逐個標籤給**左上角目標座標**
（CSS px），並寫一句為什麼選那裡（例：「搜尋卡片右半部是空白，不能碰上方的每頁筆數列」）。
標註棒照做，壓到東西才做最小位移並回報。**手冊圖一律貼身標籤，不用 legend。**
