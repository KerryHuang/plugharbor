# S7 gaps 分流：⚡ 當場收掉那四類怎麼收

> 由 `operation-manual` SKILL.md 的 S7 節指向。SKILL.md 有分類表與紅線一句，
> 本檔放執行細節與必須擋下來的情況。

## 「回寫規格」不進清單，當場派 agent 改掉

**那一類不需要任何人決策**——實作是權威，文件錯了，就是事實訂正。
證據此刻最新、最完整，人也還在場。**進了清單就是等它爛掉。**

> 案例：某輪產出的 12 條分流好幾天一條都沒動，下一輪又再產出 26 條。清單本身放在 `.tmp/`——**一個宣告
> 「隨時可以被清掉」的地方**。`linear-create` 有觸發點，其餘去處沒有，於是「產出清單」變成終點。

做法：判為此類的每一條，**派 agent 直接改進規格文件**，並在該文件檔頭 CHANGELOG
補一列（摘要寫「完工回寫：實作對齊」）。可與 S8 平行，不必等。

## 🔴 紅線：文件可以直接改，DB 不行

schema 那類**只准改文件**。校準後若發現設計庫需要加寬，那是 **DDL**，
依專案的 schema 治理規範（如有）要 PO 逐類授權、測試環境先行、正式機逐條明示。
**一律唯讀查證，查完回報，不要自己動。**

同理，「驗證上限跟欄位長度不符」（例如驗證規則限 10 字但欄位是 char(12)）
**不是文件訂正**——放寬驗證是行為變更，留給使用者決定。

## 三個必須擋下來、不可以直接改的情況

| 情況 | 為什麼不能改 |
|---|---|
| 改了規格等於**要求實作改行為** | 那不是訂正文件，是開規格變更。例：規格寫的條件式與團隊既有規範衝突，改規格會讓實作變成 Bug |
| 觀察來自**單一客戶的變體** | 甲客戶看不到的欄位不代表乙客戶也沒有。寫成通則會毒害所有客戶的規格 |
| 該事實**只在一種資料樣態下成立** | 例如「這個分級只有兩色」可能只是這個環境沒有那種資料 |

命中任一條就退回清單，交 PO 或 PM。**派工時要明講這三條，並要求 agent
發現時停下來回報而不是照改。**

## 實跑的分類例子

**小清單例**（8 條）：只有「英文名標紅星號但送出空值不被擋」該開 Bug 票；
FRD 三個欄位語意錯位與長度寫錯屬於規格回寫；「BFS 標 Command 端待建立但實機 CRUD 全可用」
是文件過期；「部門下拉混入客戶／廠商」是資料品質。

**大清單例**（26 條）：6 條直接改規格、5 欄直接改型別記載、3 條直接開票、
6 條丟掉，只剩 11 條需要人決定。**照「一律開票」會開出 23 張錯票。**
其中一條命中第一道閘：BFS 的軟刪條件寫法與團隊既有規範衝突，
改規格會讓現行實作變成 Bug——那是決策不是訂正。
