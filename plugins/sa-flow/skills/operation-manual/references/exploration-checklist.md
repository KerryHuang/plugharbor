# 探索檢查表

`manual-explorer` 走每個畫面時逐項確認。**漏記的東西撰寫者就不能寫**，
所以寧可多記。

## 開工第一件事：接下分支銷帳表

skill 會給一份**規格分支清單**（從 FRD／FFS 抽出的每一個條件分支：空狀態各分支、
權限差異、上限值、狀態相關的訊息）。這張表**逐條銷帳，不准留空**，每條標三態之一：

| 狀態 | 意思 | 要附什麼 |
|---|---|---|
| `已驗證為真` | 造出該條件，看到規格說的行為 | 截圖檔名＋訊息原文 |
| `已驗證為不存在` | 造出該條件，實機沒有那個行為 | 截圖檔名＋實際看到什麼（這是一條 gap） |
| `未驗證` | 沒造出來 | **原因**（造不出資料／權限不足／時間不夠） |

**沒測就寫 `未驗證`，不要留白也不要略過。** 留白會被下游讀成「不存在」，
而「不存在」是一個需要證據才能下的結論。

> 案例：規格明列查詢落差提示有三個分支，探索只走了路由清單、沒測其中「訂單已結案」那支。
> 撰寫者把「證據裡沒有」讀成「不存在」，寫出「查不到資料的**三種**情形」這個窮舉斷言，
> 還教了一條對已結案訂單完全走不到的路徑。審查抓到後退回補測，**多花將近半小時**。
> 更糟的是：DB 證據檔裡明文寫著「已結案資料量大，該分支容易造得出來」——
> **證據裡點名要測，三棒都沒測，也沒人發現沒測。**

**路由清單走完 ≠ 探索完成。** 路由是「頁面有幾個」，分支是「同一個頁面有幾種樣子」，
兩者不能互相替代。

## 順手記座標——後續標註不必回頭量

你現在就站在頁面上，`getBoundingClientRect()` 幾乎零成本；標註棒事後對著 PNG 目測，
既不準又要多跑一輪。**每張截圖存檔前，把該畫面上可能被標註的元素連同 selector
與矩形一起記進 inventory。**

```javascript
() => {
  const pick = sel => Array.from(document.querySelectorAll(sel)).map(el => {
    const r = el.getBoundingClientRect();
    return { text: el.innerText.replace(/\s+/g,' ').trim().slice(0,40), sel,
             x: Math.round(r.x), y: Math.round(r.y),
             w: Math.round(r.width), h: Math.round(r.height) };
  }).filter(o => o.w > 0 && o.h > 0);
  return [].concat(pick('button'), pick('[role=alert]'), pick('thead th'),
                   pick('input, select, textarea'), pick('[class*=banner]'));
}
```

寧可多記——記了沒用到零成本，沒記就是標註棒要重跑一輪畫面。
**提示卡、警示帶、驗證訊息這類會消失的元素尤其要記**，事後未必重現得出來。

## 每個畫面都要記

| 項目 | 為什麼 |
|---|---|
| 進來時的**預設狀態** | 停在哪個頁籤、預設帶了什麼查詢條件、預設值是什麼 |
| **工具列按鈕全文**（含 disabled） | 檢視狀態與編輯狀態不一樣，兩種都要記 |
| **表格完整欄位** | 查 DOM 不要靠捲動猜，畫面窄會截斷 |
| **查詢條件全部欄位** | 含提示文字（placeholder），那常是唯一說明用途的地方 |
| **該有而沒有的功能** | 使用者會一直找。例：訂單沒有刪除按鈕 |

## 互動要展開

- 每個**下拉選單**點開，記錄選項來源與是否可自由輸入
- 每個**頁籤／檢視切換**都切過去，記錄各自的欄位差異
- 每個**開關**撥動看結果
- **列最右側**常有隱藏的操作圖示（複製／刪除／上移／下移），捲到底確認

## 必須走完整流程

**唯讀拍不到手冊最重要的部分。** 至少要走一次：

1. 開新單 → 記錄哪些欄位已有預設值
2. 選主檔（如客戶）→ **記錄哪些欄位自動帶入、值是什麼**
3. 換不同主檔 → 記錄帶入的內容如何隨之改變
4. 選一個**資料不完整的主檔** → 記錄哪些欄位會留白（這是新人最常遇到的狀況）
5. 填明細 → 記錄自動計算的結果
6. 刪一列 → 記錄項次是否重排
7. 送出 → **記錄產生的單號與格式**
8. 必填不填再送一次 → **記錄驗證訊息原文**

建資料前先確認該功能**能不能刪**；不能刪就先問 skill。
品名與備註一律帶「操作手冊示範用」。

## 容易漏的地方

| 漏掉的 | 後果 |
|---|---|
| 列印預覽 | 手冊寫不出「哪些欄位會印給客戶」——那常是最容易誤會的部分 |
| 同名但不同用途的欄位 | 例：表頭「備註」印出來標題變「付款條件」，旁邊的「其他說明」根本不印 |
| 空狀態的**每一種** | 只測到「查無此單號」就以為空狀態只有一種，實際還有「存在但不在條件內」「已結案」 |
| 規格點名、證據檔點名的項目 | 別人已經告訴你哪裡有東西可測，跳過就是白費那份證據 |
| 權限差異 | 沒有金額權限時金額欄顯示「—」而不是 0 |
| 快速新增入口 | 欄位旁的小加號，兩個長一樣但建的東西不同 |

## 與規格比對

skill 會給既有規格（FRD／FFS）的預期行為。**照實記錄兩邊說法到 `gaps.yml`，
不要自行判斷誰對誰錯**——那是 SA 看過證據後才能下的判斷。

常見落差型態：

- 規格寫文字欄位，實機是日期選擇器
- 規格列為 Must 的功能，畫面上根本沒有
- 規格說某欄位自動帶入，實機要手填（或相反）

## 補測時一次只改一個條件

被要求回頭補測某個行為時，**不要照抄呼叫端給的步驟就跑**——先看那組步驟會不會
讓兩個條件同時成立。同時成立就證明不了是誰觸發的，補測等於白做。

> 好例：要驗「每頁 250 筆查詢必失敗」，呼叫端給的步驟同時放寬了日期。
> 補測棒改成：同條件數萬筆選 200 成功／選 250 失敗，再縮到 2 筆選 250 仍失敗、
> 改回 200 成功——四次比對隔離出「與資料量無關，是選單超出後端上限」。
