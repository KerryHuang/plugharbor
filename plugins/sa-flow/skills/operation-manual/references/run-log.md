# 實跑紀錄與經驗

> 由 `operation-manual` SKILL.md 的「時間預算」節指向。
> 判準在 SKILL.md，本檔是它的依據。**每輪收工時從該輪 `.tmp/operation-manual/{功能}/friction.md` 整理一列加在下表**（執行當下記的，不靠回想）。

## 關鍵路徑（每輪一列）

| 輪 | 功能／環境 | S1→S6 通過（分鐘；跨日填累計工時估算） | S6 退回 | 備註（退件根源在哪一棒、S4 拒產張數、工具缺陷） |
|---|---|---|---|---|
| 1 | `<功能>`／`<環境>` | | | |

空檔記「clean run」，沒紀錄記「無紀錄」——不記就看不出趨勢。

## 一輪健康的分佈

S2 探索最長（實機操作本來就慢），S4 標註的**重做時間佔該棒 <20%**，S6 一次通過。
**S6 退回，就是上游漏了東西在下游補。**

> ⚠ S4 的判準是「重做佔比」不是「總時長」。新增「先驗映射」「逐張自檢」這類**刻意要的品質關卡**會讓總時長不降反升；
> **指標訂在總時長，達標的唯一方法就是砍掉自檢。**

## 時間都花在哪：「本來不必跑」比「跑得不夠快」重要

- S4 各組**各自**在跑「目測座標 → 疊圖 → 截圖 → 框歪 → 重來」——解法不是加速，是探索時順手記 rect，整輪量測消失。
- S6 退回補測、補圖、重審——探索漏測一個規格分支，事後補。
- 加派的對帳與追查串在 S3 之後跑，其實可以跟 S3 平行。

平行本身是對的：S2b 藏在 S2a 底下、S5 藏在 S4 底下。

## 好模式（實測有效，值得照做）

- **先驗映射再批次套用**：S4 第 1 分鐘疊一個框、截下來看有沒有套準，擋下錯 rect，成本 1 分鐘、省掉整批重做。
- **上游把陷阱寫給下游**：`annotation_requests` 檔頭寫明座標換算與「fullPage 若有捲動 y 需加 scrollTop」。
- **未驗證要附原因，而且原因可以是「不該驗」**（破壞性／會動到客戶資料）。
- **補測棒自行隔離變因**：呼叫端給的步驟會讓兩個條件同時成立，agent 拒絕照做，改成多次比對，直接隔離出真正的變因。
- **下游不盲從上游的錯誤前提**：探索棒拿畫面＋程式碼雙重證據反駁主 session 的誤判，兩邊說法都寫進 `gaps.yml` 不自行論斷。
- **改完主動列出「形狀相同但性質可能不同」的項目先問再動**，而不是一律照字面處理。
- **過期的約束停下來問**，不自行解除也不死守。
- **執行棒拒絕造假**：選不到目標狀態時拒絕偽造 DOM 狀態，卡住回報並列選項。
- **標註棒不盲套 inventory 的 rect**：欄位內容會改變同一畫面的版面，逐點驗證後改用實測座標。
- **reviewer 對呼叫端的自報同樣查證**；回寫文件的棒先查實作再動筆。
- **簡報先試產再送 S6**：試產抓溢出，併進同一次修訂。
- **收尾的例行查證認真做**：回報軟刪殘留筆數時可能順手撞見更嚴重的缺陷。

## 教訓（按「根源在哪」整理）

### 拿沒驗過的中介物當事實

同一個形狀在一輪內出現多次，每次的中介物都比「直接看一眼」便宜：

| 用的中介物 | 以為它代表 | 實際代表 |
|---|---|---|
| SQL 表 `COUNT(*)` | 畫面上有沒有東西 | 某張不相干的表有幾列 |
| inventory 標「已確認」 | 座標是對的 | 有人宣稱量過 |
| caption 對帳 | 圖文相符 | 兩份文字互相一致（雙方同時說錯就漏） |
| 語意色名（`positive`） | 畫面是綠色 | 框架的分類名稱 |
| 「框內深色像素 0」 | 個資遮掉了 | 框的地方本來就是白的 |

**改進方向不是再加一層檢查，是在關鍵判定上直接看原物**（開圖、裁切、放大）。統計只能輔助，不能當結論。

### 逐格檢查，沒有人看整體

底圖在 S2a 就拍壞了，經 S3、S4、S6 都沒被擋——每一棒都在檢查自己那一格，
**沒有人負責問「這張圖適不適合放進交給客戶的手冊」**。同一個值一處遮一處沒遮也是同一個縫隙。

### 約束與它的成立條件分開傳遞

「平行時禁用 `resize_page`」到重拍時其他組早已收工、限制已不成立，但沒有機制通知執行棒可以解除。
派工的約束寫成「約束｜為什麼｜何時解除」；環境前提（測試資料可建次數等）要帶進下一棒。

### 證據充足但過期，比證據不足更危險

- **本地 checkout 不是畫面真相**：S1 第一件事讀站上 `meta[name=app-version]`，再決定比對哪條 branch，否則分支清單會列出站上已移除的欄位。
- **會毀資料的操作要在派工前查**：S1 列分支清單時，把「哪些操作會寫入或刪除資料」單獨列一份、先查清破壞範圍（例如「產生年度資料」可能是強制重產、先軟刪既有資料）。
- **「能刪」與「刪了會回到原狀」是兩件事**：派 S2a 前讀刪除後的重算邏輯，示範資料挑原本零紀錄的。

### agent 的口頭回報不等於證據

- 任何要被下游引用的實測，一律落進證據包，不要只留在回報裡。「不採信任何自報數字」對呼叫端自己同樣成立。
- 探索棒的結論可能建立在它自己的操作誤解上（例如表格其實是單選，卻記成「勾選多列只刪一筆」的缺陷）——「行為缺陷」等級的結論要附與截圖不矛盾的佐證，下游引用前先開圖。
- 補拍棒收尾自報「全部完成、無遺漏」，實際有圖沒有目標元素、座標指到別處、座標沒寫回 inventory——下游開圖驗收才抓得到。

### 截圖與量座標分開做，而示範資料會被刪掉

先把畫面走完、拍好，事後才補量 `可標註元素`：示範資料收尾刪掉後，**事後沒有任何方法回到同一個畫面狀態去量**。
壞法有四：座標沒記、`於:` 指向別的狀態、視窗尺寸中途漂移、底圖本身撐不起要講的內容（toast 已消失、欄位捲出畫面）。
**修法**：每個畫面狀態「截圖 → 立刻量 → 寫回 inventory」才准走下一個；rect 必須是數字，寫「約」或文字描述＝沒量，量不到就回報。
S2a 收件跑 `check-inventory-rects.py` 機械驗收。

### 個資與「原樣輸出」

- 凡是進 `images/` 的檔案，不論有沒有疊框，落檔的那一棒都要開圖看過個資與 caption——「沒動它」不等於「它是乾淨的」。
- anon 對照表要涵蓋整欄，不是只涵蓋預設頁看得到的（其他篩選態與下拉清單全是真名）；元件的選中值可能存在 `input.value` 屬性，只掃文字節點會漏。
- 圖面 PDF 內嵌姓名 JS 換不到，只能走文字層置換或像素遮罩。

### 自動化操作的陷阱

- 自動化 click 會點穿 fixed 頁尾——而頁尾按鈕按下就送出。**每次 click 前** `scrollIntoView({block:'center'})` → `elementFromPoint` 驗證中心點是目標或其子孫 → 與固定頁尾重疊一律不點；禁用 evaluate 原生 `.click()`。
- `fill('')` 清空可能失效、誤建一筆刪不掉的資料；框架元件的狀態在內部，合成事件改得動 DOM 沒進到元件狀態。
- hover 觸發的浮動選單要 dispatch `mouseenter`；砍框架管理的 DOM 節點會讓框架炸整頁，隱藏改用注入 CSS；3 秒消失的 toast 要在動作前先掛好觀察。
- 共用 debug Chrome 上，subagent 的 `fill`／`click` 可能被權限分類器擋；需要改欄位才能觀察的分支從一開始派主 session。`upload_file` 只有主 session 有。

### 派工措辭與規範背離

- 派工措辭太寬，執行棒會照字面刪掉有證據的事實：「描述了圖上沒有的東西就對齊圖」要寫成「只約束 caption；正文可寫 inventory 已驗證但圖上看不到的事實」。
- 規範跟實務背離時（例如規範寫回 live 重拍、各組卻都改在 PNG 上疊），先問為什麼被繞過、替繞過的路配工具，不要加強制。
- 在替一個流程加第三層補救之前，先問這個問題本來需不需要存在。
- 補救措施自己會長出新的失效模式：caption 寫得越精確，與實際標註的耦合就越緊，兩邊之間要有對帳的人。

### 規格與實機不符時

分支清單讀程式碼得出的行為，實機不符時先查是不是 bug（例如 i18n 字串在 production 丟錯、watch 清掉選取）。
**手冊照實機寫是對的，但不能寫成「設計上」。** 拿程式碼／DOM 的存在當成實機行為是最常見的 S6 退件原因；
**證據強度要與措辭相稱**，補實測解決。

### 跨平台

腳本寫死單一平台的路徑（字型、Chrome 位置）換平台直接失效，第一次在新平台跑要預留時間。
MCP 註冊若是附掛模式，要先有 Chrome 在監聽該 port（見 `browser-setup.md` 的 `--isolated` 標準）。

### 工具缺陷（已修，留作檢查點）

- `build-deck.sh` 的輸出目錄參數必填，產出一律落 `.tmp/`；marp 沒產出新 PDF 時溢出檢查會對舊檔回「通過」，要確認檔案時間。
- `annotate.py` 的 legend 行高須隨字級縮放（DPR 2 要大字級）；字型／編碼不可硬編碼單一平台。
- 平行 session 共用同一個 `.tmp` 目錄會互相覆寫，工作目錄要分。
