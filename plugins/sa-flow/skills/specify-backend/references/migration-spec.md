# Migration 規格指引

## 偵測條件

| 情境 | 是否需要 Migration |
|------|------------------|
| 新增資料表 | ✅ 是 |
| 新增欄位 | ✅ 是 |
| 修改欄位型態 / 長度 / nullable | ✅ 是 |
| 刪除欄位或資料表 | ✅ 是 |
| 純讀取、不改 schema | ❌ 否 |

## 兩層分工

| 層 | 內容 | 誰定 | 落點 |
|----|------|------|------|
| **資料模型契約** | 表、欄位名、型態、長度、可空、預設值、關聯、回填規則、字集 | **SA 定案**，PO 核可；依專案 schema 治理規範與 canonical schema | §M.1／§M.2 |
| **Migration 實作** | DB 先行或 code 先行、migration 工具寫法、索引實作、分批策略、rollback 做法 | **Dev 定**；DB 先行與否牽涉上線風險，由 Dev 提案、PO 拍板 | `decisions.md` TD，§M.3 只留提醒 |

> 為什麼欄位名與型態不留給 Dev：DB 常不是單一應用的私有實作——舊系統可能共用同一張表、多個環境的 schema 要對齊 canonical schema、
> 報表直接讀欄位、治理規則可能限制字集或大型文字型態。這些會被外面看見，屬契約。技術中立指的是實作技術，不是資料模型。
> 程式碼層的 entity／property 命名才是 Dev 的。

## BFS Migration 章節格式

插入位置：**資料模型（§5）之後、API 規格（§6）之前**

```markdown
## §M. Migration 規格

> §M.1／§M.2 是契約（SA 定案）；§M.3 是實作（Dev 定，TD 留置）。實作前必須先完成 Migration，再開發 API。

### M.1 資料模型契約（SA 定案）

| 操作 | 資料表 | 欄位 | 型態／長度 | Nullable | 預設值 | 字集 | 依據 | 說明 |
|------|--------|------|-----------|----------|--------|------|------|------|
| ADD | {Table} | {Column} | {nvarchar(50)}（範例） | YES/NO | {default} | {字集／編碼} | {canonical 現況／最寬環境／舊系統欄} | {說明} |

規則（違反即 dev-readiness 阻塞）：命名依 canonical schema 與既有同表慣例；寬度取各環境最大化聯集、只放寬不縮窄；
專案若有字集／大型文字型態規範（例：舊系統仍在用的表避免 `varchar(max)`）依其規範；型別家族轉換一律先過 PO。

### M.2 資料填補（契約，若適用）

| 目標欄位 | 來源／計算規則 | 影響筆數（實查） | 髒值處理 | 執行時機要求 |
|---------|---------------|-----------------|---------|-------------|
| {欄位} | {來源欄位或公式} | {N 筆，查詢日期} | {→NULL／擋下／PO 裁決} | {上線前一次／可背景} |

### M.3 Migration 實作（Dev 定，TD 留置）

> ⚠ TD-{n}（見 decisions.md）：約束＝{M.1 契約＋上線窗口＋不可鎖表時長}；現況＝{該表既有 migration 慣例}；
> 陷阱＝{例：特定欄位型態不能直接 ALTER、staging 定期還原會覆蓋變更、大量 ALTER 後相依 view 需重整}。
> DB 先行或 code 先行由 Dev 提案、PO 拍板；migration 寫法、索引實作、分批、rollback 做法 Dev 決定。
```

完工回寫：PR 合併後 TD 轉已定案，並同步 canonical schema 與相關對帳文件。

## CR-BFS Migration 章節格式

CR-BFS 中，Migration 章節放在「3. 資料模型變更」之後，內容與上述相同，標題改為「§M. Migration 規格（異動）」，只記錄本次新增的異動，不重複原始 BFS 的 Migration。
