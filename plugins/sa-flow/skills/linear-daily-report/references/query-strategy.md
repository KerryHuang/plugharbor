# 查詢策略與口徑

## 原則

1. **全量，不抽樣**：`hasNextPage` 為真就帶 cursor 續拉。
   只取前 100 筆會讓個人票數與待驗收數都嚴重低估。
2. **大結果落檔**：工具回傳超限時會自動存檔並給路徑，改用 jq／python 讀，
   **不要為了塞進對話而砍欄位重試**。落檔與衍生檔一律放 `.tmp/daily-report/`。
3. **需要標題的清單，故意把 `description` 加進 `fields`** 逼它落檔，再用 jq 砍掉。

## 存量 vs 流量

| 口徑 | 定義 | 用在哪 |
|------|------|-------|
| **流量** | 落在「上一個工作日 ~ 現在」窗內 | 交付、新增、狀態變更 |
| **存量** | 產出當下的全量狀態計數，不受窗限制 | 各段卡住件數 |

兩者混用會得到互相矛盾的數字。報表上分區塊放並標明口徑。

## 必備清單

| key | 定義 | 陷阱 |
|-----|------|------|
| `delivered` | 上一個工作日至今完成，**扣除批次清理** | 這才是真實交付 |
| `cleanup` | 同窗內的批次結案 | 分開列，不然虛胖 |
| `created` | 同窗內新建 | 分頁要拉完 |
| `verify_*` | 等測試／等驗收（全量存量） | 與流量不同口徑 |
| `blocked` | 前端等後端（全量存量；state 名稱用 `list_issue_statuses` 查，不寫死） | 重點是等幾天，不是幾件 |
| `new_urgent` | 窗內新建或升級為 Urgent | 紅燈來源 |
| `unblocked` | 窗內脫離被擋狀態 | 綠燈來源，別漏了好消息 |

## 批次結案偵測

**批次結案偵測（兩個條件都要成立）**：

1. 結案時間相鄰 **≤3 分鐘**聚類，簇大小 **≥5**
2. 該簇的**票齡中位數 > 90 天**

> 兩條都要，缺一不可。只看時間會誤殺——開發者本來就可能三分鐘內連關五張剛做完的票；
> 票齡中位數把「清理陳年票」和「一次交付多張」分開。
>
> 實測：間隔用 60 秒會把同一次清理切斷、漏掉幾張陳年票；放寬到 180 秒後，
> 三個簇的票齡中位數都在 100 天上下，全部確認為清理。

## 客戶歸戶

用 label（客戶 label 的名稱用 `list_issue_labels` 查，不寫死；「通用／全客戶」類 label 另列）。
`project` 欄位覆蓋率通常偏低（實測僅約 37%），不可當歸戶依據。

## 判斷「缺票」

一律另下全量查詢，**不可用時間窗反推**。窗內沒出現只代表今天沒動過。

## 停滯天數

以 `updatedAt` 起算，但先驗證可信度：最後異動日分布中**單日佔比 > 30% 即為批次痕跡**
（實測曾有單日佔近半），該批天數只是下限。
天數一律換算成**工作日**，假日處理見 `${CLAUDE_PLUGIN_ROOT}/references/report-calendar.md`。
