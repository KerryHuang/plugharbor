# 流程回顧與 Plugin 自我進化

> 非 Claude Code（如 Pi）執行時，先讀 `../../references/harness-terms.md`（相對本檔；Claude Code 為 `${CLAUDE_PLUGIN_ROOT}/references/harness-terms.md`，照字面執行可略過），把 Claude 專屬工具與路徑換成對應項。

從**實際跑過的規格鏈**中提取改進機會，讓 plugin 持續進化。

> ⚠️ **這支 skill 自己最容易犯的三個錯，動手前先讀**：
>
> 1. **只看當前 session** → 最有價值的發現往往跨 session、跨規格鏈（同一失敗模式在三條鏈重複，
>    單 session 只看得到一次，會被歸類成「偶發」）。證據來源見 Step 1。
> 2. **不回頭驗上一版** → plugin 進化若只有單向新增、沒有「上次改的實測結果如何」，
>    就會一直在累加規範而不知道哪些沒生效。**Step 0 是本 skill 的第一動作，不可跳過。**
> 3. **按「要改哪個檔」分類** → 那是症狀分類。三次返工分屬三個 skill，照檔案分會變成三條獨立
>    改進項，**永遠看不出它們同一個根因**。Step 2 先歸併根因再分類。

## 輸入參數

```
$ARGUMENTS → [--apply] [skill-name]
```

| 參數 | 必填 | 預設 | 說明 |
|------|------|------|------|
| （無） | 否 | — | 回顧整個 session，產出改進報告 |
| `--apply` | 否 | — | 產出報告後，詢問確認並直接修改 plugin 檔案 |
| `{skill-name}` | 否 | — | 只回顧特定 skill 的使用體驗（可與 `--apply` 合用） |

## 執行流程

### 0. 先驗上一版：改動有沒有生效（**第一動作，不可跳過**）

**plugin 進化必須是閉環。** 每次回顧的第一件事，是回頭驗上一次改了什麼、實測結果如何——
否則只會不斷累加規範，而不知道哪幾條根本沒生效。

1. 讀 `CHANGELOG.md` 最新 1~2 個版本，取出**上次宣稱要解決的問題**與**留下的待驗指標**
2. 若專案有記錄機制（memory、決策日誌），一併查上次留的觀察指標
3. **逐條判定**：生效／未生效／有副作用，**每條都要附本次鏈的具體證據**，不可寫「應該有效」

| 判定 | 意義 | 後續動作 |
|------|------|---------|
| ✅ 生效 | 有具體證據顯示問題不再發生 | 記錄，不再重複改 |
| ❌ 未生效 | 問題照樣發生，或換個形式發生 | **本次的最高優先項**——上次的解法方向錯了 |
| ⚠️ 有副作用 | 問題解了但帶出新問題 | 補防護，不要回退（回退會把省下的也還回去） |

> **為什麼放第一步**：曾有一版為了解「跑一個流程太久」一次做了十一項改動並留下五個觀察指標，
> 但後續回顧沒人回頭驗，直到使用者再問一次「為什麼還是這麼久」，才發現**最大賭注那項賭輸了**
> （驗證從四層砍到一層，結果鏈末缺失暴增）。累加的規範裡有多少是同樣沒生效的，沒人知道。

### 1. 收集證據（**不限於當前 session**）

單一 session 只看得到症狀出現一次。**跨鏈重複才是模式**，而模式才值得改 plugin。

**A. 當前 session**（一定要看）

| 收集項 | 找什麼 |
|--------|--------|
| 調用了哪些 skills、順序 | 使用頻率、銜接是否卡頓 |
| **使用者的修正** | 「不對」「改成」「不是這樣」——skill 指引不明確處。**這是訊號最強的一項** |
| 補充說明 | 使用者額外解釋 skill 沒涵蓋的內容 |
| 流程卡點 | 等待、重試、繞路（該流程有 `friction.md` 就以它為準，不靠回想） |
| 手動調整 | 使用者手改 skill 產出 → 範本或格式要改 |
| 好的模式 | 使用者確認「對」「就是這樣」——值得固化 |
| 意外發現 | 學到的新知識，應納入 skill 或 reference |

**B. 跨 session／跨規格鏈**（找重複模式，**不可省**）——**派 agent 蒐集**

素材量大（CHANGELOG 歷史、多條規格鏈、docs／Linear 產出）且對「歸併根因」無用，
派 `general-purpose`（`model: sonnet`）取結論：

```
subagent_type: "general-purpose"
prompt: |
  蒐集 sa-flow plugin 的跨鏈重複模式證據。**只列證據與出現次數，不做根因判斷。**

  來源五處：① 專案記憶／決策日誌（同一條教訓記兩次以上＝規範沒攔住它）
  ② 近期完成的其他規格鏈（同樣的返工是否也發生過）
  ③ `${CLAUDE_PLUGIN_ROOT}/CHANGELOG.md` 歷史（「修過又復發」＝當初改錯層級）
  ④ docs／Linear 近期產出（交付物是否重複出現同類缺陷）
  ⑤ 各流程執行資料夾的卡點紀錄 `.tmp/*/*/friction.md`（執行當下記的，比回想可信）

  本次要找的主題：{主 session 從 A 項歸納出的候選症狀，逐條列}

  回報格式：每條一列——症狀｜出現次數｜各次的出處（檔案:行號 或 票號）｜
  是否為「修過又復發」。**禁止**貼原文段落，只給定位。
```

<law>
**A 項（當前 session）不可派。** agent 看不到主 session 的對話脈絡——
「使用者說了什麼」「哪一步卡住」「哪次被糾正」只有主 session 知道。
派出去只會拿到一份憑空推測的清單。

派工前先做完 A，把歸納出的**候選症狀**當成 B 的搜尋主題——沒有主題的「找找看有什麼重複模式」會回來一堆雜訊。
</law>

> 判準：**一次是偶發，兩次是巧合，三次是流程缺陷**。只有第三類值得改 plugin——
> 前兩類改了是過度反應，會讓規範越長越沒人讀。

**C. 量化成本**（有就取，沒有不要編）

跑一條鏈實際花的時間、往返次數、返工次數、鏈末驗證抓出的缺失數。
**沒有實際數據時直說「無量化數據」，不要憑印象給數字**——編造的數字會讓後續判斷全錯。

### 2. 根因歸併（**分類之前先做**）

把 Step 1 的所有證據攤開，問一個問題：**這幾件事，是不是同一件事？**

歸併判準——**看「當時為什麼會做錯」，不是「錯在哪個檔案」**：

| 歸併訊號 | 例 |
|---------|---|
| 同一個錯誤動作，發生在不同 skill | 三次都是「照抄既有產出而沒讀範本」，分屬 requirement／specify-backend／linear-create |
| 同一個缺失的檢查點，換不同形式出現 | 契約不一致、欄位對不上、狀態碼不一致——都是「沒有回查上游契約」 |
| 同一個前提被沿用而沒人驗 | 多份文件引用同一個錯誤結論 |

**歸併後才分類。** 三條獨立的 P1 歸併成一條根因後，往往會升級成一條 P0，
而且**解法完全不同**——分開改是三個補丁，歸併改是一條原則。

> 實例：`requirement` 版型錯、`specify-backend` 抄錯結論、`linear-create` 票面格式錯，
> 分開看是三個不同 skill 的小毛病；歸併後是一條「權威來源優先序」原則，一次治三處。

### 3. 分類改進點

將**歸併後的根因**分為五類：

#### 3.1 Skill 內容改進

skill 的指引不夠清楚、步驟有遺漏、或產出品質不符預期。

| 改進項 | 範例 |
|--------|------|
| 步驟遺漏 | 「規格書寫完忘了檢查 X」 |
| 指引模糊 | 「不知道何時該用 A 還是 B」 |
| 產出格式 | 「表格欄位順序不直覺」 |
| 判斷邏輯 | 「模式偵測條件不夠精確」 |

#### 3.2 範本改進

範本的結構、欄位、範例需要更新。

| 改進項 | 範例 |
|--------|------|
| 章節缺失 | 「BFS 範本應多一個 X 章節」 |
| 欄位調整 | 「這個表格應多一欄 Y」 |
| 範例更新 | 「JSON 範例不符實際結構」 |
| 註解補充 | 「撰寫指南應提醒 Z」 |

#### 3.3 Reference 改進

參考文件的知識需要補充或修正。

| 改進項 | 範例 |
|--------|------|
| 知識補充 | 「分析標準應加入 X 檢查項」 |
| 知識修正 | 「Linear workflow 的狀態流轉有誤」 |
| 新增 reference | 「需要一份新的 X 參考文件」 |

#### 3.4 流程改進

skills 之間的銜接、前後順序、前置檢查需要調整。

| 改進項 | 範例 |
|--------|------|
| 銜接斷裂 | 「A skill 完成後不知道下一步」 |
| 前置缺失 | 「B skill 應先檢查 X 是否存在」 |
| 重複工作 | 「C 和 D skill 做了同樣的事」 |
| 順序不當 | 「應先做 E 再做 F」 |

#### 3.5 新增需求

session 中發現需要但 plugin 目前沒有的能力。

| 改進項 | 範例 |
|--------|------|
| 新 skill | 「需要一個專門做 X 的 skill」 |
| 新 reference | 「需要 Y 的標準參考」 |
| 新範本 | 「需要 Z 文件的範本」 |

### 4. 評估影響與優先級

| 優先級 | 條件 | 行動 |
|--------|------|------|
| P0 | 影響正確性（產出有誤）**或上一版判定為 ❌ 未生效** | 立即修復 |
| P0 | **固定成本結構問題**——每條鏈都付、與功能複雜度不成比例 | 立即修復 |
| P1 | 影響效率（流程卡頓、重複工作） | 下次更新修復 |
| P2 | 影響體驗（格式、順序、提示） | 排入待辦 |
| P3 | 新功能建議 | 評估後決定 |

> ⚠ **「固定成本結構問題」必須是 P0，不可歸到 P3「新功能建議」。**
> 它的表徵是「這不算錯，只是有點多餘」，因此極容易被降級——但它**每條鏈都收一次稅**，
> 累積影響遠大於任何單點錯誤。判別方式：問「這個成本，簡單功能付得起嗎？」
>
> 實例：單欄字典與含交易權限的主檔功能走同一條完整規格鏈，前者固定成本佔比極高。
> 它不影響正確性、不是單點卡頓，照舊判準會落到 P3；**但它才是「每個功能都花同樣久」的主因**。

**排序原則**：同為 P0 時，**上一版未生效的項目排最前**——它代表方向判斷錯過一次，
再錯一次的代價是使用者對整套流程失去信任。

### 5. 產出回顧報告

**先判讀再派工**：根因歸併、優先級、版本建議都是主 session 的判斷（Step 2~4 已完成）。
派 `report-writer` 只是把已定案的結論寫成報告：

```
subagent_type: "sa-flow:report-writer"
prompt: |
  report_type: retrospective
  out_path: {workspace 根}/.tmp/retrospective/report-{日期}.md
  template: ${CLAUDE_PLUGIN_ROOT}/skills/retrospective/references/report-template.md
  dataset: {Step 2~4 結論的彙整檔絕對路徑}
  constraints: |
    **開頭先給一句結論＋三個數字**（例：「上一版兩項未生效；本次 3 個根因、
      P0 4 項、待驗指標 6 條」）
    **全文 ≤1500 字**——證據與量測細節放附檔，不塞進正文
    根因、優先級、版本建議由呼叫端判定，**不得自行改判**
    「本次的待驗指標」必填且**判準須可觀察**——那是下次 Step 0 的輸入
    無量化數據時直說「無量化數據」，**不要憑印象給數字**
  siblings: 無
```

章節順序：上一版驗證（Step 0）→ 根因歸併（Step 2）→ 改進摘要表 →
詳細發現（P0～P3）→ 值得固化的好模式 → **本次的待驗指標** → 版本建議。

### 6. 執行修改（--apply 模式）

僅在使用者指定 `--apply` 時執行。

**修改前**，使用 `AskUserQuestion` 列出即將修改的項目，等待確認：

```
以下 P0/P1 項目將被直接修改，確認執行？

P0：
- [skill-name] SKILL.md：{描述}

P1：
- [reference-name].md：{描述}

P2/P3 項目不修改，僅列入報告。
輸入 y 繼續，或指定要跳過的項目編號：
```

**改法的優先序：刪 → 改寫既有句 → 新增。** 每項先問「刪掉哪句能解決」，再問「改哪一句」，兩者都不行才新增，
並在報告寫明為何刪與改都不夠——只加不刪的規範會越長越沒人讀。改完對動到的段落做**逐句 no-op 測試**：
拿掉這句，執行者的行為會不會變？不會就刪。回報每個動到的檔案行數前後（例：299 → 281）。

確認後依 [references/apply-changes.md](references/apply-changes.md) 執行：P0／P1 直接改、P2／P3 只列報告；**版號不要自己改**（交該 repo 既有的版號同步機制，所有版號位置同步、級距依變更性質）；跑 `claude plugin validate .`；驗證新增檔案引用路徑；同批更新 `CHANGELOG.md`（格式見該檔「進化追蹤」）。

## 收尾條件

全部成立才算完成（見 `${CLAUDE_PLUGIN_ROOT}/references/dispatch-conventions.md` §八）：

1. Step 0 上一版驗證已做——**這是第一動作，跳過就無從判斷改動有沒有效**
2. 報告已寫入 `.tmp/retrospective/`，正文 ≤1500 字，證據附檔留在同目錄
3. **「本次的待驗指標」已填實且判準可觀察**——那是下次 Step 0 的唯一輸入
4. `--apply` 模式：改動已套用且逐項列出改了哪些檔；未套用的說明原因

## 錯誤處理

| 錯誤情境 | 處理方式 |
|---------|---------|
| 當前 session 無 skill 使用記錄 | **不終止**——改走 Step 1-B 的跨 session 證據（記憶、CHANGELOG、近期規格鏈產出）。使用者問「檢討流程」時，往往正是在一個沒跑 skill 的 session 裡問的；此時終止等於這支 skill 永遠用不到 |
| 完全無任何證據來源 | 才終止，並說明查了哪些來源都是空的 |
| 指定的 `{skill-name}` 不存在 | 列出可用 skill 名稱，終止 |
| `claude plugin validate .` 失敗 | 顯示錯誤，回滾該項修改，繼續處理其他項 |
| 找不到版號同步機制 | 依該 repo 的 `CLAUDE.md` 規範手動同步全部位置，**並在報告中標明改了哪幾處供覆核** |

### 7. 進化追蹤

在 plugin 根目錄維護 `CHANGELOG.md`，記錄每次回顧驅動的變更：

```markdown
## [{version}] - {YYYY-MM-DD}

### 來源
- Session 回顧

### 變更
- **{skill-name}**: {改進描述}
- **{template-name}**: {改進描述}

### 觸發證據
- {簡述使用者的回饋或發現的問題}
```
