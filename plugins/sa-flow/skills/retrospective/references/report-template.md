# 回顧報告格式

> 由 SKILL.md Step 5 指向。報告開頭先一句結論＋三個數字，全文 ≤1500 字，細節放附檔。

```markdown
# 流程回顧報告

**日期**：{YYYY-MM-DD}
**回顧範圍**：{本次涵蓋哪些規格鏈／session，不只寫「當前 session」}
**使用的 Skills**：{列表}
**Plugin 版本**：{version}

## 上一版驗證（Step 0）

| 上次的觀察指標 | 判定 | 本次證據 |
|---------------|------|---------|
| {指標} | ✅／❌／⚠️ | {具體證據，不可寫「應該有效」} |

> ❌ 未生效項是本次的最高優先——列在 P0 最前面。

## 根因歸併（Step 2）

| 根因 | 表徵（分屬哪些 skill／哪幾次） | 出現次數 |
|------|---------------------------|---------|
| {一句話講清楚「當時為什麼會做錯」} | {症狀 A（skill X）／症狀 B（skill Y）} | {N} |

> 只列出現 **≥3 次**者為流程缺陷；1~2 次列入觀察不改 plugin。

## 改進摘要

| 類別 | P0 | P1 | P2 | P3 | 合計 |
|------|----|----|----|----|------|
| Skill 內容 | | | | | |
| 範本 | | | | | |
| Reference | | | | | |
| 流程 | | | | | |
| 新增需求 | | | | | |

## 詳細發現

### P0 — 立即修復
{每項列出：問題、證據（對話中的具體片段）、修復方案、動作（刪／改／增；增要寫明為何刪與改都不夠）}

### P1 — 下次更新
{同上}

### P2 — 排入待辦
{同上}

### P3 — 新功能建議
{同上}

## 值得固化的好模式
{這次效果好的做法，應寫入 skill 或 reference}

## 本次的待驗指標（**必填——下次回顧的 Step 0 輸入**）

| 指標 | 判準 | 不如預期時 |
|------|------|-----------|
| {改動 N 是否生效} | {怎樣算生效，要可觀察} | {回退還是換方向} |

> **沒有待驗指標的改動＝沒有下次驗證的依據。** 每項 P0／P1 改動都要有對應指標，
> 且判準必須可觀察（「鏈末缺失數是否下降」可觀察，「品質是否提升」不可）。
> 同時寫進 `CHANGELOG.md`，並在專案記憶／決策日誌留一份。

## 版本建議
- 當前版本：{version}
- 建議版本：{新版本號}（**依變更性質判級距**：改流程結構或新增 reference＝minor）
- 變更摘要：{一句話說明}
```
