# FRD 撰寫派工樣板

`requirement` Step 8 的 `spec-writer` 派工 prompt。
派工**前**必須完成 Step 5 內容規劃、6 PM 加值、6.7 決策落檔、7 疑問點清查。

`{}` 為呼叫端填入值；所有路徑一律展開成**絕對路徑**。

```
subagent_type: "sa-flow:spec-writer"
prompt: |
  doc_type: FRD
  out_path: {功能目錄}/{功能名稱}_需求文件.md
  template: ${CLAUDE_PLUGIN_ROOT}/templates/frd.md
  boundary_row: {spec-dedup-and-budget.md「各文件套用值」表的 **FRD 欄**（表頭是 `項目｜FRD｜SAD｜BFS｜FFS`，要抽的是那一**欄**跨全部項目列）}
  evidence:
    - {功能目錄}/{功能名稱}_探索摘要.md        # 六維收斂結果（若有）
    - {功能目錄}/{功能名稱}_prototype.html     # §0.5 對焦素材的「已定案」清單（若有）
    - {功能目錄}/analysis/background-scan.yml  # A 路：既有實作與舊系統
    - {功能目錄}/analysis/db-analysis.yml      # B 路：欄位型別（若有）
    - {功能目錄}/analysis/ui-survey.md         # C 路：現有畫面（若有）
    - {功能目錄}/analysis/consultant-notes.md  # 顧問桌裁示（若有）
  decisions: {功能目錄}/decisions.md ＋ 本階段編號 {D-0xx…}
  feature: {功能名稱}／{模組}／{功能目錄}
  brief: |
    §1.1.1 需求來源與證據強度表：{來源／親口提及／confirmed・PO 轉述・推論／出處}
    §2.1 使用者故事清單（MoSCoW 排序，**角色欄必填**，US-XX 是全鏈追溯鍵）：{清單}
    §2.2 只展開 Must：驗收條件（Given-When-Then，**直接代入數字**）
    §3 業務流程圖（必畫）；有狀態機時 §3.2 狀態圖（必畫）
    §4 畫面設計**只寫業務層**：畫面清單（SCR-XX ＋ 業務目的）、操作表、
      **業務層有話要說的欄位**、原型連結（若有）。**不列完整四類欄位群**（owner 是 FFS §2）
    §5.1 只列輸入欄位與有業務規則的欄位（純顯示衍生欄不列）
    §5.3 業務規則：{清單}。**公式／比率／分攤／遮罩／優先序類 BR 必附算例**
      （數值型給數字；**條件判定型給條件組合→結果**，不要假設一定是算術）
    §6 非功能性需求：{有效能／安全性等特殊要求時填，無則精簡}
    §7 驗收標準：一段說明（業務驗收＝§2 AC；TC owner 為 QA 票／BFS §12／FFS §8）
      ＋ §7.2 非功能驗收短表。**不列 TC**
    §8 附錄：術語表（每個 domain 詞附實例）、外部參考文件、開放議題
    Step 6 PM 加值的結論：{隱含需求、偏離項、風險表}
    去重判準：不同視角的圖不算重複
  mode: new
  extra_checks: |
    BDD｜每條關鍵 BR 至少推導一個正例＋一個反例，落入對應 US 的驗收條件分支（§2.2 AC-n）；
       **不允許只有規則敘述而無具體例子的 BR**｜逐條 BR 檢查對應 AC 是否含正反例
    INF｜推導出的隱含業務規則必須標 `[推論]` 並說明依據；
       **未經確認的推論不得寫成既定規則**｜grep -n '\[推論\]' 對照 §5.3
    NUM｜§2 驗收條件**直接代入數字**，不寫「數量超過上限時」這種抽象敘述｜
       抽查 AC 是否含具體數值
```

## `mode: change`（CR-FRD）補充

`--change` 模式改為 in-place 更新主文件，另需傳：

```
  mode: change
  main_doc: {既有 FRD 絕對路徑}
  ticket: {票號}
  change_scope: |
    變更類型：{新增使用者故事／修改業務規則／調整欄位規格／混合}
    影響章節：{逐項}
    **修訂是取代不是追加**——被改寫的舊敘述必刪，不留兩個版本並存
```

若功能目錄存在 `features/*.feature`，更新 §2.2 後依
`${CLAUDE_PLUGIN_ROOT}/skills/requirement/references/bdd-feature-guide.md`「CR 同步」節
**整檔覆蓋重轉譯**（不做差異式手改）——這一步由主 session 在 agent 回報後執行。

## ⚠ 派工前必做：確認引用的章節實際存在

<law>
**章號是變數不是常數。** 每份上游文件的章節編號都不同——實測：
某份 BFS 的 **§6 是「排程／背景作業」而 API 在 §5**、**§7 是「讀寫元件規劃」而非驗證規則**；
某份 SAD **根本沒有 §6.6**，全文也找不到 B1~B13 那套邊界編號。

照樣板字面填「ref BFS §7 同編號 VR」，agent 會 ref 到錯的章；
指向不存在的章節，它**既無法對照也無法回報未落實**——只能自己猜，那正是派工要避免的。
</law>

派工前逐項驗：

```bash
grep -n "^## " {BFS 絕對路徑}    # API 章、驗證規則章的實際編號
grep -n "^## " {SAD 絕對路徑}    # 邊界清單章是否存在
grep -n "^## " {FRD 絕對路徑}    # 畫面設計章、業務規則章
```

**brief 裡一律寫「語意 ＋ 實際章號」**：

- ✅ `ref BFS 的驗證規則章（本份為 §4.3 PR-01~PR-06）`
- ❌ `ref BFS §7 同編號 VR`

**另外掃一次編號引用**（避免改編號讓既有交叉引用靜默斷掉）：

```bash
grep -rn "FFS-TC-\|BFS-VR-\|FRD-BR-\|-TC-[0-9]\|-VR-[0-9]" {功能目錄}
```

同目錄有文件引用了本文件的編號 → **brief 裡明說用哪一套**（遷就既有，不要照範本另起）。

**引用的章節不存在時**：不要照樣板填。改寫成實際可依循的指示
（如「本功能 SAD 無邊界清單章，§4 依 FRD §5.2 VR 落實」），或先補做該分析再派工。
