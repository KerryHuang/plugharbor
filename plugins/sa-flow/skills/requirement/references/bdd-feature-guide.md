# BDD .feature 產出規範

> 由 `sa-flow:requirement` Step 9.5（標準模式）與 Step A4（調整模式）引用。
> 本規範預設專案**無任何 BDD 執行工具鏈**（無 Cucumber / SpecFlow / Reqnroll），
> .feature 是**純溝通產物**，不會被自動執行。
> 其價值在：QA/PO 以情境敘事閱讀、QA 票 TC 直接引用場景、未來可無痛接工具。

## 一、權威關係（最重要，防漂移的根）

- **FRD §2.2 的 Given-When-Then 驗收條件表格 = 唯一事實來源**，維持既有表格格式不變。
- .feature 是 FRD §2.2 的**機械轉譯**：同一 AC 編號、同一 Given/When/Then 文字，只換 Gherkin 語法包裝。
- **禁止**在 .feature 新增 FRD 沒有的分支或改寫語意——發現 FRD 缺分支時，回頭改 FRD（走 CR 流程），再重轉譯。
- 同步方向永遠單向：**FRD → .feature**。

## 二、產出條件（不是每個功能都要）

| 條件 | 產出 |
|------|------|
| US 含業務規則分支（一條 BR 多種結果）或狀態轉換 | ✅ 建議產出 |
| 純 CRUD 查詢、單一 AC、無 BR/VR 分支 | ❌ 豁免（Gherkin 版只是表格轉文字，零邊際價值） |

> 屬**可選收尾產出**（AskUserQuestion 詢問），不是必要步驟。試點心態：若 QA 撰寫 TC 未因它變快變準，應廢棄此產出而非硬撐。

## 三、檔案位置與命名

```
{docs-root}/{模組名稱}/{功能名稱}/features/{功能名稱}.feature
```

- **一個功能一個 .feature 檔**（與 FRD 一檔對一功能的慣例對齊），功能內所有 US 是同一 Feature 下的多個場景；**不要**每個 US 拆一檔。
- 範例：`{docs-root}/訂單/訂單管理/features/訂單管理.feature`

## 四、語言：`# language: zh-TW` 全中文關鍵字

讀者是 PO/客戶/QA（專案文件慣用繁中）。Gherkin 官方 zh-TW 關鍵字：
`功能`、`規則`、`場景`、`場景大綱`、`例子`、`假設`、`當`、`那麼`、`並且`、`但是`、`背景`。
未來若接 SpecFlow/Reqnroll/Cucumber.js，三者皆原生支援 zh-TW locale，不構成相容障礙。

## 五、結構對應（FRD 編號 ↔ Gherkin）

| FRD | Gherkin | 說明 |
|-----|---------|------|
| 整份 FRD（功能） | `功能:` | 一檔一功能 |
| BR-xxx（橫跨多場景的業務規則） | `規則:`（標題含 BR 編號） | 規則只示範單一 US 時可省略 `規則:` 層 |
| US-xx 的每個 AC 分支 | `場景:`（名稱前綴 AC 編號） | 場景名 = `AC-n {分支情境}` |
| VR-xxx 同構重複驗證（格式/長度/範圍/唯一性） | `場景大綱:` + `例子:` 表格 | **僅限**同一邏輯、純數值/狀態列舉不同時使用 |

> **場景大綱使用紀律**：「查無 / 已存在 / 正常」這類**語意迥異**的分支必須是獨立場景，
> 不得硬塞進例子表格——會稀釋分支意圖，PO/QA 難以閱讀比較。

## 六、追溯 tag

每個場景掛 FRD 編號 tag，純文字 grep 即可雙向定位（符合目前無工具的現實）：

- 檔案層：`@FRD-{模組代號}-{序號}`
- 場景層：`@US-xx`（必掛）＋ `@BR-xxx` / `@VR-xxx`（該場景示範的規則）

QA 票 TC 引用格式：`見 {功能名稱}.feature :: AC-2`。

## 七、完整範例

```gherkin
# language: zh-TW
@FRD-ORD-001
功能: 訂單建立與出貨
  身為業務人員，我想要建立訂單並安排出貨，以便加速接單流程

  規則: 已核准訂單不可再編輯明細 (BR-001)

    @US-01 @BR-001
    場景: AC-1 正常情境 - 草稿狀態可編輯
      假設 訂單狀態為「草稿」
      當 業務人員修改訂單明細
      那麼 系統允許儲存變更

    @US-01 @BR-001
    場景: AC-2 已核准訂單編輯遭阻擋
      假設 訂單狀態為「已核准」
      當 業務人員嘗試修改訂單明細
      那麼 系統顯示錯誤訊息「已核准訂單不可編輯」
      並且 明細不被寫入

  規則: 訂單編號重複驗證 (VR-005)

    @US-02 @VR-005
    場景大綱: 唯一性驗證 - 不同重複情境一致擋下
      假設 系統中已存在訂單編號 "<既有編號>"
      當 使用者輸入訂單編號 "<輸入值>"
      那麼 系統顯示錯誤訊息「訂單編號已存在，請重新輸入」

      例子:
        | 既有編號   | 輸入值     |
        | SO-0001   | SO-0001   |
        | SO-0002A  | so-0002a  |
```

## 八、CR 同步（調整模式）

FRD §2.2 因 CR 更新後：**整檔覆蓋重轉譯**（從更新後的 FRD §2.2 重新機械轉譯、覆蓋既有 .feature），
**不做差異式手改**——覆蓋式轉譯比人工 diff 更不易漏改漂移。

## 九、漂移防治

`sa-flow:verifying-specs`（--cross 模式）檢核：若功能目錄存在 `features/*.feature`，
其場景 AC 編號集合必須與 FRD §2.2 AC 編號集合**一一對應（無多無少）**，不一致 = CRITICAL，
處置方式一律「依 FRD 重新機械轉譯」（不得反向改 FRD 遷就 .feature）。
