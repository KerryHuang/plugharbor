# 指標定義與禁用指標

## 清單即真相

每個統計數字都必須是某張清單的 `len()`。建 drill dataset 時同時記下 key，
組報表時**用 `len(items)` 插值，不要另外算一次**。

發布前用 `scripts/verify_counts.py` 強制檢查，非零 exit code 即不得發布。

## 必備清單

| key | 定義 | 陷阱 |
|-----|------|------|
| `delivered` | `completedAt` 落在上週窗內，**扣除批次結案** | 這才是產能 |
| `cleanup` | 上週窗內的批次結案（見下） | 與產能分開，不然虛胖 |
| `created` | `createdAt` 落在上週窗內 | 分頁要拉完，漏頁會少算 |
| `testing` / `readyqa` | 全量狀態計數（非窗內） | 存量與流量不同口徑，要標明 |
| `blocked` | 前端等後端的狀態（state 名稱用 `list_issue_statuses` 查，不寫死） | 停滯天數是重點，不是張數 |
| `req` | 需求／規格中（PM team 進行中） | 含大量陳年掛單，要講明 |
| `overdue` / `dueweek` | 有期限、**且未完成** | 含已完成會虛報（實測 75 vs 37） |
| `lead_*` | 流動時間分桶，**只算 `delivered`** | 含 cleanup 會製造假長尾 |
| `wip_*` / `del_*` | 依客戶標籤的在手／交付 | 同一刻度畫圖才誠實 |
| `case_*` | 各案子的所有在跑工作 | 案子用標籤或功能代碼比對 |

## 批次結案的偵測

判準與閾值寫在 SKILL.md Step 3。這裡只記兩個踩過的坑：

> **間隔不能用 1 分鐘**——實測一次清理橫跨約三分鐘，60 秒會把它切成
> 兩段、其中一段不足 5 張而漏判，幾張陳年票因此被算成當日產能。放寬到 180 秒解決。
>
> **不能只用「lead time > 30 天」**——會漏掉簇內剛開的票（實測：某張票建立 11 天後
> 隨簇結案，lead 很短，但它確實是清理）。所以用**簇的票齡中位數**而非逐票判定。

## 衍生指標

| 指標 | 算法 | 呈現 |
|------|------|------|
| 淨變化 | `len(created) − len(delivered) − len(cleanup)` | 正值＝積壓惡化 |
| 產能 vs 需求 | 依客戶標籤分群，交付 vs 在手 | **左右同一刻度**，比值愈大愈危險 |
| 開發段耗時 | `completedAt − createdAt`，只算 `delivered` | 中位數＋分桶 |
| 驗收段停滯 | `now − updatedAt`，算 `testing`＋`readyqa` | 中位數＋「停超過兩個月」張數 |

開發段與驗收段**要放在一起對照**——這對照本身就是結論
（實測：交付中位數數天，驗收段停滯中位數卻達兩個月）。

## 禁用指標

| 指標 | 為什麼不用 |
|------|-----------|
| **Cycle 完成率** | Cycle 若被當成全票容器而非 sprint 承諾，完成率永遠偏低，無資訊量 |
| **工時／故事點** | `estimate` 覆蓋率通常偏低且格式不一致。畫出來很專業但數字是編的，被追問一句就垮 |
| **人員票數排名** | 票數 ≠ 工作量，且會議上點名會變成防禦性辯論、吃掉決策時間。改報「哪一棒缺人」 |

工時覆蓋率低這件事**本身**要進「臨時動議」——是待決事項，不是可跳過的缺陷。
