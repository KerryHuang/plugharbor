## Assignee 與狀態預設值

### 初始狀態決策（★ 依「分析階段 + 建立範圍」）

初始 workflow state **不是固定值**，由三個維度決定：**(1) Feature / Bug**、**(2) 需求分析是否已完成**（Step 4.4 詢問）、**(3) 本次建立範圍**（Step 4.5：單票 / 開 SA 分析 / 建 Dev 樹 / 一次建齊）。前端另看**有無對應後端票**。

**狀態語意**（名稱為語意名稱；實際 state 一律用 `list_issue_statuses` 查該 team 有的，沒有同名者選語意最近的，如 `In Refinement` 無則 `Backlog`、`Testing` 無則 `In Review`）：

| 狀態 | 語意 | 適用 |
|------|------|------|
| `Backlog` | 未啟動 / parked（尚未輪到或未分析） | 全部 |
| `In Refinement` | PM 需求分析中（已開 SA 在分析） | PM |
| `In Progress` | 分析完成、Dev 可進行 | PM |
| `Todo` | 可開工 | SA（分析）、QA、BE、FE |
| `Blocked By BE` | 前端等後端完成（Dev team 自訂 state，無則 `Todo`） | FE |

**Feature 情境對照**：

| 情境 | PM | SA | QA | BE | FE |
|------|----|----|----|----|----|
| 單開任一票（無子票、不往下） | Backlog | Backlog | Backlog | Backlog | Backlog |
| 建完整樹・**未分析**・選擇開 SA 分析 | In Refinement | Todo | Backlog | Backlog | Backlog |
| 建完整樹・**未分析**・不開 SA（整棵 parked） | Backlog | — | Backlog | Backlog | Backlog |
| 只有 PM・**未分析**・決定開 SA 分析 | In Refinement | Todo | — | — | — |
| 建 Dev 樹・**分析已完成**（不開 SA）※ | In Progress † | — | Todo | Todo | Todo / BBE |

> ※ 涵蓋三種：從零已分析建完整樹、只有 PM 已分析再建 Dev、完整樹已存在開工。分析已完成代表「已在 PM 票內完成」，故**不另開 SA 票**。
> † PM 票**若已存在則更新**其既有狀態為 `In Progress`（非新建）；若同批新建 PM 也直接給 `In Progress`。

**Bug 情境對照**（無分析階段，直接可開工；驗收人＝根票開票人）：

| 情境 | QA | BE | FE |
|------|----|----|----|
| 建 Bug 樹（新建 QA 根票 + Dev） | Todo | Todo | Todo / BBE |
| 既有 PM Bug 根票 → 直接掛 Dev（不補 QA） | —（不新建） | Todo | Todo / BBE |
| 單開某一票 | Backlog | Backlog | Backlog |

> **PM 根票變體**：PM 已自行開 Bug 根票時，Dev 票 parentId = 該 PM 票；PM 根票的內容、assignee、state 均不調整（驗收由 PM 做，最後一個 Dev 票關票時 @PM 並將 PM 根票 → Testing）。

> **FE 判斷（BBE = Blocked By BE）**：表中 `Todo / BBE` 依 SKILL.md Step 8.5 第 1 條決定；ID 偵測見 §Blocked By BE ID。
>
> **核心邏輯一句話**：單開 / 未分析 parked → `Backlog`；未分析要往下 → 開 SA 分析（PM `In Refinement`、SA `Todo`，Dev parked）；**分析完成**建 Dev → PM `In Progress`、Dev = `Todo`/`BBE` 可開工；**Bug** 無分析階段，下游直接可開工。
>
> **Assignee**：PM/QA(Bug)=`"me"`，SA/BE/FE=下列佔位符（見 \*）。
> \* 佔位符未替換為實際 user id 時，linear-create 於 Step 5.5「Assignee 解析」呼叫 `list_users` 取該 Team 成員讓使用者選；`list_users` 失敗則 fallback `"me"` 並於報告標註需手動指派。

### 重要：狀態指定方式

Linear MCP 用名稱匹配狀態時，同 type 的多個狀態可能導致匹配錯誤（如 `Backlog` 被匹配到同為 backlog type 的其他狀態）。

**必須使用狀態 ID 指定**，避免名稱匹配歧義：

> **注意**：以下狀態 ID 需依實際 Linear 環境替換。

| 團隊 | Backlog ID | In Refinement ID | Todo ID | In Progress ID | In Review ID | Testing ID | Done ID |
|------|-----------|------------------|---------|----------------|-------------|-----------|---------|
| `{PM_team}` | `{PM_team_backlog_id}` | `{PM_team_in_refinement_id}` | `{PM_team_todo_id}` | `{PM_team_inprogress_id}` | — | `{PM_team_testing_id}` | `{PM_team_done_id}` |
| `{SA_team}` | `{SA_team_backlog_id}` | — | `{SA_team_todo_id}` | `{SA_team_inprogress_id}` | — | — | `{SA_team_done_id}` |
| `{QA_team}` | `{QA_team_backlog_id}` | — | `{QA_team_todo_id}` | — | — | `{QA_team_testing_id}` | `{QA_team_done_id}` |
| `{Dev_team}` | `{Dev_team_backlog_id}` | — | `{Dev_team_todo_id}` | `{Dev_team_inprogress_id}` | `{Dev_team_inreview_id}` | — | `{Dev_team_done_id}` |

> `In Refinement`（PM 需求分析中）、`In Progress`（PM 分析完成、Dev 可進行）為 PM 分析階段用狀態；需依實際 Linear 環境替換 ID。

#### Blocked By BE ID（Dev team，前端票等後端時用）

| 團隊 | Blocked By BE ID |
|------|-----------------|
| `{Dev_team}` | `{Dev_team_blocked_by_be_id}`（未設定或該 state 不存在時 → 改用 `{Dev_team_todo_id}`） |

> `Blocked By BE` 是 Dev team 自訂的 workflow state（非全 team 皆有）。安裝後若該 team 無此 state，`{Dev_team_blocked_by_be_id}` 仍為佔位符；linear-create 於建票前以 `list_issue_statuses` 動態偵測，找不到即 fallback 為 Todo。

## Due date（SLA）預設規則

依「優先級 → 完成天數」SLA 自動帶入 `dueDate`，**僅套用 Dev 子票（前端/後端）與 Bug 樹的 QA 票**；其餘票種不設 Due date。天數為預設建議值，各團隊可依自己的歷史完成時間調整。

### 適用範圍

| 票種 | 設 Due date | 基準 |
|------|:---:|------|
| Dev 後端票 / 前端票（Feature 與 Bug 皆適用） | ✅ | 下表「Dev 子票」天數 |
| QA 票（**Bug** 樹） | ✅ | Dev 子票天數 **+ 1 天**（QA 在 Dev 之後驗證） |
| PM 票（Feature） | ❌ | 走 Cycle / Milestone 規劃，不套 SLA |
| SA 票（Feature） | ❌ | 同上 |
| QA 票（**Feature** 樹） | ❌ | 同上 |

### SLA 天數（自建票當日起算，日曆天）

> 此處「Normal」= Linear `priority=3`（Medium）。

| 優先級 | Dev 子票 | QA Bug 票（Dev + 1） |
|--------|:---:|:---:|
| Urgent | +3 天 | +4 天 |
| High | +5 天 | +6 天 |
| Normal（Medium） | +10 天 | +11 天 |
| Low | 不設 | 不設 |
| 無優先級（None） | 不設 | 不設 |

### 計算與帶入方式

- `dueDate = 建票當日 + N 個日曆天`，以 `save_issue` 的 `dueDate` 參數（ISO `YYYY-MM-DD`）帶入。
- Low / 無優先級**不帶** `dueDate` 參數。
- 不適用範圍的票種（PM / SA / Feature 樹 QA）**不帶** `dueDate`。
- 「一次建齊」模式下 Dev / QA 票即使初始為 Backlog，仍依本表帶 `dueDate`（SLA 從建票日起算，與啟動時機無關）。

## Estimate（Story Points）預設規則

**僅套用 Dev 子票（後端／前端）**，由 AI 依規格內容自動判定後帶入 `save_issue` 的 `estimate`，**不詢問使用者**。PM / SA / QA 票一律不帶——那是流程票，估了會讓 cycle velocity 失真。

尺規為 Fibonacci `1 / 2 / 3 / 5 / 8 / 13 / 21`。**不使用 0**（多數團隊未開放零估點，且「不需開發」的票本就不該開）。前後端各自估自己的票，不共用同一個點數。

### 判定基準

以「該票自己要做的事」為準：後端看端點／DB／商業規則，前端看畫面／欄位／狀態。取**最高符合**的一列。

| 點數 | 後端票 | 前端票 |
|:---:|------|------|
| 1 | 單處常數／設定／文案調整，無 DB 異動、無契約變更 | 單一欄位顯示或文案調整，無 API 契約變更 |
| 2 | 既有端點小改（多回一個欄位、加一條驗證），無 migration | 既有畫面小改（加一欄位、加一個篩選），無新元件 |
| 3 | 一組完整 CRUD 或一支新端點含驗證，無 schema 變更 | 一個畫面的完整改版（表單＋清單連動），沿用既有元件 |
| 5 | 多支端點＋一支 migration（加欄位／索引） | 一個新畫面（表單＋清單＋對話框）含 API 對接 |
| 8 | 新表／多支 migration，或跨模組寫入鏈、報表匯出 | 多畫面模組，或含列印／匯出版面實作 |
| 13 | 上述再疊存量資料回補、跨租戶調整或效能改造 | 跨模組流程改造，或全站共用元件改動 |
| 21 | ⚠ 超出一個 cycle — **不要直接開 21**，先回步驟 8 拆成多張 Dev 票 | 同左 |

### 帶入規則

- **依規格推導**：有 BFS／FFS 時，依其工作項數與上表對照；資訊不足（僅自然語言描述）→ 前後端各以 `3` 起評，描述中出現 DB 結構變更或新畫面時上調一階。
- **既有票校正**（步驟 3.5）：**原本已有 estimate 的票不覆寫**（那可能是 Dev 自己調過的），原本沒有才補上。
- 判定 ≥ `13` 時，於開票結果報告加註「建議拆票」。
- `save_issue` 帶 `estimate` 失敗（團隊未啟用估算，或尺規不含該值）→ **去掉 `estimate` 重送一次**，票照建，於結果報告標註「estimate 未寫入」；**不因此中斷建票**。

## 票描述原則（所有票種）

票是給開發者與 QA **翻**的，不是讀的。票面只放「要交付什麼、對齊哪條需求、去哪查明細」；規格明細留在文件。

1. **定位行＋參考文件表必附**（格式見下方「定位行」節），描述第一個標題一律 `##`，不用 H1 重複標題。
2. **只放票生命週期內穩定、開發者第一眼要知道的內容**：交付範圍、端點總覽、資料表、對齊的 US／BR、AC。既有檔案路徑、可參照範本、套件選型、實作做法**不進票**——開票到開工常隔一至兩週，過期內容是辨識成本，不是省時間。
3. **規格明細不抄進票，用「文件 §章節」指路**，粒度到子節（`BFS §6.3`、`FFS §2.2`）。每種票有固定的「規格明細」指路節，見各範本。**唯一例外是前端票的畫面內容規格**（四類欄位群、檢核、權限、操作）——那是前端的工作契約本體，照 FFS §2 複製進票，因為票面禁附版面圖、欄位表就是畫面依據。
4. **AC ≤5 條**，每條對齊 FRD US-xx／BR-xxx，寫可觀察的情境結果；機械性項目（逐欄驗證、三態 UI、CRUD 基本操作）由規格書契約保證，不展開成 AC。
5. **QA 票只寫 E2E 情境**：一張表，從使用者操作走到資料落地與回歸點；不寫單元測試維度（逐欄驗證矩陣、單端點狀態碼）。
6. **技術中立**（Feature 票）：只描述行為與契約，不強制實作方式。**Bug 票例外**——必填「根因分析／程式碼問題定位／修改細節」三段。
   輸出類需求只定義「輸出什麼」，不定義產出管道；PM 票涉及新畫面時附原型連結（若專案有產出原型），不附 ASCII 佈局圖。

### 定位行（所有票種必附，置於描述最上方）

在「## 參考文件」**之前**，以引言區塊標示本票在系統中的座標——開發者與 QA 翻票時第一眼要知道「這是哪個模組的哪支程式」，不必回頭讀標題猜。

```markdown
> 📌 模組：{模組}｜{程式碼} {功能名稱}
```

規則：

- **模組**取自功能所屬的業務模組，用專案既有的模組分類（與 Dev team 的「模組」label 同一組詞彙；不自創，沒有模組分類就省略模組行）
- **跨多模組**時逐模組一行，各行列出該模組涉及的程式碼與名稱：

  ```markdown
  > 📌 模組：銷售｜{程式碼} 報價單作業、{程式碼} 訂單作業
  > 📌 模組：庫存｜{程式碼} 商品品名資料檔
  ```
- `{程式碼}` 指專案的功能代碼體系，沒有就省略
- 程式代碼登記名與畫面實名不一致時**兩者都寫**（例：`{程式碼} 商品類別（畫面實名：商品分類維護）`）——票面同時會被查代碼的人與查畫面的人搜到
- **票種專屬補充行**（選填，接在模組行下方同一引言區塊）：

  | 票種 | 補充行 |
  |------|--------|
  | Dev 後端 | `🗄️ 資料表：{表名}（讀寫）、{表名}（只讀）…` |
  | Dev 前端 | `🗺️ 路由：{route}｜主選單：{路徑}` |

**文件路徑格式**（緊接定位行之後）：

```markdown
## 參考文件

| 文件 | 路徑 |
|------|------|
| 需求文件 | `{FRD 路徑}` |
| 後端規格書 | `{BFS 路徑}` |
```
