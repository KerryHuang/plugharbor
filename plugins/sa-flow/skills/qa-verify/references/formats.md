# 機器檔格式參考

**權威來源是 `validate.py` 中的列舉常數與驗證邏輯；本檔是人讀版。改列舉值務必先改程式再改這裡。**

## 三條不變式

1. **空輸入不算通過**：`null`、`{}`、或缺頂層必要鍵會回錯誤，永不回空 list
2. **未知鍵是錯誤**：鍵白名單制，多出來的鍵直接報錯（已知步驟放錯層的教訓）
3. **`結果: null` 只在步驟失敗時合法**：run-ui 檔中 `結果` 為 null 僅當 `步驟失敗次數 > 0`
4. **`注意`／步驟 `注意` 禁結論性文字**：命中 `結果記|結果:|預期|不適用|未送出|規格` 即錯誤——`注意` 只能寫操作機制
   （selector／捲動／全選），寫觀察結果或引用規格會讓下一輪快取帶著上一輪的結論回去餵 runner，防錨定形同失效。

| cases[].預期.畫面斷言 | list | | ✗ | 第四槽，選填（舊檔無此欄合法）：查詢／清單頁的列數、合計、回第 1 頁、欄存在與否等非訊息事實 |
| cases[].預期.畫面斷言[].目標 | str | | ✓ | 要讀的畫面事實名稱（如「列數」「合計列金額」「欄:備註」）；runner 只看得到這個，不寫期望值 |
| cases[].預期.畫面斷言[].期望 | str / 數值 / null | | ✓ | 期望值；`存在`／`不存在` 時可為 null，其餘比對必填 |
| cases[].預期.畫面斷言[].比對 | str | `等於`、`包含`、`不存在`、`存在`、`數值等於`、`等於目標` | ✓ | `數值等於` 會去掉千分位逗號再比；`不存在` 要求 runner 實際為 null；`等於目標` 的 `期望` 寫同槽另一個目標名，比兩邊實際值（「修改後與修改前相同」用這個，不寫期望「是」） |
| cases[].預期.資料斷言 | list | | ✗ | 第五槽，選填：畫面讀不到的 DB 落地事實（如 `WORK_ORDER.STATUS`）。格式與 畫面斷言 相同；runner 不碰，由 fixture 跑完後唯讀查核寫 `db-check.yml` |

`期望` 不可是整段佔位符（`<該訂單單價>`、`{單號}`）——規劃時不知道的值，改用 `等於目標` 讀畫面上的來源值，或改放 資料斷言。期望也不寫個資原文（地址、email、電話、客戶名）：runner 會遮罩，逐字比對必不成立。
| cases[].寫入 | str | `無`、`建立`、`修改`、`刪除` | ✓ | 是否涉及寫入 |

**畫面斷言範例**（查詢頁「篩選後 3 列、合計 1,200、回第 1 頁」）：

```yaml
# plan.yml 預期
畫面斷言:
  - {目標: 列數, 期望: "3", 比對: 等於}
  - {目標: 合計列金額, 期望: "1200", 比對: 數值等於}
  - {目標: 目前頁碼, 期望: "1", 比對: 等於}
  - {目標: "欄:備註", 期望: null, 比對: 不存在}
# run-ui.yml rules.<TC>
畫面斷言:
  - {目標: 列數, 實際: 3}
  - {目標: 合計列金額, 實際: "1,200"}
  - {目標: 目前頁碼, 實際: "1"}
  - {目標: "欄:備註", 實際: null}
```

## db-targets／db-check（資料斷言查核）

`strip_plan.py <plan> <steps-only> <db-targets>` 在有 資料斷言 時另寫 `db-targets.yml`：`{meta, cases: {<TC>: {目標: [..], 前置條件: [..], 步驟: [..]}}}`，不含期望。fixture 跑完 runner 後依它查 DB，寫 `db-check.yml`：

| 鍵 | 型別 | 必填 | 意義 |
|----|------|------|------|
| _meta.通道 | str | ✓ | `[<DB 工具> <連線名>]` |
| rules.<case_id> | list | ✓ | 該 TC 每個資料斷言目標一筆 |
| rules.<case_id>[].目標 | str | ✓ | 與 db-targets 逐字相同 |
| rules.<case_id>[].實際 | str / 數值 / null | ✓ | 查得的值；查無列＝null；判不出是哪一列就不寫該筆（judge 判無法比對） |
| rules.<case_id>[].查詢 | str | ✓ | SQL 原文（唯讀） |
