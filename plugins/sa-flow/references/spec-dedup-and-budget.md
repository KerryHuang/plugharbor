# 規格去重閘、必畫圖與體積預算

> 適用：`requirement`（FRD／CR-FRD）、`system-analysis`（SAD）、`specify-backend`（BFS／CR-BFS）、`specify-frontend`（FFS／CR-FFS）撰寫前置檢查。
> 搭配 `doc-boundaries.md`（owner 矩陣、ref 寫法）、SPEC-INDEX 規範（定向讀寫）使用，本檔不重複兩者已定義的規則，只給各文件各自的套用值。
> **寫作 skill 先讀本檔「各文件套用值」自己那一列即可**；只在某章該不該 ref 有疑義時，才 `grep` `doc-boundaries.md` 對應產物列，不整檔載入。

## 去重閘（寫檔前必做）

對照 `doc-boundaries.md` owner 矩陣逐章自問「本章內容是否已在上游文件完整定義」：
- 是 → 改成一行 ref callout ＋「本節補充：{增量}」
- 無增量可補 → 整節只留 ref（依 `doc-boundaries.md` 規則二，代表本節應整段刪除）

展開任一節都必須能說出增量是什麼，不可為了「單份文件自足」重抄上游內容。

**去重只針對文字與表格，不同視角的圖不算重複。** FRD 業務流程圖（人與決策點）、SAD 泳道工作流與資訊流、
BFS sequence 與匯流圖、FFS 畫面轉移圖，畫的是不同層次，各自保留。曾有版本把 BFS 每份圖數由 4.4 降到 1.7，
就是把圖當重複 ref 掉的結果——讀者要的是圖，不要的是文字。

## 必畫圖清單與表格改圖通則

上表「必畫圖」列是最低要求。另兩條通則：

1. **表格超過 15 列、且表達的是順序／關係／條件** → 改圖，或圖＋表。純資料清單（欄位表、端點表、TC 表）維持表格。
2. **帶公式／比率／分攤／遮罩／優先序的規則必附算例**：格式為「輸入 → 輸出」表，數字取自代表性實際資料
   並註來源（例：測試環境 N 張訂單、毛利率 X%，數字取自實查）。術語表每個 domain 詞附一行實例；口徑差異要有
   「同一張單據在各口徑下的數字」對照。範例見 `templates/examples/diagrams-and-worked-examples.md`。

> 為什麼：圖表可能張張有實質內容，最核心的多段計算卻只剩上百行純表，
> 「口徑版本」「金額遮罩」全鏈沒有一組前後對照——圖只出現在範本留了 mermaid 佔位的地方，
> 例子只出現在 SA 剛好想到的地方。必畫圖與算例成為必填件之後，這兩者才不靠運氣。

## 體積預算：量正文，不量整檔

**正文**＝從第一個 `## 1.` 起、到 `## D.` 之前，**不含** `§0 一頁摘要`、`§D`、附錄、`<!-- CHANGELOG -->` 區塊。
量法：

```bash
F={規格檔}
awk '/^## 1\./{p=1} /^## D\./{p=0} p && !/📎/' "$F" | wc -c
```

**📎 ref 行不計入預算。** ref 三要素（檔名＋章節＋標題）是 `doc-boundaries.md` 要求的格式，
一處約 120 B；verifying-specs 一次補齊數十處 ref，就可能把 BFS／FFS／SAD 三份同時推超預算，
只能靠放行決策收場——預算與格式兩條規則各自對，互相打架時輸的是讀者。排除 📎 行後，
預算量的才是「正文自己寫了多少」。

**簡稱宣告**：正文 ref 可用簡稱，前提是在「文件資訊」表宣告一次：
`| 簡稱 | FRD＝《{功能} 需求文件》、SAD＝《{功能} 系統分析文件》、BFS＝…、FFS＝…；附錄以 §Ex／§Fx／§Gx 前綴指本文件附錄 |`。
宣告後正文寫「見 BFS §6.2 端點 1」即符合三要素；未宣告仍須全名。

**上限是預算，不是目標**；但超標處置只有兩條，**沒有「確認放行」**：

1. 先過去重閘：該 ref 的章節是否真的 ref 了；示範值（JSON 範例、示範性長表）是否已移出正文進 `templates/examples/*`。
   > 例外：FFS §2 四類欄位群是實際規格內容，不得為壓體積移進 examples。
2. 仍超標 → **拆附錄檔**：`{功能名稱}_附錄_{主題}.md`（例：`_附錄_API契約明細.md`、`_附錄_欄位對照全表.md`），
   主文該章只留總覽表＋一行連結，SPEC-INDEX 該章末尾註 `明細見附錄檔`。附錄檔自帶 `<!-- SPEC-INDEX v1 -->`。

真的要放行（拆了會讓讀者跨檔跳讀反而更差）→ 在 `decisions.md` 記一列：決策＝「體積放行」、依據＝哪一章、為何不可拆。
**放行是例外不是慣例**：同一條鏈第二次放行即代表預算或格式規則有問題，回報 `retrospective` 而不是再記一列。
沒有這一列的超標檔＝缺陷，`verifying-specs` 報 WARNING。

> 早期版本把預算定成「提示非硬門檻」，結果「體積照現況放行」成了 changelog 常態句，
> 去重閘後三類文件中位數反而上升（FRD 28.7→38.6KB、BFS 37.7→43.0KB）。預算只在寫檔那一刻量一次
> 也不夠——之後每輪回寫只加不減，所以回寫規則（`shared-preludes.md`「取代不追加」）與本節配套。

## Markdown 結構：補充說明不可切斷表格

在既有表格上補說明時，引言區塊（`>`）**一律放在整張表結束之後**，不可插在最後一列之前——
Markdown 表格遇到非表格行即中斷，插在中間會讓同一張表被渲染成兩張，中間夾一段引言。

```markdown
<!-- 錯 -->                          <!-- 對 -->
| 欄 | 值 |                          | 欄 | 值 |
| A | 1 |                            | A | 1 |
                                     | B | 2 |
> 補充說明…
| B | 2 |   ← 變成第二張表            > 補充說明…
```

同理適用於：程式碼區塊、清單、標題。**改完用 `grep -n "^|" ` 確認該表的列是連續的。**

## SPEC-INDEX 產出

寫檔時在 `§0 一頁摘要` 之後、`## 文件資訊` 之前產生 `<!-- SPEC-INDEX v1 -->` 索引區塊，格式依專案的 SPEC-INDEX 規範（`§0` 也要列一行）；無規範時，每章列一行：章節、編號區間、一句摘要。編號區間（US／BR／VR／IF／TC）須與實際章節內容一致；
章節增刪或編號區間變動時同批更新索引。
