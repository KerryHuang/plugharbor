# 文件邊界與去重規範

> 適用於撰寫 FRD / SAD / BFS / FFS（含 CR 變體）與驗證規格書。
> 目的：四份文件依各自主題撰寫，**同一份產物只在一處完整定義**，下游用 ref 串接，不重抄。

## 核心原則

1. **單一事實來源（Single Source of Truth）**：每個「產物」（狀態圖、驗證規則、ER 圖、欄位定義、既有快照…）只在它的 owner 文件完整撰寫一次。
2. **下游 ref + 增量**：下游文件需要該產物時，**不重列**，改寫「見上游文件 §X」並只補充本文件主題的增量資訊。
3. **主題優先於完整性**：寧可文件靠 ref 互補，也不要為了「單份文件自足」而重抄上游內容造成多份不同步。

## 產物 owner 矩陣

| 產物 | Owner（完整定義） | 下游處理 |
|------|-----------------|---------|
| **§0 一頁摘要**（三句、總覽圖、讀者導覽、關聯表） | 各文件自己 | 不 ref、不去重；總覽圖 ≤10 節點，不取代各章詳細圖 |
| **決策紀錄** | **功能目錄 `decisions.md`**（全鏈連號 D-001） | 各文件 `§D` 只列本階段編號與一句結論；引用寫 `見 decisions.md D-012`，不重抄（見 `decision-record.md`） |
| **算例**（公式／比率／分攤／遮罩／優先序規則的輸入→輸出） | 規則 owner 所在文件：業務算例 FRD §5.3、技術精度 BFS §2.5、VR 合法／不合法值 BFS §7 | 下游 ref 同編號，不重算；數字取自代表性實際資料並註來源 |
| 業務狀態語意（狀態清單、轉換條件） | FRD §3.2 | SAD §2.3 ref + 補「系統觸發/允許操作」；BFS §2.4 ref + 補「狀態欄位、前後置動作」；BFS **不另畫** §4.2 狀態圖 |
| 業務流程圖（人＋系統決策點） | FRD §3.1 | SAD §2.1 ref + 補「系統支撐邊界」；BFS 以 §3 sequence 表達技術流程，**不重畫** §4.1 |
| 使用者故事 / 驗收條件 | FRD §2 | SAD/BFS/FFS 以 US-XX 引用，不重述故事（舊文件的 UC-XX 為 legacy，不回溯） |
| 畫面清單、業務目的、操作表、業務層欄位語意 | FRD §4 | FFS §2 承接為欄位表的業務輸入；不重述業務目的 |

| 標準 CRUD 動線 | references/screen-spec-format.md | FRD/FFS/Dev 票皆不重畫，只寫功能特有流程與偏離之處 |
| 驗證規則（業務語意） | FRD §5.2 / §5.3 | 業務層描述留 FRD |
| 驗證規則（技術判斷細節 + 錯誤訊息字串） | BFS §7 | FRD §5 用同一編號；FFS §4 ref BFS VR（現況已對） |
| 涉及資料表（清單、讀寫、現有/新建） | SAD §4.1 | BFS §1.3 ref SAD §4.1；BFS §5.4 僅在需「完整欄位定義」時保留 |
| ER 圖 | SAD §4.2（分析）→ BFS §5.1（含完整欄位，最終事實來源） | 兩處擇一為主：若 BFS §5.1 已含完整欄位，SAD §4.2 簡化為關聯概念圖 |
| 既有實作勘察**明細**（路由清單、類別名與路徑、行號、mapping 逐欄） | **`analysis/reuse-scan.yml`（不進任何規格文件）** | 這是勘察證據不是規格。寫進文件會過期，且 Dev 會當成實作指示照做——實作方式應由 RD 決定 |

| 重用分析 | SAD §5 | BFS 以「延用/擴充/新建」標注引用，不重做盤點 |
| API 端點規格（Request/Response/JSON） | BFS §6 | SAD §6.4 僅做 US→API 對應；FFS §6.1 引用 BFS（現況已對） |
| 測試案例 | 依層次分工，不互抄 | **FRD §7 不列 TC**（業務驗收＝§2 AC；E2E 情境 owner 為 QA 票，取材 FRD §2）；BFS §12=API 層；FFS §8=UI 層。同一情境只在對應層出現 |
| 邊界與例外清單 | SAD §6.6 | 維度定義見 `boundary-dimensions.md`（B1–B13／M1–M4，SA 盤點與 dev-readiness 驗證共用同一組編號）。BFS §7 VR／§8 例外／§8.4 並發依 §6.6 承接；dev-readiness 驗「規格有無落實 §6.6 結論」，**不重新盤點** |
| 列表／報表端點 DoR | BFS §6.0 | 撰寫法見 `specify-backend/references/list-endpoint-dor.md`。排序穩定性與 1:N 取值等維度同步餵 SAD §6.6；分頁／效能餵 SAD §6.5 |
| 排序五要素 | **分層**：業務語意 = FRD §4；策略 = SAD §6.6；明確值 = BFS §6.0（後端）／FFS §2（畫面與明細） | 規則見 `sort-order-standards.md`。FRD 寫「最新在前」，SAD 定由誰排與白名單，BFS／FFS 才寫欄位＋決勝欄＋NULL 位置＋序語意 |
| NFR（效能／並發／資料量／權限／稽核） | FRD §6（業務目標值） | SAD §6.5 逐項寫約束／現況／陷阱（不寫手段，手段進 TD），不重述目標值；BFS 只在端點層補約束 |

> 編號統一原則：跨文件指涉同一規則時沿用同一編號（如 VR-001 在 FRD、BFS、FFS 一致；邊界維度用 B/M 編號），避免 `VR-01` / `VR-001` 兩套編號造成追溯斷裂。

> ⚠️ **新增跨文件產物必須先登記本矩陣**：任何「上游產出、下游承接」的新規範，
> 上線前要在此寫明 owner 章節與下游落點。沒登記的後果是斷鏈——
> 曾發生 BFS §6.0 註解要求「同步填 SAD §6.6」，而 SAD 範本根本沒有對應欄位，
> 沒有人發現，因為沒有任何一處記錄過這條承接關係。

## ref 標準寫法

在下游文件「原本要重列」的位置，改放一行 callout，**不重貼表格/圖**：

```markdown
> 📎 **見《{功能} 系統分析文件》§4.1 涉及資料表**，此處不重列。
> 本節僅補充：{本文件主題的增量，如「明細表完整欄位定義」}。
```

規則：

1. ref 指向**文件名稱 + 章節編號 + 章節標題**，三者齊備（避免章節重編號後失效）。文件名稱可用**已在「文件資訊」表宣告的簡稱**（FRD／SAD／BFS／FFS、附錄 §Ex／§Fx／§Gx），規則見 `spec-dedup-and-budget.md`「簡稱宣告」；📎 行不計入正文預算。
2. ref 後**必須**說明「本節補充什麼」；若無增量可補，代表本節應整段刪除。
3. 跨文件完整路徑連結放各文件「附錄／相關文件」表；正文 ref 用上述 callout 即可。

## 各文件「主題增量」邊界（寫什麼 / 不寫什麼）

| 文件 | 只寫（增量） | 不寫（ref 上游） |
|------|------------|-----------------|
| **FRD** | 業務背景、目標、使用者故事（含角色，US-XX 為全鏈追溯鍵）、業務流程與狀態語意、畫面清單與業務目的、操作表、業務層有話要說的欄位與規則 | 系統互動、API、技術選型、資料表結構、**完整畫面欄位表**（owner 是 FFS §2） |
| **SAD** | 三流分析（工作流/資訊流/資料流）、系統支撐邊界、重用分析、既有架構盤點、US→API 對應、NFR 約束與風險 | 重述業務故事、完整 API Request/Response、前端畫面 |
| **BFS** | 後端行為契約、API 完整規格、Entity/欄位對應、驗證技術細節與錯誤字串、例外/並發處理 | 業務動機（ref FRD）、資料表清單與既有快照（ref SAD）、前端呈現 |
| **FFS** | 畫面內容規格（前端契約層，四類欄位群完整）、操作流程、欄位連動、即時計算、狀態控制、錯誤訊息 i18n 對照 | API 端點定義（ref BFS）、驗證規則語意（ref BFS VR）、業務狀態語意（ref FRD）、版面配置、元件名稱、標準 CRUD 動線 |

## BFS 文件內部去重

BFS 同一份文件內也避免自我重複：

| 重複點 | 處理 |
|--------|------|
| §2.4 狀態轉換表 vs §4.2 狀態圖 | 擇一：保留 §2.4 表（含前後置動作），§4.2 刪除或 ref FRD §3.2 |
| §3 CRUD sequence vs §4.1 業務流程圖 | 技術流程以 §3 sequence 為準，§4.1 刪除或僅留 ref |
| §12 測試 / §13 驗收 / §14 完整性確認 | §12 列測試案例；§13/§14 改為「檢查清單」引用 §12 編號，不重述情境 |

## CR 變體（CR-FRD / CR-BFS / CR-FFS）

CR 文件本身已是 delta-only（僅記錄異動 + ref 原始文件），縱向去重良好。**橫向邊界**沿用上述矩陣：

| 項目 | 規則 |
|------|------|
| 業務動機 / 變更語意 | owner = CR-FRD；CR-BFS/CR-FFS ref，不重述 |
| CVR / CBR 編號 | CR-FRD §4.3 為事實來源；CR-BFS §5、CR-FFS §4 沿用同一編號。技術判斷細節與錯誤訊息字串 owner = CR-BFS §5（對應一般矩陣 BFS §7 角色），CR-FFS §4 僅 ref 對應編號，不重列規則內容 |
| CR-FFS §4 驗證表 | **必須**有「對應 CR-BFS VR」欄（與主 FFS §4 一致） |
| API 端點 | owner = CR-BFS §4；CR-FFS §5 ref |
| 資料表 / 既有快照 | ref SAD §4/§A（CR 流程重用同一份 SAD，不另立 CR-SAD） |
| 畫面異動（UI 內容規格 delta） | baseline owner = 原始 FFS §2（完整欄位群）；**CR-FFS §2 是本次異動唯一記錄處**，只寫增量差異（`[+]/[~]/[-]` 標示），不重列完整欄位群。CR-FRD 無獨立 UI 章節（§4 為「欄位規格變更」，非畫面），不承擔 UI owner；畫面異動的業務觸發動機 ref CR-FRD §3 使用者故事 |

| 檢查項目 | 等級 |

| 跨文件同一規則使用一致編號 | BLOCKER |

| **FFS §2** 四類欄位群齊備、無省略號、來源欄無空白（FRD §4 不受此檢查，它不再承載欄位群） | BLOCKER |

## 存量文件 grandfather 條款

**唯一定義處**。其他 skill／reference 一律引用本節，不重述條件、不複製生效日——
散寫的後果是調整生效日要改五個地方，漏一處就出現兩套標準。

| 項目 | 值 |
|------|-----|
| 規範生效日 | **導入本 plugin 的日期**（由專案在 CLAUDE.md 記 `sdlc-spec-rules-since: YYYY-MM-DD`；未設定＝全部文件都適用，不豁免） |
| 適用維度 | 畫面內容規格完備性（B11）、輸出類需求管道中立（B12） |
| 豁免條件 | 文件建立日早於生效日 **且** 本次未觸及該畫面 |
| 豁免效果 | 檢查降為 INFO，列入待辦清單，**不阻塞** |
| 不豁免 | 本次 CR 有動到的畫面照常 BLOCKER——**改到哪裡就補到哪裡** |

其餘邊界維度（B1–B10、M1–M4）**不適用豁免**：邊界缺漏與文件新舊無關，
舊文件一樣會讓開發者猜錯。

## SPEC-INDEX（定向讀取索引）

每份 FRD / SAD / BFS / FFS 必須在 `§0 一頁摘要` 之後、「文件資訊」之前含 `<!-- SPEC-INDEX v1 -->` 區塊（`§0` 與 `§D` 各列一行）。
格式依專案的 SPEC-INDEX 規範；無規範時，每章列一行：章節、編號區間、一句摘要。撰寫類 skill 產出文件時同批產生；
`verifying-specs` 檢查索引章節與實際 `^## ` 章節是否一一對應（不對應 = WARNING）。

## BFS §6 表達法

| 內容 | 寫法 |
|------|------|
| 端點的 Request / Response 欄位 | **欄位表**：欄位／型別（含長度）／必填／來源與規則（標 VR-XXX、BR-XXX、來源欄位） |
| 回應與錯誤 | 一行帶過：`回應：201 + XxxDto（同 §6.2 欄位表）` / `錯誤：400 BR-012、409 同鍵重複` |
| JSON 範例 | **僅限**兩種情形才寫：巢狀結構（欄位表無法表達層次）、批量請求格式 |
| 跨端點共通的包裝格式／分頁參數／錯誤回應結構 | 只在 §6.0 與 §6.N+1 各定義一次，端點內不重列 |

範例見 `templates/examples/bfs-api.md`。

## 票↔文件雙向註記

Linear 票與規格／分析文件要能互相找到，`qa-verify`、`qa-sweep` 從票號反查 FFS §8 就靠這條。

- **開文件相關的票時**：票面註明對應文件路徑（`linear-create` 的「參考文件」表）。
- **文件裡**：記所屬票號——檔頭註記，或 CR 文件用票號檔名後綴（`{功能}_功能調整{前端／後端}規格書_{票號}.md`，`consolidate-docs` 以 `*_{票號}.md` 比對）。
- **票進入 Done**：跑 `sa-flow:consolidate-docs`，把票號後綴的變更文件合併回主規格並刪除票號來源檔。
- 開立／關閉狀態看 `sa-flow:linear-daily-report`，**不要**另外維護手動票號清單。
- 檔名慣例以 docs repo 的 `README.md`「文件命名規則」為準（有的話）。
