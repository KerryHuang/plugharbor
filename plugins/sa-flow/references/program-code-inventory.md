# 功能代碼盤點（Program Code Inventory）

## 概念

每個對外的功能頁面都對應一組**功能代碼**（program code），是權限控管的接合鍵——後端據此授權、前端據此決定選單與頁面可見性。**沒有代碼的頁面就沒有權限控管**，只能靠暫時性的圈法（如僅限管理員帳號）擋著。

代碼的權威清單是一份**盤點來源**（不在本 plugin 內）。SDLC 產出的規格書必須與它對齊：**分析階段查有沒有代碼、規格階段把代碼寫進文件、新增代碼時同步更新盤點**。

盤點來源有兩種形態，處理方式略有差異（Step A 讀取、Step D 回寫時分流）：

| 形態 | 典型位置 | 特徵 |
|------|---------|------|
| **markdown 文件** | docs repo | 人讀為主，含表格與統計摘要；回寫要維護表格結構與摘要數字 |
| **結構化資料檔**（JSON／YAML） | 應用程式 repo 的設定目錄 | 機器可讀、可被部署流程消費；回寫只加物件，無摘要可維護 |

> 為何 plugin 不寫死路徑：plugin 跨專案複用，盤點來源是各專案的產物。路徑一律由設定解析。
> 盤點來源**不一定住在 docs repo**——若它是被程式消費的設定檔（如部署時據以建立代碼的 catalog），
> 通常住在該應用程式的 repo，此時回寫會跨 repo，須留意各 repo 的分支紀律（見 Step D 第 4 點）。

## 設定方式

在目標專案的 CLAUDE.md（或 CLAUDE.local.md）中加入：

```markdown
sdlc-program-code-inventory: {相對於 docs-root 的盤點文件路徑，例：system/feature-inventory.md}
```

**路徑解析規則**：

| 情境 | 解析結果 |
|------|---------|
| 有設定，相對路徑 | 相對於 `{docs-root}`（專案 CLAUDE.md 設定，預設 `docs/`）解析。**可用 `../` 跳出 docs 指向同 workspace 的其他 repo**（盤點來源為程式消費的設定檔時常見） |
| 有設定，絕對路徑 | 直接使用 |
| **未設定** | 在 `{docs-root}` 下搜尋檔名含「功能盤點」/「功能清單」的 `.md`；找到唯一一份即採用 |
| 未設定且搜尋不到 | **靜默跳過**本規範全部步驟，不阻斷 skill（專案可能無此制度） |
| 未設定但搜尋到多份 | 用 `AskUserQuestion` 請使用者指定，並建議把選擇寫進設定 |

**禁止**：在 SKILL.md、範本或 reference 內寫死任何專案的實際盤點路徑／代碼前綴／類別值。這些一律從盤點文件當下內容讀取。

---

## Step A：分析階段 — 查代碼（`system-analysis` 適用）

功能涉及**新頁面**或**既有頁面的權限行為**時，於系統分析下結論前執行：

1. 解析盤點路徑（見上表）；解析不到 → 靜默跳過。
2. 讀盤點文件，以**功能語意 + route/畫面名稱**比對，判定屬於下列哪一種：

| 判定 | 依據 | 動作 |
|------|------|------|
| **已有代碼** | 盤點中查得對應列 | **維持現有代碼，不得另編新碼**。把代碼記進 SAD |
| **無代碼（新功能頁）** | 盤點兩張表皆無對應 | 走 Step B 暫編新碼 |
| **不需代碼** | 非獨立頁面（元件／對話框／既有頁內分頁），或該專案明訂不綁碼 | SAD 註明「不需代碼」與理由 |

> ⚠️ **先查再編**：既有代碼優先於新編。同一功能重複編碼會造成權限分裂（同一頁兩個碼、授權對不上）。
> ⚠️ **勿只靠檔名或印象比對**——盤點文件的代碼描述與前端 route 名稱未必同字面，需以功能語意判斷。

3. 若盤點文件本身的統計摘要與其表格內容對不上（列數／旗標數量），**一併回報**——摘要過期是常見漂移，別沿用錯誤數字。

## Step B：暫編新代碼規則

**代碼是有主的資源，暫編前必須驗證不撞碼。**

1. **編碼規則**：一律**沿用盤點文件當下記載的暫編慣例**（通常是「同類別主前綴 + 不衝突流水號」），不要自創格式。類別／前綴取自盤點中**功能語意最相近的既有代碼**。
2. **一碼一頁**：一個獨立 route／頁面一個代碼。多支頁面**不共用**單一代碼（除非盤點文件明載該專案採共用制）。
3. **撞碼驗證（強制）**：新碼與其接合鍵（route name / URL）必須**跨全部環境／租戶資料庫實查**確認未被占用，而非只查單一 canonical 庫。
   - 連不上的環境記為「**未實查**」，不可當成「無衝突」。
   - seed 語句一律**冪等**（存在即略過），讓未實查環境自我保護；並把未實查缺口寫進 seed 註解與規格書，上線後補驗。
4. 驗證結果（查了哪些、幾家無衝突、哪些未實查）寫進 SAD／BFS，不要只留在對話裡。

### ⚠️ seed 必須明給所有必要欄位——**不可依賴 DB 預設值**

代碼表除了「看得見」的欄位（代碼／名稱／類別／route），通常還有**決定可見性與啟用狀態的隱藏旗標**。seed 時必須**逐欄明給**，理由：

- **DB 預設值跨環境會漂移**。同一欄在多數環境的 default 是有效值、在少數環境卻是空字串——靠 default 的 seed 會在後者產生空旗標。
- 空旗標常被權限查詢過濾掉 → 該功能**對所有人隱形**，且**不會報錯**，只會「沒人看得到」，極難從症狀回推。
- **驗證單一環境不足以證明安全**。要嘛跨環境實查該欄 default，要嘛（更好）明給值讓 default 失去影響力。

寫規格時：
1. 先找**該專案的正確 seed 樣板**（通常是應用層的「建立代碼」handler，而非既有 migration——既有 migration 可能正在犯同樣的錯）。
2. 以樣板為準列出 seed 必含欄位清單，寫進 BFS。
3. 若既有 migration 用「一次性補值 + 白名單」修過這類漏洞，注意**那是一次性的**：在它之後 seed 的碼無人接手，會重新踩坑。規格須明寫新碼自行帶齊欄位。

> 教訓：seed 若漏給欄位、讓旗標吃 default，多數環境可能僥倖正確，例外環境卻會讓該功能對所有人隱形；即使前一支 migration 已明文警告，照抄前例仍會重蹈覆轍——**照抄前例不等於對，前例可能就是壞的**。

## Step C：規格階段 — 寫進文件（`specify-backend` / `specify-frontend` 適用）

### BFS（後端規格書）

**必須**包含「功能代碼」段落，載明：

| 項目 | 內容 |
|------|------|
| 代碼與描述 | 每個頁面對應的代碼、名稱、類別、旗標 |
| 來源 | 既有代碼（引盤點文件位置）／本次新編（引撞碼驗證結果） |
| seed 方式 | 新編代碼須說明如何佈到各環境（冪等腳本／migration），含授權管理員帳號 |
| **seed 欄位清單** | 逐欄列出（含隱藏旗標）與各欄取值＋依據樣板。**明寫「不依賴 DB 預設值」**（見 Step B 的 ⚠️ 節） |
| 授權端影響 | 端點權限是否隨代碼改變；**若不變，明寫不變與理由** |
| **發布旗標**（若專案有） | 專案若有「未測試功能上線前先隱藏」的旗標（如 Beta／灰度旗標，沒標＝正式環境直接露出），新功能上線前須標上，並明寫落地位置——若功能目錄的權威資料已搬到另一個資料庫，舊表旗標的 UPDATE 對前端無效，seed／UPDATE 必須落在權威側；**票面驗收條件寫「查權威側旗標＝true」，不寫舊表** |

> ⚠️ 代碼存在 ≠ 端點就該改用代碼授權。**先確認該專案後端是否真有 program-code 授權機制**——若沒有（或規格鏈另有要求），代碼只是給前端 gate 用的資料，端點權限維持原樣。這點必須在 BFS 寫明，避免下游誤改權限。

### FFS（前端規格書）

**必須**包含「功能代碼綁定」段落，載明：

| 項目 | 內容 |
|------|------|
| route ↔ 代碼 | 每支 route 綁定的代碼 |
| 綁定方式 | 依前端現行慣例（先查既有同類頁面怎麼綁，勿自創） |
| 暫時圈法的移除 | 若既有暫時性權限圈法（如僅限管理員帳號）因綁碼而該移除，明列移除點 |
| 上線順序 | 前端綁碼**必須在後端 seed 之後**才生效——明寫協同上線依賴 |

### CR-BFS / CR-FFS

變更既有功能時同樣適用：代碼**沿用不變**則明寫「代碼沿用 `{代碼}`，本次不變更」，不要略過該段落（下游會誤以為沒查）。

## Step D：更新盤點文件（新編代碼時強制）

**新編代碼與更新盤點來源必須同批完成**，不可事後補——盤點漂移會讓下一個人重複編碼。

依盤點來源的形態分流：

**A. markdown 文件**

1. 依既有表格結構加入新列（欄位、排序、旗標一律對齊該表現行慣例）。
2. **同步更新統計摘要**——以實際表格內容重新計算，不要在舊數字上加減。發現既有數字本來就錯，一併修正。
3. 若有「決策註記」區塊，補一行說明本次編碼依據與關聯票號／seed 腳本。

**B. 結構化資料檔（JSON／YAML）**

1. 依既有條目的欄位結構加入新物件——**先讀檔內既有條目當樣板**，欄位齊全度對齊，不要只填自己想得到的欄位。
2. 檔內若有註解欄位（如 `_readme`）載明收錄標準或 provisioner 規則，**先讀再寫**：確認該碼符合收錄標準（不符合就不該加，於規格書寫明理由）。
3. 判斷類欄位（預設開關、是否啟用等）若無法從資料推導，**於規格書列為待裁決項並詢問使用者**，不要自行猜值填入。
4. 保持檔案可被程式解析——寫完驗證格式合法（JSON 用 parser 驗一次），排序沿用檔內既有慣例。

**共同**：盤點來源所在的 repo 若為獨立 Git repo，依 `shared-preludes.md` Step 0.5 的 docs 同步原則提醒使用者 commit / push。
**若它不是 docs repo**（如應用程式 repo 的設定檔），須依該 repo 的分支紀律處理——
專案可能對此類維護另有豁免（如允許直接在整合分支修改），**先查該專案 CLAUDE.md／rules 再動，不要預設可以直接改**。

