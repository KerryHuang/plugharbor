# Skill 設計慣例

寫 skill 或改 skill 流程時對照本檔。

## 流程預設平行，不是線性

畫流程圖之前先問每一步：**這是真的有資料依賴，還是我只是照時間順序排下來？**

判準是**共用資源**，不是先後感覺：

| 條件 | 結論 |
|---|---|
| 用不同工具（瀏覽器 vs DB vs 讀檔） | 可平行 |
| 不寫同一批檔案 | 可平行 |
| 後一棒要拿前一棒的產出當輸入 | 才串接 |

常見可平行的組合：

- **實機探索 ∥ 文件／DB 蒐證**——一個用瀏覽器、一個用唯讀 DB 查詢工具與讀檔
- **產圖 ∥ 寫字**——檔名先約定好，寫字的不必等圖到位
- **多維度審查**——各維度彼此獨立

### 同一棒內部也要看能不能再切

平行不只發生在「棒與棒之間」。一棒要處理 N 個獨立單位時（N 張截圖、N 個模組、
N 份文件），先問**這 N 個之間有沒有共用狀態**：

- 沒有 → 分組，一組一個 agent
- 有 → 按狀態分組，同組序列、跨組平行

**分組方式要現場分析，不要在 skill 裡寫死。** 每個案子的單位性質不同，
寫死的分組表換一個案子就分錯。skill 該寫的是**判準與分析步驟**
（先列每個單位的前置條件 → 前置相同者歸組 → 有副作用的單獨跑），
範例要標明「僅供參考不要照抄」。

組太細也會變慢——每組都有固定啟動成本（登入、導航、載入），
一組只有一個單位通常不值得切。

瀏覽器工作尤其值得切：工具吃 `pageId`，每個 agent 開自己的分頁就能各自維持狀態。
**會寫資料的那組單獨跑**，它會改變其他組看到的畫面。
同一個瀏覽器實例內，分頁獨立不代表全部獨立，平行時要守三條：

| 共用的東西 | 撞法 | 約束 |
|---|---|---|
| 「當前選中頁」 | 一個 agent 切分頁，另一個的分頁失去選中 | **每次呼叫都明確帶自己的 `pageId`** |
| 視窗尺寸 | 分頁同屬一個 window，resize 影響全體 → 截圖尺寸不一致 | 尺寸由 skill 派工前統一設定，**平行時 agent 不准自己 resize** |
| 原生對話框 | `confirm`／`alert` 會卡住瀏覽器自動化 | 探索腳本避開會觸發原生對話框的按鈕 |

瀏覽器工具的選擇與限制見各 skill 所述；工具不可用時改人工，不要硬撐。

#### 派工訊息裡的環境宣稱，本身就是待驗證的對象

呼叫端在 prompt 裡寫的「瀏覽器是乾淨的」「這是測試環境」「這批資料是假的」——
**都是宣稱，不是事實**，agent 收到後要自己再驗一次。細則見 `dispatch-conventions.md` §五。

串接的地方要在 SKILL.md **寫出依賴的理由**，避免後人以為可以拆。

> 事故：`operation-manual` 首跑時流程寫成全串接，探索跑實機時整條鏈乾等。
> 實際上規格深讀與 DB 查詢完全不碰瀏覽器、也不寫同一批檔案。

平行的收益不只省時間：DB 蒐證補的**欄位長度／必填是畫面看不出來的證據**，
有了它 gaps 才能做三方比對（規格 vs 畫面 vs 資料庫），只有畫面證據時
手冊寫不出任何欄位限制。

### 派平行 agent 的五件事

1. 明講「另一個 agent 正在寫 X，不要碰」——避免撞檔
2. 各自的**輸出**檔名先分開
3. 各自的**工作區**也要分開——`scratchpad/g1/`、`g2/`、`g3/`
4. 匯流點（誰等誰）在 SKILL.md 標明
5. `context: fork` 的 skill 派平行 agent 一律**前景**（同一則訊息多個 Agent 呼叫、不帶 `run_in_background`）——fork 背景派工可能先結束自己這一輪，回報送到最上層 session，匯流點就沒人接（曾在規格驗證實測發生）

> 事故（`operation-manual` 三組平行標註）：輸出檔名分得很乾淨（完全不重疊），
> 但三組都在共用 scratchpad 建暫存產生器，各自取名 `gen.py`，第 1 組**靜默覆寫**了第 3 組的。
>
> 分開輸出是直覺會做的事；**中間工作檔會撞是因為它們不在派工訊息裡，沒人想到要分**。
> agent 自行決定的暫存檔名高度趨同（`gen.py`、`tmp.html`、`out.png`），
> 撞名機率比想像高，而且覆寫不會報錯。**派工時直接指定每組的工作目錄。**

### 遮罩不能蓋掉標註的主角

在截圖上同時做遮罩與標註時，**先確認要標註的元素不在遮罩範圍內**。

> 事故：錯誤提示正好落在被遮罩的欄位上，整片遮罩把提示蓋掉了——
> 這張圖的唯一主角被自己的遮罩消滅。改成把遮罩拆成三塊繞開提示才解決。

同一次教訓還帶出一條：**座標要量，不要目測**。疊完一定要回頭截圖檢查，框歪了就調。

## 優化流程之前，先問它有沒有必要存在

規範寫得越完整，越容易忘記問這個問題。曾在短時間內出現三次同一個形狀：

| 我們做了什麼 | 其實該問的 |
|---|---|
| 為瀏覽器 profile 衝突寫了一整套診斷、協調、收尾釋放規範 | 改用隔離模式後，**沒有任何 session 會持有 profile**，整層規範作廢 |
| 想把「事後逐張量座標」從 25 分鐘壓到 15 分鐘 | 探索當下就在頁面上，`getBoundingClientRect()` 幾乎零成本——**那一輪回頭量測根本不必存在** |
| 補「派工前檢查 lock」防止碰撞 | 同上，隔離模式下沒有東西可碰撞 |

判準：**當你在替一個流程加第三層補救措施時，停下來問「這個問題本來需要存在嗎」。**
補救措施會自我證成——每一層都真的解決了上一層的漏洞，所以每一層看起來都必要，
但整疊可能建立在一個可以移除的前提上。

徵兆是**規範在成長而問題沒有消失**：碰撞一再發生，規範從一節長到四節，
碰撞照樣發生。那不是規範不夠細，是層級選錯了。

> 收尾條款那條是反例，值得對照：它有效，是因為**把負擔從人的記憶轉移到流程裡**
> ——派工時就寫明「做完關掉並回報確認」，而不是靠誰記得去查。
> 前幾次補的「怎麼診斷」「怎麼協調」都是在人身上加負擔，所以都沒生效。

## 流程要能一次跑到底

skill 的價值是**把一條鏈跑完**，不是把它切成 N 次往返。設計時就要讓它自主完成，
中途只在**真正需要人決策**的地方停。

| 該停下來問 | 不該停 |
|---|---|
| **起手的環境／目標選哪個**（選錯整輪白跑） | 「這一棒做完了，要繼續嗎」 |
| 政策決定（要不要重拍、動別人的 agent） | 回報進度 |
| 會造成不可逆後果（建了刪不掉的資料） | 每一棒的結果摘要 |
| 兩種做法各有代價、需要取捨 | |

**起手參數尤其要問。** 環境、目標對象、要做哪個模式——這些一旦選錯，
後面每一棒的產出都要作廢。規範裡的「優先用 X」是取捨建議，**不是替使用者
決定的授權**。

> 事故：skill 自行挑了內部 demo 環境開跑，使用者實際要的是客戶測試站，
> 探索到一半被中止重來。

> 事故（`operation-manual` 首跑）：每跑完一棒就回報並問「要繼續嗎」，
> 八棒變成八次往返，最後還出現「跑完了才發現交付物沒產出、要重跑」。

**收尾條件要在動工前就講清楚**：這條鏈跑完的定義是什麼、產物落在哪、
哪一步之後才算交付。含糊的收尾條件就會變成「跑完了才發現沒做完」。

## 終點是可版控的來源檔，不是衍生物

skill 的終點應該停在**可 diff、可校正、可版控**的來源檔（md、yml、程式碼），
不要一路產到二進位衍生物（PDF、PPTX、圖片壓縮包）。

衍生物另外問：要不要產、什麼時候產由使用者決定。理由是來源檔通常要先經過
幾輪人工校正才定稿，**太早產衍生物只是產一份馬上過期的檔案**，而且二進位檔
進版控會讓 diff 失去意義。

## 主 session 不產文件，派 agent 產

**主 session 的職責是統整、派工、思考、決策；執行一律派 agent。**
完整對照表與硬規則見 `dispatch-conventions.md`。

「產文件」包含：規格、手冊、簡報、報告、分析結論、證據彙整——
只要是**要寫出內容**的工作，都派出去。理由是 **context**：主 session 要維持全局判斷力，
一旦自己動手寫長文，context 被產出內容佔滿，就失去統整與決策的餘裕。

> 事故：`operation-manual` 首跑期間，主 session 自己寫了證據彙整、手冊草稿、
> 簡報草稿、gaps 分流清單、回顧報告五份文件。每一份都該派 agent。

**唯一的例外是機械性落檔**：agent 回傳內容、由 skill 寫入指定路徑——
僅限 agent 沒有 Write 工具時。

## session 看到的 agent 與 skill 都是啟動時的快照

**agent 型別與 skill 內容都在 session 啟動時載入。** 改了檔案，
**當前 session 已註冊的那份不會更新**。這件事有三種形式，都踩過：

| 形式 | 症狀 |
|---|---|
| agent 的 `tools` | 提示裡寫「你有 Write」，agent 回「我的工具清單沒有 Write」 |
| agent 的 `tools`（**反向**） | 檔案早就補好了，session 卻顯示舊清單，**誤判成「skill 有缺陷要修」** |
| **skill 的 SKILL.md** | `Skill` 工具餵回舊版流程，磁碟上的版本早已不同 |

**反向那個更危險**：正向會當場報錯，反向不會——你會據此得出「這支 agent 缺工具」
的結論，然後去修一個根本不存在的問題，甚至新建一支重複的 agent。

**判斷方式**：只要這個 session 內改過該 agent 或 skill，**一律以磁碟為準**，
不要相信 session 餵給你的版本：

```bash
grep -n "^tools:" agents/<name>.md          # agent 實際工具集
ls -la skills/<name>/SKILL.md               # skill 檔案大小與時間
grep -n "^### S\|^## " skills/<name>/SKILL.md   # 流程段落，跟載入版對照
```

對照不上就照磁碟版執行。要讓 session 真的吃到新版，只能重啟——
但**不要為了驗證這件事去打斷進行中的實測**，用磁碟版跑完這輪即可。

## Agent 分工是為了 context 隔離

不是為了多開 agent。拆的理由要是**素材性質不同**：

- 探索會產生大量畫面快照與截圖，那些對撰寫毫無用處卻會擠爆 context
- 撰寫是長文本生成，不需要看探索過程的雜訊
- 審查該由沒寫過的人做，且要同時讀多份大素材

沒有這類理由就不要拆——每多一個 agent 就多一份要維護的定義。

## 中間產物不夾帶個資

真實環境的姓名、電話、身分證號**不要寫進 inventory／證據檔的範例值**，
一律用 `<員工姓名>`、`<部門>` 這類佔位符。

理由：中間產物雖然不進交付物，但**會被後續每一棒讀進 context**，
個資一旦寫進去就會一路傳遞。

## 腳本放 plugin 內，不放 docs

skill 要用的腳本放 plugin 的 `scripts/` 目錄，
skill 內以 `${CLAUDE_PLUGIN_ROOT}/scripts/…` 引用。

腳本留在 plugin 以外的位置，換一台機器或換一個專案跑 skill 會找不到，而且是靜默失敗。

## 權威內容只放一處

體例、範本、規範這類「人也會讀、也會改」的內容放 `docs/`，skill **引用不複製**。
兩處各存一份必然漂移。

## skill 要主動提議，不靠使用者記得時機

skill 一多，使用者不會記得什麼時候該用哪一支；觸發靠使用者記得，實際上就不會被觸發（回顧、回饋、取樣驗證這類 skill 長期零使用就是這樣）。

| 時機類型 | 怎麼觸發 |
|---|---|
| 自然語言描述得出來 | description 的觸發語 |
| 狀態型（佇列積壓、記憶將滿、票 Done） | hook 偵測狀態，agent 在**當前任務結束時**用 AskUserQuestion 提議一次；使用者拒絕就不再提 |
| 流程型（A 做完該接 B） | skill 結尾建議下一步，並問要不要接著跑 |

誤觸發的解法是「提議而不直接執行」，不是改成只能手動（`disable-model-invocation`）——skill 這麼多，使用者不會知道什麼時機點要用哪一支。

流程型的寫法固定一行：「完成後依動線用 AskUserQuestion 建議下一步：{條件} → `sa-flow:{下一棒}`（一句理由）；使用者同意才接著跑，不自動執行。」

## 攔截／確認類 hook：除了 exit 2，任何失敗都是放行

Claude Code 的 PreToolUse hook **只把 exit 2（或 JSON `permissionDecision`）當攔截**；其他任何失敗都會放行，而且不提示。安全類 hook 壞掉的樣子跟「沒命中、放行」一模一樣，不實測壞掉的情境就不會發現。

某次做「寫入前確認」hook 一天踩三次：
1. hook 指令寫死 `python3`：Windows 的 Store 版空殼存在、但一跑就 exit 9009 → 放行。
2. Windows stdout 是 cp950：判定沒壞，但確認窗的理由變亂碼。
3. 子程序 stderr 不是 UTF-8 → `UnicodeDecodeError` → hook exit 1 → 放行。

寫任何攔截／確認類 hook 都要：

- 啟動殼先**實跑**候選直譯器（`"$py" -c "import sys"`），全部失敗就在 shell 層直接輸出 ask／block，不依賴 Python。
- stdin／stdout `reconfigure(encoding="utf-8")`；子程序釘 `PYTHONIOENCODING=utf-8`（它會蓋過 `-X utf8`），解碼用 `errors="replace"`。
- 最外層 `except Exception` 轉成 ask／block。
- 掛在高頻工具（如每條 Bash）上的 hook，在 shell 層先做便宜的關鍵字快篩，不相關的直接 exit 0，不要每次起直譯器。
- 啟動殼若把 stdin 讀進變數再用 pipeline 餵直譯器，pipeline 裡的 `exec` 只取代子 shell——跑完要明確 `exit`，否則外層會繼續往下跑、重複輸出。
- 測試要含「壞掉的直譯器」（PATH 放 exit 9009 的假 `python3`）與 `PYTHONIOENCODING=cp950` 兩種情境。
- 改了 hook 的 command 字串，既有 session 不會重新載入；實機驗證要開新 session。

反過來，**補值類 hook**（如 `hooks/agent-model-guard.py` 替未指定 model 的通用 subagent 補 `sonnet`）失敗時本來就該 fail-open：補不到值只是退回預設行為，不該擋住派工。
