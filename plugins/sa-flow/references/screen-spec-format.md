# 畫面內容規格格式（screen-spec-format）

> 適用於撰寫 FRD §4、FFS §2／§3、Dev 前端票 §1／§2。
> **本檔是唯一格式權威**——上述三處只 ref 本檔，不各自定義格式。
>
> ⚠️ ref 的對象是撰寫規範，不是票面內容。Dev 票仍須**內含**完整畫面內容規格
> （開發者看不到 plugin 檔案），只是格式由本檔統一。

## 為什麼不畫版面

示意圖只定義功能（欄位、行為、驗證、對接端點），不定義版面；
版面一律以專案既有 UI 規範／設計系統與同類既有頁面骨架為準（專案若無既有規範，由前端開發自行決定）。照抄框線圖會做出不符專案設計語言的頁面。

因此 SA 產出**不含**框線佈局圖。畫面的「長相」由前端依既有頁面決定，
規格負責的是「畫面要承載什麼、怎麼運作」。

需要給 PO／客戶做視覺確認時，可另行製作原型（工具不拘），
原型**不進 Dev 票、不當版面依據**。

## 畫面內容規格

每個畫面一節，骨架如下：

```markdown
### SCR-01 {畫面名稱}

| 項目 | 內容 |
|------|------|
| 用途 | {這個畫面解決什麼} |
| 進入路徑 | {主選單 → 子選單；或從哪個畫面的哪個操作進入} |
| 主要使用者 | {角色} |

**區塊清單**（依資訊層級由上而下）

| 區塊 | 用途 | 內含欄位或操作 |
|------|------|---------------|
| {區塊名} | {用途} | {欄位群名稱或操作清單} |

{四類欄位群表格，見下}

**操作**

| 操作 | 觸發條件 | 執行後行為 | 權限 |
|------|---------|-----------|------|
| {操作名} | {何時可用／何時停用} | {系統做什麼、結束在哪個狀態} | {權限項；無則寫 —} |

> 本節定義畫面要承載什麼、怎麼運作；版面配置由前端依同類既有頁面骨架決定。
```

最後那句 footer **每個畫面規格結尾都要有**，一字不改。

## 輸入語意（取代元件名）

欄位表的「輸入語意」欄描述**輸入行為**，不指定元件：

| 寫這個 | 不要寫 |
|--------|-------|
| 單選（可搜尋） | SearchSelect、下拉選單元件 |
| 單選（固定清單） | Radio、Select |
| 多筆選取 | MultiSelect、Checkbox Group |
| 日期 / 日期範圍 | DatePicker |
| 數值（整數／小數 N 位） | NumberInput |
| 文字（單行／多行） | Input、Textarea |
| 開關（是／否） | Switch、Toggle |
| 唯讀顯示 | disabled Input、Text |
| 開窗選取（來源：{主檔名稱}） | Dialog + Table |

> 「開窗選取（來源：…）」是輸入語意欄，FRD 與 FFS 階段都寫主檔名稱（如「廠商主檔」），
> 語意不隨階段改寫；對應端點是技術層資訊，寫在同一列的「來源」欄，
> 到 FFS 階段才從業務語意升級為端點——理由見下方〈來源欄的兩階段寫法〉。

## 四類欄位群

每個**功能**必須列全四類，四類齊備的要求在功能層級把關，不因單一畫面沒有某類而被稀釋。
單一畫面本來就不適用某類（如純表單頁沒有查詢條件／查詢結果）——這種情況於該畫面**註明「無」**，
或註明**由同功能的其他畫面承載**（如查詢條件與查詢結果在列表頁，新增/編輯頁只有表單）；
若功能內任一畫面都承載不到，才是省略整段，不得省略。

**1. 查詢條件**

| 欄位 | 輸入語意 | 必填 | 預設值 | 來源 | 條件關係 |
|------|---------|------|--------|------|---------|

- 來源：依〈來源欄的兩階段寫法〉——FRD 階段寫 `參照{主檔名稱}`，FFS 階段才寫 `端點：{路由}`
- 條件關係：多條件間是 AND 還是互斥；單一條件寫 `—`

**2. 查詢結果**

| 欄位 | 資料來源 | 顯示格式 | 對齊 | 可排序 | 重要性 |
|------|---------|---------|------|-------|-------|

- 資料來源：依〈來源欄的兩階段寫法〉——FRD 階段寫業務語意，FFS 階段寫對應 API Response 的欄位名或 `前端計算：{公式}`
- 顯示格式：`yyyy/MM/dd`、`千分位`、`小數 2 位`、`原文`
- 重要性：`主要` / `次要` / `可摺疊`——**取代像素寬度**，寬度是版面決策
- 表格結尾註明**預設排序**。FRD 階段寫業務語意（「最新在前」）；FFS 階段寫明確欄位 + 方向，
  並補齊**決勝欄**（排序鍵非唯一時）、**NULL 位置**（欄位可為空時）、**序語意**（字串型編號時）。
  完整規則見 `references/sort-order-standards.md`——排序鍵非唯一而缺決勝欄，接上分頁會跨頁重複／漏筆

**3. 新增表單**

| 欄位 | 輸入語意 | 必填 | 預設值 | 來源 | 長度上限 | 所屬區塊 |
|------|---------|------|--------|------|---------|---------|

**4. 編輯表單**

**只寫與新增的差異**，相同者一句 `其餘同新增表單`。

| 欄位 | 與新增的差異 | 條件 |
|------|-------------|------|
| {欄位} | 唯讀 / 依狀態鎖定 / 新增時不出現 | {何種狀態下} |

**明細區**（若有）兩種寫法擇一，但同一份文件內要一致：

- **內聯**：欄位名加 `明細：` 前綴，用「所屬區塊」欄標明歸屬。適用明細欄位少、
  且無獨立查詢／狀態行為者。
- **獨立列表**：四類各自再列一份，標題加註 `（明細）`。明細欄位多，
  或明細有自己的查詢條件／狀態流轉時用這種。

明細區**必須註明預設排序**，且要指名採**顯示序號／建檔序／業務鍵**哪一種——這三者常被混為一談。
明細可中途插入新列時，一併定義插入位置與項次是否重編。規則見 `references/sort-order-standards.md` §5。

## 來源欄的兩階段寫法

同一個「來源／資料來源」欄，在 FRD 與 FFS 填的是**不同層次**的內容。
理由很直接：FRD 寫在 SAD／BFS 之前，那時 Response 欄位名還不存在，不可能填；
而 FRD 又禁止出現 API 路徑。

| 層 | Owner | 輸入類欄位（查詢條件／表單） | 顯示類欄位（查詢結果／唯讀顯示） |
|---|-------|---------------------------|-----------------------------|
| 業務層（僅個別欄位的語意說明） | FRD §4 | `手動輸入` / `固定清單：{值列舉}` / `參照{主檔名稱}` | `{本單據自身欄位}` / `參照{主檔名稱}` / `系統計算：{公式}` |
| 前端契約層（**完整欄位表**） | FFS §2 | `手動輸入` / `固定清單：{值列舉}` / `端點：{路由}`（選項來源） | `` `{responseField}` ``（BFS §6 Response 欄位名）或 `前端計算：{公式}` |

FRD 階段**一律不寫** API 路徑與 Response 欄位名。

> ⚠️ **不採雙 owner 分層**：完整四類欄位群**只在 FFS §2 寫一次**。
> FRD §4 只寫畫面清單、業務目的、操作表，以及**業務層有話要說的個別欄位**
> （必填有業務理由、有計算規則、有連動語意、有權限差異者）——不列完整欄位表。
>
> 理由：兩層寫的是同一組欄位、只有來源欄不同，卻要付兩次撰寫成本並永遠面對不同步風險；
> 而 FRD 那份沒有下游讀者——**FFS §2 才是 Dev 前端票的唯一取材處**，缺一欄就等於 Dev 票缺一欄。
> FFS §2 的取材來源是 `analysis/ui-survey.md`（既有畫面現況）、原型 HTML、
> BFS §6 Response 欄位表與 `analysis/db-analysis.yml`，不依賴 FRD 先抄一遍。

「前端計算」只填**後端不回傳該值**的欄位。後端會在 Response 一併回的計算結果
（小計、合計、稅額等），來源欄一律填該 Response 欄位名，前端只負責顯示格式——
誤填「前端計算」會把計算職責靜默畫給前端，並造成前後端算法各寫一套。

## FoxPro 現況 ASCII 的轉譯

`sa-flow:foxpro-analyzer` 產出的 ASCII 畫面結構圖是**舊系統現況記錄**（「當時長這樣」），
不是新系統的版面指示，因此該 skill 刻意豁免本格式。

但**寫入 FRD §4／FFS §2／Dev 票時必須轉譯**為四類欄位群，不得整段貼入：

| FoxPro 分析報告的內容 | 轉譯成 |
|---------------------|-------|
| ASCII 框線與欄位座標 | 丟棄（版面是前端決策） |
| 框線內的欄位標籤與由上而下的排列順序 | 四類欄位群的「欄位」欄，順序照舊系統 |
| 舊系統輸入方式（GET／POPUP／BROWSE／唯讀顯示） | 「輸入語意」欄 |
| 舊系統按鈕列與功能鍵 | 操作表（操作／觸發條件／執行後行為／權限） |
| 舊欄位對應的 DB 欄位 | 「來源」欄，依上節兩階段寫法 |

ASCII 只留在 FoxPro 分析報告內，**不得**經由複製貼上回流 FRD／FFS／Dev 票。

## 三條硬規則

**1. 禁止省略號**

不得出現「欄位1、欄位2…」「等」「其他必要欄位」「依實際需要增減」。每欄實名。
真的還沒確定 → 進 `AskUserQuestion` 問清楚，不得留模糊。

**2. 欄位順序即資訊層級**

欄位必須照畫面上的先後順序列出，順序本身就是規格。

- **順序是內容決策**（誰先誰後＝重要性）→ 前端會照做，要寫
- **座標是版面決策**（放左放右、幾欄一列、按鈕位置）→ 前端不照做，不要寫

這條界線是本格式的核心，寫規格時反覆對照：
你在描述「哪些東西、什麼順序」還是在描述「擺在哪裡」？後者一律刪掉。

**3. 來源欄必填**

每個顯示欄位的來源欄都不得留空，**但兩階段填的東西不同**（見〈來源欄的兩階段寫法〉）：

- **FRD 階段**：填業務語意（`手動輸入`／`固定清單：{值列舉}`／`參照{主檔名稱}`）。
  此時 Response 欄位名尚未存在，要求填它是時序上不可能的事。
- **FFS 階段**：升級為前端契約——填 BFS §6 的 Response 欄位名，或 `前端計算：{公式}`。
  這一階段的「空白不予放行」同時擋掉「規格寫了畫面但後端沒回這個欄位」的漏接。

## 操作流程分層

流程要寫，但只寫**狀態與決策**層。

**該寫**

- 觸發動作 → 系統行為 → 結束在哪個狀態
- 分支的**業務判斷條件**
- 失敗後停留在哪、已填資料是否保留
- 哪些操作需二次確認（因不可逆或影響下游）
- 完成後的去向**若有業務理由**（如連續建檔須留在原畫面繼續下一筆）

**不該寫**

- 彈窗還是新頁、Toast 還是頂部錯誤條、載入指示形式
- 什麼時機呼叫哪支 API

導航形式無業務理由時，直接寫「依同類既有頁面慣例」——
這是明確授權前端照其規範走，不是留白讓其猜測我們有沒有意見。

## 專案標準 CRUD 動線

以下動線為**預設**，任何 CRUD 功能通用。規格與票**不重畫**，只寫例外。

| 動線 | 內容 |
|------|------|
| 查詢 | 進入畫面 → 套用預設查詢條件 → 顯示結果 → 可換頁、可改條件重查；無資料顯示空狀態 |
| 新增 | 觸發新增 → 空白表單（帶預設值）→ 填寫 → 送出前驗證 → 失敗停留原畫面並保留已填內容、標示錯誤欄位 → 成功提示後回列表並反映新資料 |
| 編輯 | 選定資料 → 載入現有內容 → 修改 → 送出前驗證 → 失敗停留原畫面並保留已填內容 → 成功提示後回列表並反映異動 |
| 刪除 | 觸發刪除 → 二次確認 → 成功提示後列表移除該筆；失敗顯示原因且資料保留 |
| 通用失敗 | 無權限顯示無權限訊息；資料已被他人異動提示重新載入；連線／系統錯誤顯示錯誤與重試入口 |

撰寫時只寫兩種東西：

1. **功能特有流程**——跨畫面接力、匯入、批次、狀態流轉、與其他單據連動
2. **偏離標準動線之處**——並註明業務理由

沒有特有流程的功能，流程章節一句
「依專案標準 CRUD 動線（見 `references/screen-spec-format.md`）」即可。

## 常見誤用自查

寫完對一遍：

- [ ] 有沒有出現框線字元（`┌ ─ │ └ ├ ┼`）？→ 刪
- [ ] 有沒有出現具體元件名或元件庫名？→ 換成輸入語意
- [ ] 有沒有像素寬度？→ 換成重要性
- [ ] 有沒有省略號或「等」？→ 補實
- [ ] 每個顯示欄位都有來源，且寫法符合當前階段（FRD 業務語意／FFS Response 欄位名）？→ 補齊
- [ ] 標「前端計算」的欄位，後端真的不回這個值？→ 後端會回就改填 Response 欄位名
- [ ] 有沒有從 FoxPro 分析報告整段貼過來的畫面結構圖？→ 轉譯成四類欄位群
- [ ] 整個功能四類欄位群都齊備（單一畫面不適用寫「無」或註明由其他畫面承載）？
- [ ] 流程章節有沒有在描述彈窗／Toast／API 呼叫時機？→ 刪
- [ ] 每個畫面結尾都有那句 footer？
