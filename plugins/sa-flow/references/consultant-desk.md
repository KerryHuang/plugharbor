# 顧問桌（唯一定義處）

> `domain-advisor` 的觸發時機、編制（單顧問／同一支開兩個視角的雙顧問）、流程。
> `explore` / `requirement` / `system-analysis` 直接引用本檔；其他 skill 經 `shared-preludes.md` 間接適用。一律引用本檔，不各自定義。

## 核心規則：一條規格鏈只開一次顧問桌

同一功能的 FRD → SAD → BFS → FFS 是**同一批 domain 問題**的四種寫法。
顧問在 FRD 階段答過的邊界，到 SAD 階段不會有新答案——**重開一次桌，只是把同樣的結論再聽一遍**。

| 階段 | 預設 | 說明 |
|------|------|------|
| `requirement`（FRD） | **不開**（除非命中下方「FRD 例外」） | 此時只有需求描述，顧問缺乏可審的設計，產出多為泛論 |
| `system-analysis`（SAD） | **開（主場）** | Step 3 已完成 codebase/DB 勘察、Step 4-8 已有三流與方案，證據最足、問題最具體 |
| `specify-frontend`（FFS） | 不派 domain 顧問 | UI 動線問題，非 domain 邊界 |
| `dev-readiness` | 不派；domain 疑點併入 SAD 階段既有結論 | 該階段是驗「規格有無落實」，不是重新做 domain 判斷 |

**FRD 例外**（命中任一才在 requirement 階段開桌，且開了就在 FRD 註記，SAD 階段改用「差異複審」）：

- 全新業務概念，既有系統與既有 docs 皆無對應；
- 需求本身的**業務邊界未定**（做不做得到、算不算同一件事），不先釐清就寫不出 US；
- 涉及聚合根／狀態機的**歸屬爭議**（這張單據到底屬於誰、誰能改）。

> 這條例外對應分析嚴謹度閘第 5 條「domain 邊界必把關」（`analysis-rigor.md`）——**鏈上叫過一次即滿足**，
> 不要求每個階段各叫一次。

## 觸發式單點諮詢（分析過程中就地介入）

顧問桌是**階段末審查**（草稿完成後整份審）。但有些問題等到階段末才問就太晚了——
方向從第 4 步就歪了，第 8 步整份審只會告訴你「要重做」。

因此在 `system-analysis` **Step 4~6 分析過程中**，一旦命中下列訊號，
**當場派一次單點諮詢**（`domain-advisor`，只問命中的那一個點），不等 Step 8.3。

| 訊號 | 為什麼不能等 |
|------|------------|
| 出現**狀態流轉**（單據／訂單／申請的生命週期） | 狀態機定義錯，後面的三流分析、VR、並發處理全部要重來 |
| **聚合根歸屬**不明（這張單據屬於誰、誰能改、跟誰一起異動） | 邊界切錯會讓 API 粒度與交易範圍整組錯位 |
| **客戶變體**（同功能各客戶行為不同） | 沒先確認變體維度，方案會建立在「只有一種行為」的假設上 |
| **產品邊界**（多產品線或多種客群共用同一系統／資料庫） | 判錯會讓整份規格對錯客群 |

**做法**（單點、便宜、不打斷主線）：

```
subagent_type: "sa-flow:domain-advisor"
prompt: |
  mode: review
  scope: single-point            # 只回答這一個問題，不做整體審查
  question: {命中的具體問題，含當下已知證據}
  evidence_bundle: {analysis/db-analysis.yml 與 reuse-scan.yml 的相關片段}
```

結論即時併入當下的分析步驟，並**追加寫入** `analysis/consultant-notes.md`。

> **與 Step 8.3 的關係**：觸發式諮詢已解決的點，Step 8.3 整份審時**不重問**——
> 把已解結論一併給顧問，要求它只審「尚未觸及的面向」。
> 全部 domain 面向都已在過程中單點問過時，Step 8.3 可降為快速複核。

## 編制：預設單顧問

| 編制 | 用時機 |
|------|--------|
| **單顧問（預設）** | 一般需求，一個 `domain-advisor` 整份審 |
| **雙顧問（同一支開兩個視角）** | 業務流程與資料／系統邊界可能互相牽制（狀態機牽動聚合根、跨模組或外部系統的 SoT 爭議、權限與稽核和流程綁在一起），或單顧問自陳「另一面向證據不足」 |

兩個視角是同一支 `domain-advisor` 的兩個實例，派工時以 `lens` 區分：`business-flow`（業務流程）與 `data-boundary`（資料與系統邊界）。不另建 agent。

以 `AskUserQuestion` 讓使用者選，**推薦選項置首**：
`單顧問（推薦）` / `雙顧問（流程與資料邊界互相牽制時）` / `跳過`。

## 流程

### 單顧問（預設路徑，1 個 agent 回合）

```
subagent_type: "sa-flow:domain-advisor"
prompt: |
  mode: review
  context: {該階段成果摘要——SAD 為工作流/資料流摘要 + 推薦方案 + _sad-draft.md 路徑}
  evidence_bundle: {既有勘察結果；SAD 階段直接用 Step 3 成果與 analysis/*.yml，不重派 scout}
```

### 雙顧問討論（兩個視角互相回應，最多 5 輪）

兩個視角各自提出爭點後**交叉審、輪流回應對方**，主線當主持人：轉話、控輪數、判結局，不參與立場。
指令、檔案格式、pane 操作與異常處理見 [advisor-discussion.md](advisor-discussion.md)。

**執行方式：預設開 herdr pane**（兩位顧問開在主線右側，使用者隨時看得到分析與討論、也能直接在 pane 插話）；
沒有 herdr 或主線不在 herdr pane 裡 → 退回 subagent（`Agent`＋`SendMessage` 續接），並告知使用者紀錄位置。

1. **開場**（兩位平行，`mode: discuss-open`，各帶自己的 `lens`）：各自讀證據，交出爭點提案，每人最多 5 個、依影響排序，其餘列備忘。
2. **整理議程**（主持人）：合併重複；兩方立場已一致的直接結案為「共識」；其餘進討論，**總數上限 5**（D-1～D-5）。
3. **討論輪**（`mode: discuss-reply`）：每輪＝雙方各回應一次，所有未結案爭點同一輪處理。
   主持人把 A 的回應轉給 B、B 的轉給 A。每個爭點每輪必須落到「同意／讓步（修正立場）／補證據反駁」之一。

   | 輪 | 要求 |
   |----|------|
   | 1～2 | 回應對方論點；反駁必須附**新**證據（自己查碼／文件，或主線補進的 DB 實查） |
   | 3～4 | 不得再提新論點，只能補證據或提出「我可接受的最終方案」 |
   | 5 | 強制收斂：只回「接受對方方案」或「堅持本方方案＋最強一條證據」 |

   **提前結束**：某爭點有一輪雙方都沒有新證據、也沒有讓步 → 不跑滿 5 輪，直接判結局。
   **改循序回應**：某爭點出現「雙方同一輪各自讓步成對方上一輪的立場」（互換），下一輪該爭點改成循序——
   A 先答，B 看過 A **同一輪**的回應再答。平行回應時兩邊都只看得到對方的舊立場，會被對方的舊論點說服而來回翻轉。
   互換若再發生一次，視同僵局直接判結局。
4. **判結局**（主持人只能依此表，不憑偏好）：

   | 結局 | 條件 |
   |------|------|
   | 共識 | 雙方立場一致 |
   | 撤回 | 一方接受對方方案 |
   | 證據裁決 | 一方 Confirmed、另一方只有 Likely／Unknown → 採 Confirmed 方並記理由 |
   | 交使用者 | 雙方都 Confirmed 但結論相反（業務取捨），或雙方都只有 Likely |

5. **交使用者**：全部爭點判完才問。`AskUserQuestion` **一次一題**，題目寫爭點本身，兩個選項＝雙方最終方案、各附一行最強證據；
   主線依證據有傾向才把該項置首標（推薦）。每答一題立即寫回落檔，再問下一題。
6. **收尾**：使用者答完、結果落檔後才關顧問——答案若引出追問，顧問還保有上下文。

**範圍控制**：討論中冒出的新議題記入「延後清單」，不展開；新議題若阻斷當前爭點，可替換一個現有爭點，總數仍 ≤5。
延後清單隨落檔交回主線，由主線決定要不要另開一次。

**不會被卡住**：顧問以 `--agent` 啟動或以 subagent 派發，工具只有唯讀查詢，**沒有 `AskUserQuestion`、不能寫檔**——
需要使用者判斷的寫進回應的「需使用者裁決」欄，由主線統一問。主線問使用者時顧問已閒置，不會被拖住。

> 為什麼不是「兩份報告並行、主線比對」：那樣顧問之間沒有對話，對方沒機會回應反駁，衝突靠主線猜，也沒有收斂上限。

## 校準與證據（單顧問、雙顧問共用）

**只把符合任一條的問題提為缺口或爭點**，其餘降為「備忘」（一行、不討論、不問使用者）：

1. 有證據顯示現行草稿／設計會讓資料或流程出錯；
2. 缺了這個答案規格寫不下去（狀態機、聚合根歸屬、客戶變體、SoT 未定）；
3. 與既有系統行為衝突（現況勘察、舊系統移植的對齊）。

- 預設採信現行草稿；要推翻須有證據。**業界常識只能拿來提問，不能拿來下結論**。
- 舊系統移植鏈（`chain_origin: foxpro` 等）以舊系統行為為準，不提新功能。
- **偏離舊系統的處置**：專案已收錄的通用預設（平台先例、通用裁決清單）以內的偏離，照預設裁定、不交 PO；通用預設以外的偏離，一律交 PO。
- 每個主張標證據等級：**Confirmed**（附 `檔案:行號`／查詢摘要＋結果／文件章節）、**Likely**（寫明假設）、**Unknown**（寫明查不到的原因）。
- 查 DB 一律唯讀、只連測試環境；顧問自己沒有 DB 工具，需要的實查由主線先做好放進 `evidence_bundle`。
- Likely 不能推翻 Confirmed；要反駁對方的 Confirmed 必須拿出同等級證據。
- 討論模式不打分數。

### scout 派發

只在**沒有既有勘察結果**時派 `sa-flow:scout`（典型為 requirement 階段命中 FRD 例外）。
SAD 階段一律不派——Step 3 與 `analysis/db-analysis.yml`、`analysis/reuse-scan.yml` 已是 evidence_bundle。

## 產出整合

| 顧問輸出 | 落點 |
|---------|------|
| 兩方共識的缺口／L3 差距 | 補進當階段草稿的對應段落 |
| 單顧問的仍需釐清 | 併入該 skill 的確認門或疑問點總清查，依 `shared-preludes.md`「互動詢問規範」逐題問 |
| 雙顧問討論判為「交使用者」的爭點 | 依上方「雙顧問討論」第 5 步，`AskUserQuestion` 逐題問 |
| 備忘、延後清單 | 只落檔，不問使用者 |
| Domain 重大風險 | 確認門明確告知，建議先解決 |

顧問桌成果**必須落檔**至 `analysis/consultant-notes.md`（依 `shared-preludes.md` Step 0.8）：
諮詢日期、編制、逐項結論與證據、未解爭點、已裁決項與理由。
雙顧問討論另依 [advisor-discussion.md](advisor-discussion.md)「consultant-notes.md 追加格式」落檔，完整逐輪紀錄留在 `analysis/advisor-discussion/`。
同時在該階段正式文件記一行「已諮詢 {顧問}／日期／結論見 analysis/consultant-notes.md」。

下游 skill **先讀這份檔**：已有結論的問題不重問顧問、不重問使用者；
只有落檔內容未涵蓋的新問題才單獨補派，補完的結論**追加寫回同一份檔**。
