# 規格鏈分流（standard / lite）

**同一套流程套在所有功能上，小功能付的稅最重。** 單欄字典跟含交易、權限、migration 的主檔功能
走同一條七棒鏈，產出四份文件、開一次顧問桌、跑三段邊界檢核——其中大半對前者是空轉。

本檔定義兩條鏈與判定方式。判定在 **FRD 定稿後**做一次，之後不再重判。

## 判定：五條全中才是 lite

逐條檢查，**任一不成立即走 standard**。有疑慮的條目要點名寫出（哪一條、缺什麼證據），在確認時由 PO
判一次，不得以「有疑慮」帶過不判——判錯成 lite 由下方「中途升級」接住；「有疑慮一律 standard」
實測讓 lite 只佔約一成，小功能被迫付完整鏈的流程稅。

票面「產出物」列了 SAD **不算**使用者指定 standard；只有使用者明說才覆寫判準，且 decisions.md
分流列仍要寫五條判定結果。

| # | 條件 | 不成立的例子 |
|---|------|------------|
| 1 | **單表寫入**，無跨表交易 | 調價要同交易更新前一筆、主從單據、寫入後觸發別表 |
| 2 | **無狀態機**——沒有狀態欄位驅動的合法／非法轉換（軟刪除，以及專案已定案的「撞到已刪列→復活或建新列」處置不算） | 單據有草稿→送出→核准；停用／啟用會改變下游可用性 |
| 3 | **只新建一個畫面**（含其對話框） | 新建兩個以上畫面、跨頁精靈、從清單開子畫面再回填 |
| 4 | **無 migration，或僅為加欄位等級** | 補主鍵、改型別長度、建索引、新表 |
| 5 | **無金額計算、無權限分歧**（標準 CRUD 權限除外） | 單價驅動下游計價、刪除需獨立於新增的權限 |

> **條件 3 的界線**：在**既有畫面**的某一欄加掛選字／建議清單，**不計為第二個畫面**——
> 它沒有新版面、沒有新動線，只是一欄的輸入行為變了。單欄字典幾乎都有這種消費端加掛
>（如付款方式字典掛訂單表單、會員等級掛會員主檔），若計入，五條永遠不可能全中。
> 但**新建第二個畫面**（例：字典維護頁之外另做一個匯入頁）就計入，直接判 standard。

> **判定要看的是「這個功能實際要做什麼」，不是「這張表看起來多簡單」。**
> 「商品價目表」只有一張表、一個畫面，但它有調價交易（違反 1）、停用影響取價（違反 2）、
> 新增欄位＋金額欄位型別精度地雷（違反 4）、單價驅動下游計價＋刪除獨立權限（違反 5）——
> **五條中違反四條，是標準鏈**。反過來，「付款方式」「會員等級」這類單欄字典五條全中。
>
> ⚠ **但「單欄字典」不是 lite 的同義詞。** 「商品備註常用詞」同樣是單欄字典，
> 卻**違反兩條**：維護頁本身就是清單＋對話框兩個新畫面（違反 3）、欄寬擴大加廢除一支 view（違反 4）。
> 它的「新增撞已刪→復活」是軟刪除的既定處置，不算判準 2。
> **判定一律逐條過，不可用「這是單欄字典」一句帶過。**

## 兩條鏈

```
standard  explore → requirement → system-analysis → specify-backend
          → specify-frontend → dev-readiness → verifying-specs → linear-create

lite      explore → requirement → specify-backend
          → specify-frontend → dev-readiness(限縮) → verifying-specs → linear-create
                    ↑ 跳過 system-analysis
```

### lite 跳過 system-analysis，但它的必要產物不能憑空消失

SAD 的三流分析（工作流／資訊流／資料流）對單表 CRUD 幾乎是機械展開——那才是可以省的部分。
**下列四項是 SAD 真正的產出，lite 下改由他人承接**：

| SAD 原本負責 | lite 改由誰 | 落點 |
|-------------|-----------|------|
| 涉及資料表清單、ER 關聯 | `specify-backend` | BFS §1.3（本來就有這節，改為第一手產出而非 ref SAD） |
| 重用分析結論（既有可用／需擴充／需新建） | `specify-backend` | BFS §A.3，勘察明細照常落 `analysis/reuse-scan.yml` |
| US → API 對應 | `specify-backend` | BFS §6.1 端點總覽的「對應 US」欄 |
| **邊界盤點 B1~B10** | `specify-backend` **撰寫當下直接盤** | BFS §7／§8／§8.4；三段責任壓成兩段（原：SAD 盤點→BFS 落實→dev-readiness 複核） |

> ⚠ **邊界盤點不可省，只是換人做。** 它是抓漏主力——省掉它，省下的時間會在
> `dev-readiness` 或鏈末原封不動還回來，而且那時候要改的文件更多。

### lite 下 dev-readiness 的限縮

- **只跑** B1（空值必填）／B2（邊界值精度）／B3（唯一性含已刪除）／B9（既有資料相容）／B11（畫面內容完備）／B13（參數化來源一致）
- **跳過**領域特化維度（若專案有定義）——單表字典不涉流程狀態、成本歸集等領域邏輯
- B4（狀態轉換）／B5（並發）／B6（主從連動）／B10（排序完備）**若判定為 lite 就不該有內容**；
  一旦發現有東西可寫，代表**判定錯了** → 停下，改走 standard 補 SAD

### 顧問桌

lite **預設不開**。單表字典的 domain 風險集中在「軟刪同名怎麼處理」「值域語意」兩點，
這兩點由 PO 裁決而非顧問。命中 `consultant-desk.md` 的 domain 訊號（產品邊界／
客戶變體／聚合根歸屬）才單點問一次。

## 判定的執行

`requirement` 收尾時（FRD 已定稿、開放議題已收斂）逐條過上表五條，然後：

1. 以文字列出五條的判定結果與依據（一條一行），**不要只講結論**
2. `AskUserQuestion` 確認：`走 lite（推薦）` / `走 standard` — 推薦項依判定結果置首，
   description 寫明「省掉什麼、風險是什麼」
3. 判定結果寫入 `analysis/_context.yml` 的 `chain_profile`（`standard` | `lite`）與 `profile_reason`
4. 下游 skill 讀 `_context.yml` 取用，**不重判**

```yaml
chain_profile: lite
profile_reason: "五條全中：單表寫入、無狀態機、單一畫面、無 migration、無金額計算與權限分歧"
profile_decided_at: "2026-08-13"
```

## 中途升級（lite → standard）

lite 執行中發現任一判定條件其實不成立 → **立即停下告知使用者**，補做 `system-analysis` 後回到
standard 鏈。**不要**在 lite 鏈上硬撐著把 SAD 的內容塞進 BFS——那會產出一份四不像的規格書，
而且下游不知道該去哪讀。

升級訊號（出現任一即重判）：

- 寫 BFS 時發現需要交易，或需要跨表寫入
- 寫 BFS 時發現狀態欄位有合法／非法轉換要定義
- `dev-readiness` 在 B4／B5／B6／B10 抓到實質內容
- migration 從「加欄位」擴大成補主鍵、改型別或建索引

## 邊界（明確不做）

- **不因 lite 而降低規格品質標準**——欄位表完備性、驗證規則、例外清單、驗收條件一律照舊
- **不省 `verifying-specs`**——文件變少不代表跨文件一致性風險消失，反而因為 SAD 不在、
  BFS 一次承擔更多責任而更需要驗
- **不省 `dev-readiness`**——只限縮維度，不跳過
- CR（`--change`）模式不套用本分流，依既有文件範圍決定
