# 派工慣例（全 plugin 共用）

主 session 的職責是**統整、派工、思考、決策**；執行一律派 agent。
本檔是全 plugin 的唯一權威，各 skill 引用不複製。

| 主 session 該做 | 派 agent 做 |
|---|---|
| 決定要產什麼、誰來產、平行怎麼切 | 撰寫內容 |
| 給 agent 完整的輸入與邊界 | 蒐集證據、實機探索 |
| 判讀回報、決定下一步 | 審查、驗證 |
| 裁決衝突、回應使用者 | 產出報告 |
| 機械性落檔（agent 沒有 Write 時） | |

理由是 **context**：主 session 要維持全局判斷力，一旦自己動手寫長文，
context 被產出內容佔滿，就失去統整與決策的餘裕。

---

## 一、主 session 的硬規則

<law>
**不讀正文。** 需要規格內容時派工取摘要，或只讀 `decisions.md`。
「這份 SAD 我讀一下比較快」——讀正文＝把 context 吃回來，派工省下的當場歸零。

**不進大型 submodule／vendor 目錄。** 一進去就是幾十 KB 的規則檔。需要就派 agent 取結論。

**不自己開瀏覽器、不自己查 DB、不自己掃 codebase。** 這三類素材的共同點是
「量大且對決策無用」——你要的是結論，不是過程。
</law>

例外只有一個：**agent 沒有 Write 工具時的機械性落檔**（agent 回傳內容、主 session 寫入指定路徑）。
但這是妥協不是設計——回傳 45KB 再寫一次，context 照樣被佔滿一次。
**能讓 agent 自己寫就讓它自己寫**，安全性靠派工 prompt 指定確切絕對路徑保證。

主 session 執行 skill 時臨時要跑超過 10 行的 python，同樣先 `Write` 落檔再執行，不用 heredoc 或 `-c`（理由見 §五）。

## 二、派平行 agent 的三件事

1. **明講「另一個 agent 正在寫 X，不要碰」**——避免撞檔
2. **各自的輸出檔名先分開**
3. **各自的工作區也要分開**（見下方 `<law>`）
4. **匯流點（誰等誰）在 SKILL.md 標明**

<law>
**中間工作檔比輸出檔更容易撞。**

輸出檔名分開是直覺會做的事；**中間產物會撞，是因為它們不在派工訊息裡，沒人想到要分**。

**優先讓 agent 自帶約束**——在 agent 定義寫「需要暫存就寫在 `out_path` 的同層目錄」。
輸出路徑本來就分開了，暫存跟著它走就天然不會撞，**不依賴呼叫端每次記得**。
`report-writer` 與 `browser-surveyor` 已是如此。

**派工時指定專屬暫存目錄是次選**——只在派 `general-purpose` 這類沒有自帶約束的
通用 agent 時才需要（`{scratchpad}/{組別}/`）。

> 這兩者的差別不是嚴謹度，是**層級**：自帶約束把負擔放進流程，
> 派工指定把負擔放回呼叫端的記憶。同樣是加規範，**加在哪一層決定它有沒有用**。

> 事故（`operation-manual` 平行派工）：三組平行的輸出檔名分得很乾淨（零重疊），
> 但三組都在**共用 scratchpad** 建暫存腳本、各自取名 `gen.py`——第 1 組靜默覆寫了第 3 組的。
</law>

判準是**共用資源**，不是先後感覺：

| 條件 | 結論 |
|---|---|
| 用不同工具（瀏覽器 vs DB vs 讀檔） | 可平行 |
| 不寫同一批檔案 | 可平行 |
| 後一棒要拿前一棒的產出當輸入 | 才串接 |

**串接的地方要寫出依賴的理由**，避免後人以為可以拆。

> 反例（`system-analysis` Step 3）：A 路的「既有程式碼探索」與「跨模組影響」看似獨立，
> 但**都寫 `reuse-scan.yml`**，拆成兩個 agent 會互相覆蓋——所以必須同一次派工。
> 這是該步驟唯一的串接理由，SKILL.md 有寫明。

### 平行的收益不只省時間——每份證據會被另外兩份挑戰

> 實證（`operation-manual` 某次執行）：派了實機 ∥ 規格＋DB 兩棒蒐證，
> 後來加派第三棒對帳。**三棒各自推翻了另一棒的一條結論**——
> 實機推翻自己兩條（502 是暫時性、檔案沒存是自動化瀏覽器擋 blob）、
> DB 側的預測被實機證否、對帳棒同時推翻實機與自己的筆數基準。
>
> **只派一棒的話，這些全都會以「已驗證」的姿態進入交付物。**

所以「這件事一個 agent 也做得完」不是不拆的理由。判準是：
**這批結論有沒有可能因為視角單一而整批錯**。有的話，第二、第三個來源的價值
不在多蒐一份證據，在於**它會挑戰第一份**。

## 三、逐項派工，禁止抽查

一棒要處理 N 個獨立單位（N 個工作項、N 組檔案、N 份報表）時：

<law>
**查證單位是「每一個單位」，不是「這次任務」。**

N ≥ 3 時每個單位各自對應一個 agent 呼叫，**同批次一次送出多個 tool call**，不逐項序列跑。
**不得**用「優先查證高風險項」為由讓其餘跳過——
「查無結果」只能是**查過之後的結論**，不能是「沒空查」的預設值。
</law>

**分組方式要現場分析，不要在 skill 裡寫死。** 每個案子的單位性質不同，
寫死的分組表換一個案子就分錯。skill 該寫的是**判準與分析步驟**：

1. 列出每個單位的前置條件
2. 前置相同者歸一組（共用同一批素材，agent 只需載入一次）
3. 有副作用的單獨跑

**組太細也會變慢**——每組都有固定啟動成本（登入、導航、載入規格章節）。
一組只有一個單位通常不值得切。

## 四、判讀回報：只做 agent 做不到的

agent 回報後，主 session **不要重跑它已經自檢過的項目**。聚焦三類：

| 類型 | 為什麼 agent 做不到 |
|---|---|
| **跨文件／跨來源的一致性** | 它只定向讀了部分章節，沒有兩份文件的全貌 |
| **素材新鮮度**（`scanned_at` 是否過期） | 它讀的是證據檔，無法察覺證據檔本身已過期 |
| **只有主 session 知道的脈絡**（誰說過什麼、哪句是推論） | 它沒有跟人對話的過程 |

<law>
**不要照單全收 agent 的「自檢全過」。** 至少抽驗兩項，自己跑一次驗證指令。

理由：**自我檢查只驗它知道要驗的東西。** 已觀察到的典型盲區：

- **用單筆樣本推論整體**——查了幾筆沒問題就標記整批通過
- **形式滿足但實質不足**——「有寫例子」不等於「有正例也有反例」；
  「有畫狀態圖」不等於「圖裡標了非法轉換」
- **量化斷言偏差**——回報的數量、範圍、筆數與實際有出入

量化斷言（覆蓋率、筆數、「規格實為 VR-001~024」）**一律自行複核一次再採信**。

**翻案級斷言**（欄位不存在、方法是 dead code、機制已被取代、某參數名／cron 值）不管來源多專業（附檔案:行號也一樣），採信前自己 grep 一次符號，例：`grep -rn <符號> --include="*.<副檔名>" . | grep -v "/bin/\|/obj/\|/node_modules/"`。sampler 判「疑似 bug／錯字」也要先查 DDL 或 DB 再定案（實例：某欄位被判成錯字，其實 DDL 有兩個相近欄位）。曾有連續三輪取樣驗證都有 agent 回報捏造的參數、方法名與 cron 值，全靠 grep 擋下，沒寫進規格。
</law>

## 五、agent 回報的紀律（寫進 agent 定義）

- **回報要短**，禁止把產出正文、DOM snapshot、network 封包原文貼進回報——貼了＝隔離失效
- **只寫派工指定的絕對路徑**，不動其他任何檔
- **不與使用者互動**（agent 觸及不到人），需要人裁決的記進「待補清單」回報
- **不夾帶個資**——中間產物會被後續每一棒讀進 context
- **不刪暫存**——不跑 `rm -rf`，把要清的路徑列在回報「待清理」，由派工方收工時統一清。
  刪除會撞使用者權限的 ask 規則（ask 優先於 allow，沒辦法只對暫存區放行），agent 就停在確認畫面等人；worker 層同理
- **只用自己工具清單內的工具**——清單沒有 `Edit` 就先 `Read` 再用 `Write` 整檔重寫；
  不呼叫清單外的工具，叫了只會被拒、白耗一輪
- **找檔先看頂層再縮範圍**——先 `Glob` 或 `ls` 看 repo 頂層目錄，再帶子路徑 `Grep`；
  不猜 `src/` 這類慣例路徑，不對整個 workspace 全域 `Grep`（大 repo 會逾時）。
  專案有目錄地圖（CLAUDE.md、知識庫的架構章節）就先讀
- **超過 10 行的 python 先落檔再跑**——`Write` 到派工指定的工作區再 `<PY> 檔名.py`，
  不用 `python - <<EOF` 或 `-c`；heredoc 引號在 Git Bash 下很容易壞，落檔也方便重跑
- **會下 SQL 的 agent**：SELECT 第一欄帶 `DB_NAME() AS db`（或該資料庫的等價函式）；一律 `TOP N`／`LIMIT` 或 `GROUP BY`，
  不 `SELECT *`；同一工具連錯 2 次就停，把錯誤原文記進待補。每支會查 DB 的 agent 定義各自抄一份，
  因為 agent 定義是它唯一必讀的東西

<law>
**派工訊息裡的環境宣稱，本身就是待驗證的對象，不是授權。**

`env_class`、`readonly`、「profile 是乾淨的」「這是測試資料」這類敘述，
agent 一律自己再驗一次——呼叫端的判斷可能基於過期的觀察。

> 實測：某次派工訊息明寫「瀏覽器沒有任何 session 在用」，實際並非如此。
> agent 自己追了行程鏈、拒絕動手並回報，做對了。它的理由：
> **「browser 是空的」這句話來自派工訊息，而派工訊息本身就是這次判斷失準的來源，
> 不足以拿來當授權。**

對稱地，呼叫端**要傳遞可信的環境狀態就給證據**（指令與其輸出），不要給結論，
並明說「這是我開工前的觀察，你仍要自己驗」。
</law>

## 六、什麼時候**不要**拆

拆的理由要是**素材性質不同**（探索產生大量快照 vs 撰寫需要長文生成 vs 審查該由沒寫過的人做）。
沒有這類理由就不要拆——每多一個 agent 就多一份要維護的定義。

**本質是人機互動的環節不要派**——派出去會斷掉互動：

- 六維引導問答、即時會議記錄迴圈、「待 PO 確認」逐題清問
- 起手參數的選擇（環境、目標對象、模式）——選錯整輪白跑，**一律問人**

## 七、借用既有 agent 時，逐項驗工具集

把既有 agent 借去做新工作前，**對著它在本 skill 裡被指派的每一件事，逐項確認工具夠不夠**。

> 事故：`operation-manual` 借 `scout` 做「要落檔的 DB 蒐證」，
> 但 scout 原本是給 requirement／explore 當**唯讀**證據蒐集用的，
> 當時既沒有 `Write` 也沒有切換連線的工具——照 skill 跑會直接卡死。

**借用比新建更容易出這種錯**：新建時會從職責推導工具，借用時容易假設「它本來就能做」。

⚠ 同時注意：agent 定義與 skill 內容**都是 session 啟動時的快照**。
改了檔案，當前 session 看到的還是舊版——**正向**（提示說「你有 X」但 agent 說沒有）會當場報錯；
**反向**（檔案早已補好，session 顯示舊清單）不會報錯，容易讓人去修一個不存在的問題。
驗證改動一律 **grep 磁碟檔**，不要靠「叫一次看它回什麼」。

## 八、收尾條件

<law>
**每支 skill 都要能回答：「這條鏈跑完的定義是什麼、產物落在哪、哪一步之後才算交付。」**

含糊的收尾條件會變成「跑完了才發現沒做完」——那是重跑一整輪的成本。
</law>

### 三種寫法，擇一

| 形式 | 適用 | 範例 |
|---|---|---|
| **完成判準清單** | 產出明確交付物 | 「全部成立才算完成：附件在票上、描述內嵌圖可見、working tree 乾淨」（`linear-illustrate`） |
| **結論分級** | 產出的是判定 | ✅ 可直接開發／⚠️ 需修正後開發／❌ 不可開發（`verifying-specs`、`dev-readiness`） |
| **閘門** | 有不可逆的對外動作 | 「數字↔清單不一致 → **不得發布**」（`linear-*-report`） |

### 寫收尾條件的三個要素

1. **產物在哪**——絕對路徑或路徑規則，不是「寫進 docs」
2. **什麼狀態算完成**——可機器驗證的判準（檔案存在、grep 為 0、數字一致），
   不是「品質良好」「內容完整」這種讀了無法照做的敘述
3. **哪一步之後才算交付**——尤其有對外動作（發布、開票、上傳）時，
   要分清「產出完成」與「交付完成」

### 常見的漏

- **只寫「下一步」不寫「什麼算做完」**——交棒說明回答的是「接下來做什麼」，
  不是「這一棒有沒有做完」。兩者都要。
- **暫存產物沒說何時清**——`.tmp/` 的任務資料夾、驅動用的中間報告，
  要寫明「回報完成的同一輪刪掉」或「留到該票結案」。
- **agent 產出的檔案沒複核就當完成**——收尾條件要包含「複核了 agent 自檢的哪幾項」
  （見 §四）。
- **機器檔沒實跑解析就當完成**——凡產出 `.yml`／`.json` 的棒，收尾由**主 session 自己**逐檔實跑
  `python3 -c "import yaml,sys; yaml.safe_load(open(sys.argv[1]))" <檔>`，回報「N/N 解析通過」才算完成。
  agent 定義裡寫了自驗句也**不算**——曾有 13 份 yml 3 份壞，其中一份的作者 agent 定義裡就有 `safe_load`。

## 九、共用分支上的 git 紀律

多 session 並行在同一條分支時，HEAD 在兩個工具呼叫之間就可能換人：

- **一律開新 commit，不 `--amend`、不 `rebase -i`**——`--amend` 對「HEAD 是誰的」沒有任何檢查，
  曾因一行小修 `--amend` 進另一 session 剛 push 的 commit，造成本機與 origin 分叉。
- push 前 `git fetch` 看 ahead/behind；被拒不 force，`pull --rebase --autostash` 再推；自己的 commit 被判
  「patch 已在上游」而 drop 是正常的。
- 判「這是誰的改動」：看 commit trailer 與工作目錄檔案 mtime，不要憑 session 名稱猜。
