# 分析嚴謹度閘（上游分析下結論前）

> 在 `explore`／`requirement`／`system-analysis`／`linear-triage` 根因分析等上游階段，
> 下**結論**前逐項過這六條閘。每一條都對應一次真實踩過的坑。碰到不確定就先查證，不憑印象定論。
> 經 `shared-preludes.md` 適用於所有 sa-flow skill；顧問桌的「FRD 例外」對應第 5 條（見 `consultant-desk.md`）。

## 六條閘

1. **來源查齊**：下「需新建／沒有／就是這樣」結論前，掃過 **codebase＋docs（同義功能目錄）＋票務系統（既有票、重複票）＋DB 實資料＋該模組最近的 commit**。
   > 坑：把「需新建」標錯——既有規格鏈和票樹都在，只是沒查 docs 與票；開了重複 Bug 票——沒查最新程式碼與 git log，功能早就修好。

2. **深度到源頭**：欄位空、行為異常時，追「**為什麼空／為什麼這樣**」的上游寫入鏈與根因，**不是**找「哪張表有值」改讀別表把源頭蓋掉。
   > 坑：某日期欄位空，真因是上游排程漏寫狀態，差點改讀另一張冗餘表把源頭遮蓋。

3. **現況對齊**：改規格或寫 CR 前，**先勘察後端＋前端已完工的實際行為**與近期修復票，依實況對齊，不在文件之間互抄。
   > 坑：照舊文件抄出一個實作裡不存在的設計。

4. **維度齊全**：分析權限、流程時列出**全部維度**（例：權限要查建立人、系統固定帳號，不拿某個分類欄位當閘門）。
   > 坑：業務查詢權限漏了一個分析維度。

5. **domain 邊界必把關**：碰到**產品邊界、多產品共庫的鑑別欄位、客戶變體、聚合根／狀態機、整合邊界** → **一定交 domain 顧問（`domain-advisor`）**（大量蒐證可先派 `scout`），不憑印象定論。規格鏈上叫過一次即滿足，不要求每個階段各叫一次。
   > 坑：同名欄位在不同產品線語意不同；同一支功能有多種客戶變體；舊系統與新系統的欄位型別並存是刻意的，不是漂移。

6. **證據優先於靜態推論**：涉及資料語意或行為，用 **唯讀 DB 實查＋封包／DB 實證**，不只靜態讀碼下結論。設計庫可能落後實際模型（沒有 migration 歷史時尤其如此）。
   > 坑：明細重複的根因要靠 Network＋DB 時戳實證，靜態分析會定錯論。

## 結論分級

分析結論一律標示信心度：**Confirmed**（有證據，附出處）／**Likely**（合理推論，寫明假設與待驗證項）／**Unknown**（查不到，寫明原因）。
不把推論寫成事實；證據不足就寫「證據不足」，不寫「應該是 X」。

## 通過條件

- 每條都是「已查」或「不適用（附理由）」才算過閘；**有 domain 邊界卻沒叫顧問＝未過閘**。
- 過閘紀錄不必寫進交付文件（屬分析過程）；但結論若與某條牴觸，文件要標明依據。
