# 邊界維度庫（SA 盤點 ／ DoR 驗證 共用）

> **單一維度定義權威**。同一個維度在上下游用**同一個編號**，避免 SA 一套切法、dev-readiness 另一套切法，
> 導致重疊部分重複勞動、縫隙部分無人認領。

## 三段責任，同一份維度

| 階段 | Skill | 怎麼用 | 產物 |
|------|-------|--------|------|
| **① 盤點**（規格寫之前） | `system-analysis` Step 6.5 | 逐維度問「這個功能在這個維度上會怎麼壞？」，推出預期系統行為 | SAD §6.6 邊界與例外清單 |
| **② 落實**（規格**撰寫當下**） | `specify-backend` / `specify-frontend` | 寫 VR/BR、欄位驗證、狀態控制那幾章時，**逐維對照 §6.6 逐條落地**——見下節 | BFS §7／§8／§8.4、FFS §4／§5 |
| **③ 複核獵漏**（規格寫完之後） | `dev-readiness` | 驗「②有沒有真的落實」＋獵 ①②都沒想到的漏網 | 就緒度報告 + 裁決回寫 |
| **④ 複查** | `verifying-specs` | 查 SAD §6.6 是否每個適用維度都有結論（含「不適用」） | 驗證報告 |

> **② 是最省的一段。** 過去邊界的主要發現點在 ③——
> 意思是「BFS/FFS 都寫完了，才發現有五條邊界沒寫」，然後退回去補。
> 而 BFS §7 本來就是邊界的天然落點：**寫那一章的當下對照，比事後獵回來便宜得多**。
> ③ 因此從「主要發現點」降為「複核 + 獵漏網」——它仍然要獵，但獵到的應該是少數漏網，
> 不該是整批未落實項。**③ 一次獵出大量阻塞，代表 ② 沒做，不是 ③ 做得好。**

## ② 撰寫階段落實對照（BFS／FFS 專用）

撰寫下列章節時，**打開 SAD §6.6 逐條對照**，確認每條結論都已在本章落成具體規格。
每個維度的落點分兩層：**契約行為**（系統對外怎麼反應——回應碼、訊息、擋下或降級、資料語意）由 SA 定案寫進規格；
**實作手段**（鎖種類、快取、佇列、重試與補償做法、儲存位置）不定案，寫成 TD 留置（約束＋現況＋陷阱，見 `decision-record.md`「技術決策留置」）。

| 撰寫中的章節 | 對照維度 | 落實成什麼 |
|------------|---------|-----------|
| BFS §7 驗證規則（VR/BR） | B1 空值、B2 邊界值與精度、B3 唯一性、B9 既有資料相容 | 每條邊界一條 VR/BR，含**具體判斷條件與錯誤訊息字串** |
| BFS §2.4 狀態轉換 | B4 狀態轉換合法性、M1 單據狀態流轉 | 合法轉換表 + **非法轉換的系統回應** |
| BFS §8 例外處理 | B7 權限可見性、B8 整合一致性 | 每個例外的回應碼與處理方式（契約行為，SA 定）；B8 的重試／補償**手段**寫 TD |
| BFS §8.3／§8.4 | B6 主從連動、B5 並發衝突 | **契約行為**：表頭重算時機、衝突時擋下／後寫覆蓋／合併、回應碼與訊息、控制欄位是否進契約；**實作手段**（鎖種類、佇列、快取）寫 TD |
| BFS §6.0 列表 DoR | B10 排序完備性、B12 輸出管道中立 | 排序五要素（欄位＋決勝欄＋NULL 位置＋序語意＋是否可切換） |
| FFS §4 欄位驗證 | B1、B2、B3 | 前端驗證時機與訊息（ref BFS VR 同編號） |
| FFS §5 狀態控制 | B4、B7 | 各狀態下的欄位可編輯性與按鈕顯示 |
| FFS §2 畫面內容規格 | B11 畫面內容規格完備性 | 四類欄位群齊備、來源欄無空白 |
| **全文件（寫完前掃一次）** | **B13 參數化來源一致性** | 每個複述兩次以上的數值／格式／長度都標明來源；有設定檔落點者明寫「沿用 {某規則} 同一推導值，不得另寫死常數」 |

**對照方式**：SAD §6.6 每條結論在本文件找得到落點 → 標記已落實；找不到落點 → **當場補寫**，
補不出來（資訊不足）→ 併入該 skill 的疑問點總清查，依「互動詢問規範」逐題問。
**不得**留給 `dev-readiness` 收拾——那是把便宜的事拖成貴的事。

> SAD 不存在或 §6.6 從缺時（CR 流程、簡化鏈），改為直接對照本檔 B1~B10／M1~M4 維度，
> 標準相同：每個適用維度在規格裡都要找得到答案。

**問題必須以該功能真實的 DB／業務語境具體化，不照抄本檔通用問句。**
本檔是彈藥庫，不是要逐條抄進文件的清單。

## 通用維度

### B1 空值 / 必填缺漏
- 每個必填欄位未填時的行為？（擋下 / 預設值 / 報錯訊息）
- DB 可為 NULL 的欄位，規格有沒有定義 NULL 的**業務語意**？
- 選填關聯（FK）為空時，下游計算 / 顯示如何處理？
- 查無結果、空明細、空關聯回傳什麼？

### B2 邊界值與精度
- 數值欄位的 min/max？數量為 0 或負數允不允許？
- 字串長度 / 位元組上限？超過如何回應？（多位元組字元依資料庫編碼計算）
- decimal 精度與四捨五入規則？
- 日期邊界：起訖相等？跨日 / 跨月 / 跨年？未來日期允不允許？

### B3 唯一性 / 重複
- 唯一性檢查的範圍？是否排除已刪除（軟刪）資料？
- 編號 / 流水號的產生與衝突處理？
- 明細重複品項允不允許？

### B4 狀態轉換合法性
- 列出**所有狀態** + 合法轉換與非法轉換；嘗試非法轉換時系統如何回應？
- 此操作在哪些狀態下可執行？哪些狀態禁止？
- 終態後的操作（已結案 / 已核准是否還能改 / 刪）？
- 狀態轉換是否有前置條件（子單據齊備、審核通過）？

> 📎 盤點結果回補 SAD §2.3 狀態流轉——補非法轉換與並發衝突，而非只畫正常路徑。

### B5 並發衝突
- 同一筆資料多人同時編輯 → 衝突時系統**行為**是擋下、後寫覆蓋還是合併？（契約，SA 定）用哪種鎖是手段（TD 留置）
- 重複提交（快速雙擊 / 重送）如何去重？
- 主從表：表頭與明細同時被不同人改？
- 排程 job 與使用者操作同時觸發同一資料？
- 長交易期間資料被他人改動的處理？

### B6 主從連動
- **明細增刪後表頭（數量 / 金額 / 狀態）是否重算？何時算？由誰算？**
- 表頭刪除時明細如何處理？（連鎖刪 / 擋下 / 孤兒檢查）
- 跨表級聯：刪除主檔對明細 / 關聯的影響？
- 明細排序與項次規則？→ 見 B10

> ⚠️ 表頭重算邏輯過去是**兩套切法之間的縫**：SA 的「主從」只想到並發與級聯刪除，
> DoR 才問到重算，那時規格已寫完只能回頭補。盤點階段就要認領。

### B7 權限 / 可見性
- 哪些角色可執行此操作？無權限者呼叫 API 的回應？
- 跨組織 / 跨廠 / 跨客戶 / 跨租戶的資料可見性邊界？
- 欄位級權限（某些欄位唯讀 / 隱藏）？
- 狀態相關權限（僅特定角色可核准）？

### B8 整合 / 一致性
- 交易邊界：哪些操作必須原子（表頭 + 明細同生共死）？
- 外部系統（ERP 同步 / 通知 / 檔案服務）失敗時，主流程中斷或降級？重試？
- 多步驟操作部分成功時的回滾 / 補償？批次中第 N 筆失敗，前 N-1 筆如何處理？
- 逾時行為？

### B9 既有資料相容性
- 歷史髒資料 / 遷移殘留是否符合新規則？不符時如何顯示 / 阻擋？
- 新增必填欄位對既有資料的回填策略？
- schema 變更的影響範圍與遷移需求 → 同步填 SAD §4.4 資料影響評估。

### B10 排序完備性
僅在功能含多筆資料呈現時適用（清單 / 明細 / 下拉 / 匯出 / 報表）。
判定基準見 `references/sort-order-standards.md`，重點：

- 每個多筆區塊都有預設排序？（最常漏的是明細與下拉選單）
- **排序鍵在該資料集唯一嗎？** 不唯一卻沒定決勝欄 → 分頁會跨頁重複／漏筆
- 排序欄可為空卻沒定 NULL 位置？字串型編號卻沒標字面序／數值序？
- 有分頁的清單標成前端排序而無理由？匯出排序與畫面不一致而未說明？

### B11 畫面內容規格完備性
**僅 dev-readiness / verifying-specs 階段適用**（SA 盤點時 FFS 尚未存在）。
完整檢查項見 `references/screen-spec-format.md` 與 `verifying-specs` 的 checklist。重點：

- 整個功能的四類欄位群（查詢條件／查詢結果／新增表單／編輯差異）齊備？
  單一畫面不適用者有明寫「無」或註明由同功能其他畫面承載？
- 有無省略號（「等」「欄位1、欄位2…」「依實際需要增減」）？
- 每個顯示欄位都有來源（Response 欄位名 或「前端計算：{公式}」）？
- 編輯模式與新增模式的差異已註明（哪些唯讀、哪些依狀態鎖定）？
- 操作流程只寫功能特有流程與偏離標準 CRUD 動線之處？有無把標準動線重畫一遍？
- 「重要性」欄有分級？**3 欄以上全標「主要」**時有說明理由？
  （全欄同級＝沒有分級，前端無從決定摺疊順序；這種退化不會有人回報，是靜默失效）
- 來源欄的層次對應文件階段？FFS／Dev 票應填 Response 欄位名或 `前端計算：{公式}`，
  不該留 FRD 階段的業務語意（`參照{主檔}`）或 `{占位符}`
- 標「前端計算」的欄位，後端 Response 真的不回該值？
  （後端會回卻寫前端計算＝把計算職責靜默畫給前端，會前後端各算一套）

### B12 輸出類需求的管道中立
僅在需求含匯出 / 列印 / 報表時適用。

- 只定義**輸出內容**（欄位、排序、分組、分頁、紙張、檔名規則、觸發點）？
- 有無指定**產出管道**（範本機制 / library / pipeline / 既有匯出元件）？→ 管道是開發階段決策
- 輸出欄位逐欄實名（不得「同畫面欄位加幾個」）？
- 空結果、超量筆數、權限不足時的輸出行為？

### B13 參數化來源一致性
**全階段適用**（SA 盤點／規格撰寫／dev-readiness 皆須驗）。

規格裡的每個數值、格式、長度、閾值，只要出現**兩次以上**，每次都要能回答
「**這個值是誰算出來的**」。

- 每個魔術數字（長度、位數、上限、預設值、格式樣式）是**寫死的常數**，
  還是**從設定檔／schema／既有規則推導**而來？
- 同一個值在多處出現時，各處的**來源**一致嗎？
  一處寫「自設定推導」、另一處寫字面值 → 缺陷。
- 值有設定檔落點時（取號設定、系統參數、客戶設定），**驗證端與產生端取自同一個推導結果**，
  還是各算一次？
- schema 決定的界限（欄寬、精度、值域）被複述進規格時，有標明來源與勘察日期嗎？

**為什麼跨文件比對抓不到**：A 寫「8」、B 寫「推導成 8」，**字面完全一致**——
一致性檢查永遠不會報。要抓到必須問「誰算的」，不是「兩邊一不一樣」。

**掃法：先過濾出規範性語句，再問誰算的。** 不要按出現次數排序——
實測「8 碼」在四份文件出現 **40 次，其中只有 2 次是缺陷**，
其餘全是敘述性複述。高頻不代表有問題，真缺陷藏在這三類語句裡：

| 規範性語句 | 為什麼是它 |
|---|---|
| **VR／BR 的判斷條件** | 寫死就會與產生端分裂 |
| **TC 的期望值** | 寫死則設定調整後期望值過期**但測試仍照跑**，通過與失敗都不具意義 |
| **欄位規格的長度／格式** | 下游直接照抄進實作 |

反過來，這三類可以放行：實證統計（DB 實查的筆數、比率）、
歷史行為敘述（舊系統當時產生什麼）、具體範例值（TC 的測資如 `26-00123R10`）。

**修法不是逐處改寫，是設一個唯一定義處。** 在最上游的規格文件裡放一張推導鏈表
（參數 → 推導式 → 現行值），其餘章節一律引用它。逐處改成公式會讓正文難讀，
而且下次還是會有人在新章節寫死。

**失效是靜默的**：設定調整後推導端跟著變、寫死端不動，兩者分裂但不拋錯、不報警，
只是行為悄悄不一致。

> 實例：v1.0 把單據流水號格式定在系統設定表，取號以 `len(prefix)+SerialNumberLength` 推導出 8 碼。
> v1.1 新增的衍生號驗證卻寫「長度 ≥8 且前 8 碼符合 `YY-XXXXX`」——設定一旦調整，配號會變、驗證不會。
> **`dev-readiness` 12 個維度與 `verifying-specs` 五輪皆未攔下**，正因兩處字面一致。


## 領域特有維度

> 依 `references/analysis-standards.md`。盤點與驗證兩階段都適用；以下以訂單履行類系統為例，其他領域依同樣形狀自訂。

### M1 單據狀態流轉
- 單據（如訂單）在 草稿 → 處理中 → 完成 / 取消 各階段，此操作的合法性？
- 已出貨 / 已完成 / 已結案單據的可改範圍？

### M2 流程步驟依賴
- 步驟順序約束？跳序 / 倒序的處理？
- 前一步驟未完成時後一步驟可否啟動？

### M3 金額歸集
- 金額（成本、應收、庫存價值）歸集的觸發時機與重算邊界？
- 數量 / 單價異動對已歸集金額的影響？

### M4 階層結構
- 多階結構（組合品、分類樹、組織層級）的展開邊界？循環引用偵測？
- 結構變更對進行中單據的影響範圍？

## 收斂原則

- **DB／業務接地優先**：只問該功能真實成立的邊界，剔除不適用維度。標「不適用」也是結論。
- **訊號不稀釋**：寧缺勿濫，避免大量低價值假問題淹沒真阻塞。
- **業務層例外不重抄**：單一 US 的 Given-When-Then 例外歸 FRD §2，本維度庫只補**系統層**邊界。
