## §2.5 計算邏輯 User Story 完整範例

> **User Story 示範（採購單情境）**
>
> 身為採購人員，當我新增採購明細時，系統應自動計算「明細小計」與「合計金額」。
> 計算結果需與財務系統對齊（四捨五入至小數點後 2 位），避免因精度不一致產生帳差。
>
> 實際資料驗證（請用 MCP 查詢真實資料或以業務情境模擬）：
> - 訂購數量 = 150 pcs，單價 = 12.6667 → 小計 = 150 × 12.6667 = 1900.005 → **1,900.01**（四捨五入，遠離零）
> - 合計含稅（稅率 5%）= 1,900.01 × 1.05 = 1995.0105 → **1,995.01**（中間值不捨入，最終才捨入）

## §8.4 並發衝突處理 完整範例

> **User Story 示範（採購單並發情境）**
>
> 採購主管（UserA）開啟採購單 PO-20240315-001 準備核准；
> 同時，採購人員（UserB）剛修改了同一張單的訂購數量並儲存成功。
> 若無並發保護，主管的核准動作會以舊的 `LastModifiedTime` 送出，
> 後端應比對時間戳並回傳 HTTP 409，要求 UserA 重新載入。

**樂觀鎖實作規格範例**：

| 項目 | 規格 |
|------|------|
| 比對欄位 | `LastModifiedTime`（datetime，精度至毫秒） |
| Request 傳入方式 | Request Body 包含 `lastModifiedTime: "2024-03-15T10:30:00.123"` |
| 衝突判斷 | `entity.LastModifiedTime != request.LastModifiedTime` |
| 衝突回應 | HTTP 409 Conflict |
| 衝突訊息 | `「資料已被他人修改，請重新載入後再試」` |
| 前端行為 | 接收 409 後自動重新讀取最新資料，使用者重新操作 |
