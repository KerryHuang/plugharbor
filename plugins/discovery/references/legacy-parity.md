# 舊系統移植的 parity 模式

> 適用：由舊系統分析（舊系統分析報告，不限技術）起頭的規格。
> 要整個重新設計就不走舊系統分析，直接照 `spec` 寫新規格，不受本檔限制。

**移植期間，新系統的邏輯方向預設對齊舊系統**——資料口徑、寫入形狀、值域語意兩邊一致。
新舊系統常會長期並存、讀寫同一份資料；新系統「更好的設計」若改變共用欄位的口徑，
舊系統端會讀到錯的數字，而且沒有錯誤訊息，只有兩邊報表對不上。
使用者對兩套系統行為不一致的反彈，通常也大於對「舊做法」的反彈。

## 對齊面（分析／設計時逐面檢查）

| 面向 | 對齊要求 |
|------|---------|
| 共用欄位口徑 | 舊欄位的計算範圍與語意沿用舊系統，不縮不擴；顯示語意差異放在顯示層 |
| 明細寫入形狀 | 會被舊系統讀到的明細，寫入形狀與舊系統同構 |
| 值域 | 共用欄位不引入舊系統不認得的新值；必要的新值放新表 |
| 單號格式 | 沿用存量格式（位數、年制），不換制 |
| schema | 共用的舊表盡量不動；新欄位依專案慣例另開擴充表 |
| 軟刪語意 | 沿用舊系統的軟刪做法與過濾條件 |

純新表（舊系統看不到）的設計不受此限。

## 偏離四類

新舊系統之間的每一項差異先歸類，**歸類決定要不要問**：

| 類別 | 定義 | 要不要裁決 |
|---|---|---|
| **P-UI** | 版面、空／載入／錯誤態文案、responsive、欄位排序、鍵盤動線——**不改欄位集、不改規則、不改口徑、不加後端契約** | 不問，直接做 |
| **P-PLATFORM** | 新平台技術上必要的差異：API 契約形狀、平台權限機制、平台既有匯出／列印元件、排序決勝欄 | 不問，但在設計文件「決定」標「P-PLATFORM」 |
| **P-FIX** | 舊系統既有 bug（漏算、吞錯、算式錯） | **預設直接修在新系統**；PO 只裁「哪些不修」，並逐條標「修了之後兩系統結果會不會不同」 |
| **P-EXT** | 新欄位、新規則、新畫面、新流程、廢除舊規則 | **預設不做**；要做須符合下方三要件並經 PO 明示，且列在「決定」的 `### 偏離候選（預設不做）` 小節，不散在正文 |

### 允許偏離的三要件（缺一不可）

1. 屬 **bug 修正或資料完整性缺陷**，不是單純「新設計比較好」；
2. 有 **PO／使用者明確裁決**（記在設計文件「決定」，舊範本 §5 決策表）；
3. **評估過並存影響**並記在設計文件「限制」（舊範本 §6 風險）：偏離後舊系統讀寫這份資料會發生什麼、是否要先停用舊功能。

## 追溯編號

- 舊系統分析產出的規則以 `FX-` 前綴編號（如 `FX-VR-03` 驗證規則、`FX-BR-07` 業務規則）。
- parity 鏈中，每條 VR／BR 必須對到 `FX-` 編號，**或**設計文件「決定」中一條標 P-FIX／P-EXT 的裁決；兩者皆無＝孤兒規則。

## 標記與落點

- **標記**：設計文件開頭行加「來源：舊系統移植（分析報告路徑）」（舊範本為表頭一列「來源｜舊系統移植」，兩種都認）；`spec`、`spec-check` 開工讀到就套用本檔。不提供關閉旗標：要偏離就逐條走 P-EXT 裁決。
- **舊系統分析**：遷移建議逐條標「對齊」或「偏離（附三要件對應）」；報告另立「偏離候選」節，只列 P-FIX 與變體，**不列新功能**。
- **spec**：不挖隱含需求；BR 只寫舊系統既有行為（追溯 `FX-` 編號）與 P-FIX，P-EXT 只能進「決定」的 `### 偏離候選（預設不做）`；「驗收」含「並存期語意分裂」的反例（舊範本 §3.4 邊界）。
- **discovery-domain-advisor**：做**對齊審查**（哪裡會與舊系統不同、既有 bug 要不要照搬），不挖隱含需求。
- **spec-check**：找到的缺口先查舊系統現行行為——有 → 建議答案就是舊行為，標「對齊」；舊行為是 bug → 標 P-FIX；舊系統沒有、也非平台必要 → 標「不處理（parity）」，不列阻塞。
