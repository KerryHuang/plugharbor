# 票描述範本與通則

票是給人翻的，不是讀的。所有範本由 `tickets:ticket-create` 取用；標題、描述一律技術中立，只描述行為與契約。

## 通則

1. 描述第一個標題用 `##`，不重複標題。
2. 只放票生命週期內穩定的內容：交付範圍、對齊的需求編號、驗收條件。既有檔案路徑、套件選型、實作做法不進票（開票到開工常隔一至兩週，過期內容是辨識成本）。
3. 規格明細不抄進票，用「檔案路徑 §章節」指路，粒度到子節。
4. 驗收條件（AC）至多 5 條，每條是可觀察的結果，對齊需求編號（若規格有）。機械性項目（逐欄驗證、CRUD 基本操作）由規格保證，不展開成 AC。
5. QA 票只寫 E2E 情境，不寫單元測試維度。
6. Bug 票必填「根因分析／程式碼問題定位／修改細節」；根因未知時寫「最可能位置＋排查方向」，不杜撰行號或機制。
7. 有規格檔就附「參考文件」表；沒有就整段省略。
8. 最後一行放票源 flag（見 `create-dispatch.md`）。

## 標題格式

單票與父票：`{標題}`（Bug 加前綴 `【Bug】`）。子票：父票標題＋使用者給的拆分名稱。專案已有標題慣例（盤點時看同主題既有票）以慣例為準。

## 單票：Feature

```markdown
## 參考文件

| 文件 | 路徑 |
|------|------|
| 規格 | `{規格路徑}` |

## 目標

{為什麼要做、不做的影響——至多 3 句}

**包含**：{範圍}
**不包含**：{排除項目}

## 規格指路

{行為與契約的明細在：`{規格路徑} §章節`}

## 驗收條件（≤5）

- [ ] {可觀察結果}
```

## 單票：Bug

```markdown
## 問題描述

{一句話現象}

## 重現步驟

1. {步驟}

## 預期行為／實際行為

- 預期：{…}
- 實際：{…}

## 根因分析

{機制，不是現象複述}

## 程式碼問題定位

`{檔案相對路徑}:{行號}`，{函式或方法}：{此處為何造成問題}

## 修改細節

{建議方向，僅建議}

## 影響範圍

{受影響的功能、資料、使用者}

## 驗收條件

- [ ] {修好後可觀察的結果}
- [ ] {既有相鄰行為不變}
```

## 父票與子票

父票只做總覽：目標（至多 3 句）、子票清單（建立後補票號）、整體驗收條件（≤5）。子票照單票範本寫，只留該子票範圍的段落。

## 估點、期限、優先級、指派

`ticket-ops` 契約不含這些欄位。使用者要求時，優先級與期限寫在描述最上方一行文字，指派與估點列入回報的「需手動設定」清單，不自行猜工具欄位。
