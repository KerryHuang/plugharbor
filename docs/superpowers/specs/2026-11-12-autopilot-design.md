# 自動駕駛模式設計

日期：2026-11-12。狀態：草稿，已經過 builder check，待使用者核准。

## 意圖

無人值守（`workspace:unattended`）會連續推進工作單元，直到使用者回來，但路線要在當下的對話裡講定，使用者一送訊息它就停。使用者要的「自動駕駛」改成照專案的 `docs/roadmap.md` 一段接一段做，使用者在不在場都一樣，只有使用者明確暫停才停。

起因：lifecycle 2.4.0 才讓 roadmap 段表成為可以機械讀取的開發順序（列序就是順序，`feature_checklist.py --open` 會算出「可開工」）。有了這份順序，「下一步做什麼」就不必再由人講。

## 目標

- 路線從 roadmap 來：每段開工前重讀 `docs/roadmap.md` 與功能清單，取第一個未完成段來做。
- 使用者在場或不在場都適用，同一套規則。
- 使用者插手時處理完就繼續；只有「暫停」「停止自動駕駛」這類明確指示才停。
- 一段做完時，同一個 commit 更新 roadmap 段狀態與清單勾選，再開下一段。

## 非目標

- 不做新的控制通道（不讀旗標檔、不做跨 session 的暫停指令）。使用者已經能用 Remote Control 從手機進同一個對話。
- 不自己設計 roadmap 上的佔位段，也不替它切子段。
- 不自己主動改 roadmap 的段序：自己發現順序該調整時，只寫進報告。使用者明確指示改方向時，照指示寫回 roadmap（見「做法」）。

## 反目標（技術上能跑，使用者仍會認為失敗）

- 使用者送一般訊息，它就整個停下。
- 替一整塊還沒設計的產品（例：HRM）決定長什麼樣子。
- 段做完了，roadmap 或清單卻沒更新，下次 `--check` 報不同步。

## 使用者已決定的事

- **適用情境**：一個模式，在不在場都照 roadmap 跑，直到明確暫停。
- **要拍板的使用者行為類決定**：照推薦做，並且照常合併、繼續往下，和無人值守相同；接受翻盤時可能重做後續段的代價。
- **插手方式**：在同一個對話打字。一般訊息當插入事項或改方向，處理完繼續；說「暫停」才停。
- **暫停的節奏**：不再開新的工作單元，手上這個做到合併，或做到分支乾淨的狀態就停，交出報告。狀態保留，使用者說「繼續自動駕駛」就接回。
- **沒有合併授權的專案**：不開自動駕駛。開場檢查專案設定有沒有授權合併，沒有就趁使用者在場問完、寫進設定；問不到就不開，改走一般的無人值守。
- **遇到只有佔位、沒有設計的段**：停在那一段並推播通知使用者，同時整理好設計要問的問題草稿；後面若有不依賴它、而且已有設計的段，就先做。

## 做法

### 形式（主控決定）

做成 `workspace:unattended` 的一個模式，不另開新 skill。單元流程、裁決帳本、資源規則、停下條件、異常判讀、回來報告全部沿用；差異寫在新檔 `skills/unattended/references/autopilot.md`，SKILL.md 只加一小節指過去。理由：另開 skill 會有兩份流程要同步，常駐 description 也要多一條。

description 加「自動駕駛」「照 roadmap 跑」兩個觸發詞。依 repo 規則，description 不得變長，所以要同時刪減既有字句，抵銷增加的長度。

### 與無人值守的差異

| 項目 | 無人值守 | 自動駕駛 |
|---|---|---|
| 路線 | 開場講定的工作單元 | 每段開工前重讀 roadmap，取第一個未完成段；一段＝一個或多個工作單元 |
| 開場 | 沒設定就問，問不到就不合併 | 必須有合併授權，否則不開 |
| 什麼時候停 | 使用者送出新訊息 | 使用者說「暫停」或「停止自動駕駛」；停下條件；走到佔位段而且沒有其他可做的段 |
| 使用者送一般訊息 | 結束模式、交回來報告 | 當成插入事項，處理完回到 roadmap 繼續 |
| 回來報告 | 使用者回來時交 | 改成每段做完就更新同一份報告（累積），使用者說暫停或模式結束時交 |
| 推播 | 無 | 要拍板的事（行為類主控裁決）在照推薦做之前先推播；使用者在場就能早點答，翻盤範圍比較小 |
| 收尾 | 做完路線 | 段做完，同一個 commit 改 roadmap 段狀態與清單勾選 |

使用者送的一般訊息若是改方向（例如「先做 O2」），就把新順序寫回 `docs/roadmap.md` 的列序，照專案的合併方式 commit 進主線，再照新順序繼續。理由是 roadmap 是唯一的來源，只記在帳本的話，跨天或 context 壓縮後重讀 roadmap 就會回到舊順序（主控決定）。

暫停的觸發詞只認「暫停」「停止自動駕駛」。「先停一下這個做法」這類話當成一般插手（主控決定）。理由是「停」字太常見，誤判就踩到反目標。

### 每段的流程

1. 重讀 roadmap 與清單。有 lifecycle 的 `feature_checklist.py` 就跑 `--open`，取「可開工」；沒有就自己讀段表，找第一個狀態不是「已上線／已完成／完成」的列。
2. 判斷這段能不能做：
   - 段表那一列連到存在、而且有內容的 spec：照無人值守第 2 節，逐單元做到合併、部署、驗證。沒有 spec 一律算佔位（實作時依 final review 收緊，不靠段表文字自己拆單元）。
   - 只有佔位（沒有 spec、內容寫「開工前再切段」之類）：在報告寫「待決：<段> 需要設計」，附問題草稿並推播。往後找下一個「不依賴它、而且已有設計」的段；找不到就結束模式、交報告。「不依賴」的判斷方式：那段沒有 ⛔ 指向佔位段，它的 spec 也沒寫要用到佔位段的產出；判斷不了就不跳（主控決定，寧可提早停，也不要做錯段）。
   - 段被 ⛔ 擋住（等裁決或前置）：同上，跳過並記進報告。
3. 段內所有單元都合併後，同一個 commit 把 roadmap 段狀態改成完成、清單相關項目打勾，再跑 `--check`（有 lifecycle 才跑）。這個 commit 照專案設定的合併方式進主線，規定走 PR 的專案就也開 PR（主控決定）。
4. 更新累積報告，回到步驟 1。

### 跨天執行

- context 被壓縮後，以帳本、roadmap、`git log` 為準接續。
- 額度用盡或 session 中斷時，使用者回來說「繼續自動駕駛」，就讀同一份帳本接續，不重做已合併的段。帳本路徑寫在報告開頭。
- 長測試可能因電腦睡眠逾時，照無人值守第 5 節判讀。

## 交給 builder 決定

- `autopilot.md` 的段落結構與用字；SKILL.md 怎麼指過去。
- 推播用哪個工具，以及沒有推播工具時（其他 CLI）的退路，例如只寫進報告。
- 判斷「只有佔位、沒有設計」的具體規則：怎樣算有 spec 連結、段表內容要多細才能直接拆單元。
- 沒裝 lifecycle 時讀段表的寫法：照 lifecycle `references/feature-checklist.md` 的段表定義自己讀。依 plugin 獨立規則，不呼叫 lifecycle 腳本也要能用。
- 版號與 CHANGELOG：workspace minor bump，起因寫本設計。
